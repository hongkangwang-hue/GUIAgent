# OCR 双引擎对照实验小结 —— M1 交付物 4

> PaddleOCR vs EasyOCR，同一批图、同一套预处理。
> 原始数据：`docs/m1-ocr-benchmark-synth.json`、`docs/m1-ocr-benchmark-real.json`。
> 复现方式见文末。

## 结论先说

1. **PaddleOCR 在本项目的场景下全面胜出**：真实截图上快 **1.55 倍**
   （合成的清晰小图上快 3.4 倍），中文 / 英文 / 中英混排的字符准确率
   均为 **100%**，且零漏检。
2. **预处理（灰度 + CLAHE）没有带来收益**，两个引擎都是空跑组最好或持平，
   还多花时间。**这条是靠对照组测出来的，不是猜的。**
3. **一个初读会得出的错误结论**：原始数据显示「EasyOCR 混排 93.3% >
   PaddleOCR 88.3%」。深查后发现这是**空格输出约定**造成的假象——
   PaddleOCR 每个字都认对了，只是不输出中英之间的分隔空格。
   去空格归一化后 PaddleOCR 混排为 **100%**，而 EasyOCR 保持 88.9%
   （它的失分是真实的识别错误）。

系统因此保持 PaddleOCR 为默认引擎，EasyOCR 作为可切换的备选实现保留。

## 实验设计

### 为什么用合成测试集

交付要求记录**中文准确率、英文准确率**，而准确率需要**逐字真值**。

本项目手上的真实截图标注（`annotate.py` 产出的 `*.gt.json`）记的是
「元素框 + 元素名」，用途是召回率评测。那些标签是人凭印象打的，
不是屏幕文字的逐字转录——拿它当 OCR 真值，会把「人打的标签和屏幕上的字
不一样」误判成 OCR 识别错误。

也**不能拿一个引擎的输出当另一个的真值**：那只能证明两者像不像，
不能证明谁更准。

因此另建一组合成图：把已知字符串渲染到 GUI 版式的背景上，
**真值就是渲染时用的那个字符串**，逐字精确、零标注成本、完全可复现
（`scripts/make_ocr_testset.py`，种子 `20260823`）。

短语取自真实桌面界面的常见文案（`文件` / `蓝牙和其他设备` /
`Display resolution` / `Wi-Fi 设置`），而非随机字符——OCR 的语言模型会
利用上下文纠错，用无意义串测会低估它在真实界面上的表现。

**这组测的是两个引擎在清晰文本上的识别能力上限**，不能外推到真实截图。
真实截图那一组另测（见 §3），只报吞吐与延迟。

### 配置

| 项 | 值 |
|---|---|
| 合成集 | 6 张 1280×800，90 条逐字真值（中文 / 英文 / 中英混排） |
| 真实集 | ScreenSpot-v2 桌面子集随机 6 张（种子 20260823） |
| 预处理臂 | `passthrough`（空跑对照）、`default`（灰度 + CLAHE） |
| 硬件 | 宿主机，CPU 推理 |
| PaddleOCR | 3.7.0，PP-OCRv5_mobile 检测 + 识别 |
| EasyOCR | 1.7.2，`ch_sim` + `en` |

**空跑对照组不可省。** 没有它就无法证明预处理到底是帮忙还是帮倒忙。

## 1 主结果（合成集，逐字真值）

| 引擎 | 预处理 | 平均条数 | 平均耗时 | 中文 | 英文 | 混排 |
|---|---|---:|---:|---:|---:|---:|
| **paddleocr** | **passthrough** | 15.0 | **1902 ms** | **100.0%** | **100.0%** | 88.3% |
| paddleocr | default | 15.0 | 2114 ms | 100.0% | 99.8% | 88.3% |
| easyocr | passthrough | 14.7 | 6468 ms | 98.1% | 99.3% | 93.3% |
| easyocr | default | 14.5 | 6564 ms | 96.1% | 99.3% | 93.3% |

真值每张 15 条。PaddleOCR **6 张全部 15/15 匹配**，EasyOCR 平均 14.7 条
（存在漏检）。

### 速度

**PaddleOCR 1902ms vs EasyOCR 6468ms，快 3.4 倍。**

这个差距在本项目里是有实际后果的：Agent 每步都要做一次感知，
而隔离客机没有 GPU。M1 实测客机上 PaddleOCR 单张需 11.5 秒
（图更大、CPU 更弱），若换成 EasyOCR 会进一步恶化到不可接受。

> 相关发现：客机上 OCR 占满 4 个 vCPU 长达 11.5 秒，会把并行执行的
> UIA 通道饿死（COM 跨进程调用拿不到 CPU），导致 UIA 遍历被截断。
> 详见 `docs/m1-recall-evaluation.md`。这进一步说明 OCR 的耗时不只是
> 它自己的问题。

## 2 那个混排指标是假的

原始表格里 EasyOCR 混排 93.3% 高于 PaddleOCR 88.3%，
初读会得出「EasyOCR 更擅长中英混排」。**这个结论是错的。**

逐条比对识别结果：

| 真值 | PaddleOCR | EasyOCR |
|---|---|---|
| `OK 确定` | `OK确定` | `OK 确定` |
| `PDF 导出` | `PDF导出` | **（漏检）** |
| `Wi-Fi 设置` | `Wi-Fi设置` | `Wi-Fi 设置` |
| `USB 设备` | `USB设备` | `USB 设备` |

**PaddleOCR 每一个字都认对了**，差异全部来自它不输出中英之间的分隔空格。
EasyOCR 保留空格，因此在按字符串严格比对的口径下得分更高。

去空格归一化后重算：

| 引擎 | 语种 | 原始 | 去空格后 | 差值 |
|---|---|---:|---:|---:|
| paddleocr | 中文 | 100.0% | 100.0% | — |
| paddleocr | 英文 | 100.0% | 100.0% | — |
| **paddleocr** | **混排** | 86.7% | **100.0%** | **+13.3%** |
| easyocr | 中文 | 97.4% | 97.4% | — |
| easyocr | 英文 | 99.3% | 99.2% | — |
| **easyocr** | **混排** | 88.9% | 88.9% | **0** |

**PaddleOCR 三项全部 100%；EasyOCR 的失分不随归一化改变，是真实的识别错误。**

### 这对系统的影响

本项目用 OCR 的目的是**定位可交互元素**，不是精确转录。
元素文本用于匹配与展示，空格差异在下游一律会被归一化。因此：

- **系统层面：** PaddleOCR 的空格约定不构成问题
- **评测层面：** 报告 OCR 准确率时必须说明是否做了空白归一化，
  否则同一份识别结果能得出相反的结论

这也是一条通用的教训：**指标口径不明确时，数字会指向错误的方向**，
而且不会报错。

## 3 真实截图上的吞吐与延迟

ScreenSpot-v2 桌面子集随机 6 张（种子 `20260823`），分辨率从 606×744 到
1920×1080 不等。**该组无逐字真值，因此只报产出量与耗时，不报准确率**
——理由见「实验设计」。

| 引擎 | 预处理 | 平均条数 | 平均耗时 |
|---|---|---:|---:|
| **paddleocr** | passthrough | **28.0** | 5623 ms |
| paddleocr | default | 27.2 | **4921 ms** |
| easyocr | passthrough | 22.7 | 8728 ms |
| easyocr | default | 20.8 | 8305 ms |

### 两点与合成集不同的观察

**其一，速度差距收窄。** 合成集上 PaddleOCR 快 3.4 倍，真实截图上只快
1.55 倍（5623 ms vs 8728 ms）。真实截图分辨率更高、文本更密、
背景更复杂，两个引擎的检测阶段都变重，固定开销被摊薄。

**报告速度优势时应引用真实截图的 1.55 倍，而不是合成集的 3.4 倍**——
后者是干净小图上的理想值。

**其二，预处理在真实截图上反而更快，但产出更少。**

| 引擎 | 条数变化 | 耗时变化 |
|---|---|---|
| paddleocr / default | **−0.8** | **−702 ms（0.9×）** |
| easyocr / default | **−1.8** | −423 ms（1.0×） |

灰度化把三通道变成单通道，检测阶段的数据量减少，所以更快。
但**识别出的文本条数同时下降**。

**没有真值就无法判断少掉的那些是漏检还是去噪**，这一点必须如实写明，
不能因为「变快了」就把它当成优化。合成集那一组有真值，
在那里 `default` 的准确率是下降的（PaddleOCR 英文 100.0% → 99.8%，
EasyOCR 中文 98.1% → 96.1%），因此本项目仍然保持 `passthrough` 为默认。

## 4 预处理：不提升准确率，速度影响两组相反

`default` = 灰度 + CLAHE。与空跑组相比：

| | 合成集（1280×800） | 真实截图（分辨率不一） |
|---|---|---|
| paddleocr 条数 | ±0 | **−0.8** |
| paddleocr 耗时 | +213 ms（1.1×，**更慢**） | −702 ms（0.9×，**更快**） |
| easyocr 条数 | −0.2 | −1.8 |
| easyocr 耗时 | +96 ms（1.0×） | −423 ms（1.0×） |

速度方向相反：合成图小且干净，灰度化省下的时间抵不过多一道处理的开销；
真实截图大，三通道变单通道省下的数据量更可观。

**但准确率上两组结论一致——都是空跑更好。** 合成集有真值，可直接验证：
PaddleOCR 英文 100.0% → 99.8%，EasyOCR 中文 98.1% → 96.1%。
真实截图无真值，只能观察到条数下降，**无法判断少掉的是漏检还是去噪**。

综合两组：`default` 在有真值可验证的那一组明确降低准确率，
在另一组只能确认「产出变少」。**因此系统默认设为 `passthrough`。**

### 为什么会这样

现代 OCR 的检测与识别网络是在自然图像上训练的。灰度化丢掉颜色通道、
CLAHE 改变局部对比度分布，都让输入偏离训练分布。
「预处理提升 OCR」的经验来自 Tesseract 时代的传统算法，
在深度学习引擎上不再成立。

> 项目早期的默认配置还包含 **2× 超分**，M1 阶段实测在整屏截图上是净亏损
> （+51 秒换 +1 个识别框）：2560×1600 放大到 5120×3200 后超过 PaddleOCR
> 的 `max_side_limit`，反被内部缩回去。该配置已从默认值移除，
> 保留为 `upscale2x` 对照臂以便复现该结论。

## 5 选型结论

| 维度 | PaddleOCR | EasyOCR | 采用 |
|---|---|---|---|
| 速度（合成 1280×800） | **1902 ms** | 6468 ms | PaddleOCR |
| 速度（真实截图） | **5623 ms** | 8728 ms | PaddleOCR |
| 产出量（真实截图） | **28.0 条/图** | 22.7 条/图 | PaddleOCR |
| 中文准确率 | **100%** | 97.4% | PaddleOCR |
| 英文准确率 | **100%** | 99.2% | PaddleOCR |
| 混排准确率（归一化） | **100%** | 88.9% | PaddleOCR |
| 漏检 | 0（15/15 全中） | 平均 0.3 条/图 | PaddleOCR |
| 空格约定 | 不输出中英分隔空格 | 保留 | EasyOCR（对本项目无影响）|
| 安装体积与依赖 | paddlepaddle | torch | 相当 |

**默认引擎：PaddleOCR。** EasyOCR 作为 `OCREngine` 的另一个实现保留在
代码中，接口一致，可通过配置切换——保留它的价值在于：若将来在
无 PaddlePaddle 支持的平台上部署，或需要交叉验证识别结果时可直接启用。

### 需要说明的局限

- **合成图比真实截图干净**：没有半透明叠加、渐变背景、抗锯齿差异与
  遮挡。本文的 100% 是**清晰文本上的能力上限**，不是真实界面的识别率。
- 样本量小（6 张 / 90 条），且短语取自 Windows 设置类界面，
  未覆盖代码编辑器、终端、表格等文本密集场景。
- 仅测 CPU 推理。GPU 下两者的相对差距可能变化。
- 未测识别框的定位精度（只比对文本内容）。定位质量由
  `docs/m1-recall-evaluation.md` 的召回率实验覆盖。

## 复现

```bash
# 1. 生成合成测试集（种子固定，结果可复现）
python scripts/make_ocr_testset.py --count 6

# 2. 合成集：准确率 + 耗时
python scripts/ocr_benchmark.py --dir data/ocr-testset \
    --configs passthrough default --out docs/m1-ocr-benchmark-synth.json

# 3. 真实截图：吞吐 + 耗时
python scripts/ocr_benchmark.py --dir data/ocr-realset \
    --configs passthrough default --out docs/m1-ocr-benchmark-real.json
```

真实集的图来自 ScreenSpot-v2 桌面子集，按种子 `20260823` 随机抽 6 张
（见 `data/` 模块的下载脚本）。
