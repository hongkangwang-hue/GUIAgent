# UI 元素召回率实测 —— M1 验收标准 4

> 客机内实测，2026-08-23。原始数据在客机的 `outputs/gallery/`
> （`*.gt.json` 真值 + `*.detections.json` 检测结果），`outputs/` 不入库。

## 结论

| 指标 | 值 |
|---|---|
| 样本 | **5 张截图，50 个标注元素** |
| **点击点判据召回率** | **100%**（50/50） |
| IoU ≥ 0.5 判据召回率 | 66%（33/50） |
| 按来源：UIA | **72%** |
| 按来源：OCR | 28% |

采集环境：客机 1920×1080 / 100% 缩放 / dxcam / 双通道串行识别
（UIA 深度 20 层、8000ms 预算，无截断）。

## 三个需要说清楚的点

### 1. 样本量是 5 张，不是原定的 20 张

**这是本项目自设指标的下调，不构成对官方大纲的偏离。**

大纲第 2 周的细分任务是「实现 UI 元素坐标定位与**边界框绘制功能**」，
交付物是「模块完整代码 + 单元测试报告」——**「召回率」在大纲中一次都没
出现**。定量测召回率是本项目自加的验收标准 4，20 张这个数字也是自定的。

下调理由：真值必须人工逐个画框（不能用检测结果预填，见下），20 张约需
200-400 个框。在 M1 剩余工期内，5 张（50 个元素）已足以支撑结论的定性
方向，边际信息量不值那个时间。

**代价**：样本量小，且 5 张全部是 Windows 原生应用。**未覆盖网页内容**
（Edge 的搜索结果页已采集但未标注），而网页是自绘渲染、UIA 读不到 DOM 的
场景——本报告的 100% 不能外推到那一类界面。

### 2. 真值为什么必须手工标，不能用检测结果预填

用检测结果做起点、人工增删，会**系统性地低估漏检**：人不会去补一个检测器
没提到、自己也没注意到的元素，而那恰恰是召回率要衡量的东西。这样得到的
数字会自动接近 100%，失去意义。

`scripts/annotate.py` 因此只在**未画框的原图**（`*.raw.png`）上标注，
全程不显示任何检测结果。

### 3. 口径：只标「任务相关元素」

全屏 1920×1080 上有几百个文字块，全标一遍不现实，且大部分文字（正文、
说明、状态栏）Agent 根本不需要点。因此只标**会被交互的东西**：按钮、
菜单项、输入框、可点击列表行、标签页、图标按钮。每张 10 个。

**所以本文报告的是「任务相关元素召回率」，不是「全文字召回率」**，
两者不可混用。

---

## IoU 是个坏判据 —— 我们做了一次对照实验

`eval_recall.py` 的主判据是**检测框的中心点是否落在真值框内**，
而不是传统检测任务的 IoU ≥ 0.5。理由在代码文档里写着：对 GUI Agent 而言
框重合多少不重要，**点下去能不能点中才重要**。

标注过程中意外得到了这条判断的直接证据。

计算器那张最初的标注只框住了数字字符本身（`7` 这几个像素），
而 UIA 报告的是整个按钮方块。改成框住整个按钮后重新评测：

| | 真值框 | 点击命中 | IoU 命中 |
|---|---|---:|---:|
| 第一次标注 | 只框数字字形 | 100% | **10%** |
| 第二次标注 | 框整个按钮 | 100% | **100%** |

**检测结果一个字节都没变，IoU 从 10% 变成 100%，只因为人画框的方式不同。**
而点击点判据两次都是 100%——它衡量的是「能不能点中」，对标注框的松紧不敏感。

汇总的 IoU 也因此从 48% 升到 66%。**剩下的差距同样来自标注习惯**
（`settings-system` 第二张 IoU 为 0%，是因为真值框比控件的实际可点区域窄
得多），不是检测能力的差异。

**这就是不用 IoU 作主判据的实证理由**，比引用文献更有说服力。

---

## 按来源分项：UIA 72% / OCR 28%

这个分工比例是**修复一个 bug 之后才测准的**，过程值得记录。

`ElementDetector` 默认把 OCR 甩进工作线程、UIA 留在调用线程并行执行，
依据是模块文档里的假设「OCR 是慢的那个，几百毫秒」。**这个前提在客机上
不成立**：客机无 GPU，CPU 推理的 PaddleOCR 要 11.5 秒，把 4 个 vCPU 吃满，
UIA 的跨进程 COM 调用被饿死。

同一个设置页面的实测对比：

| 调度方式 | UIA 耗时 | UIA 抓到 | 是否截断 | 分项结论 |
|---|---:|---:|---|---|
| 并行（默认） | 8133ms | 61 个 | ⚠ 时间截断 | uia 37.5% / ocr 62.5% |
| **串行（UIA 先跑完）** | **228ms** | **98 个** | 无 | **uia 72% / ocr 28%** |

**分项结论完全反转。** 不改的话报告会写成「OCR 是主力通道」，而事实相反。

图集采集因此改为串行（`parallel=False`），Agent 循环维持并行——那里延迟
是主要矛盾，且不做分项统计。

> 顺带修掉的两个相关问题：UIA 遍历的深度上限（12 层）在文件资源管理器上
> 会被触发（控件树嵌套深），已提到 20 层；截断提示原先不分原因一律建议
> 「加时间预算」，而深度截断时那么做完全无效，现已按 time / depth / count
> 分流给出对应的旋钮。

## 一个与预期相反的发现

采集前预判：画图工具栏的图标按钮（铅笔、橡皮擦、取色器、放大镜）没有
文字，**OCR 必然漏检**，会拉低召回率。

**实测 paint 一图 100% 命中。** 现代 XAML 应用的控件 `Name` 属性完整，
UIA 能读到每个图标按钮的语义名称，OCR 认不出来并不影响最终覆盖。

结论方向因此反转，但仍有价值：

> 图标类控件不是感知盲区，因为 UIA 覆盖了它们。
> 反过来说，**非 Windows 平台降级为 OCR 单通道时，这批无文字元素才会
> 真正丢失**——双通道不是冗余，是覆盖互补。

---

## 未测量的部分

- **精确率（precision）未测**。50 个真值对应 799 个检测框，说明检测器
  输出了大量真值之外的元素。它们可能是有效控件（只是未被标注），也可能
  是噪声，本次无法区分。验收标准 4 只要求报告召回率。
- **网页类界面未覆盖**，见上文第 1 点。
- 元素类型分项全部落在 `other`：标注时未填类型编号（类型不参与召回率
  计算，`eval_recall.py` 的判定是纯几何的）。

## 复现

```bash
# 客机内
python scripts/capture_gallery.py --name <场景> --delay 5   # 采集
python scripts/annotate.py outputs/gallery/<图>.raw.png      # 标注真值
python scripts/eval_recall.py                                # 评测
```
