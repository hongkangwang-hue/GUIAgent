### 那 1 条跳过是什么

`test_safety.py::test_ordinary_text_passes[shutdown 是一个危险命令]`

参数化用例里的一条。文本 `shutdown 是一个危险命令` 会被安全规则拦下——
**这是有意接受的误报**，由紧邻的 `test_pattern_matching_has_false_positives`
专门断言并说明理由：

> 宁可挡住一次无害的输入，也不要放过一次真的关机。误报的代价是模型换一种
> 说法重试，漏报的代价是测试环境重装。

同组还有 `test_pattern_matching_can_be_bypassed`，明确记录**文本匹配挡不住
有意规避**（拆成两次输入即可绕过）。**已知局限写成测试，而不是留在注释里。**

### 为什么有五个模块低于 70%

**它们的未覆盖部分全部是「必须有真实硬件才能进入」的分支**，不是遗漏：

| 模块 | 未覆盖的是什么 | 由什么覆盖 |
|---|---|---|
| `dpi.py` 32% | Windows `SetProcessDpiAwareness` / `GetDpiForWindow` 等 Win32 API 调用 | `scripts/diagnose_capture.py`、`verify_control.py` |
| `uia_tree.py` 50% | pywinauto 遍历真实控件树 | `scripts/capture_gallery.py`（实测 799 个元素） |
| `ocr_engine.py` 59% | PaddleOCR / EasyOCR 的实际推理调用 | `scripts/ocr_benchmark.py`（90 条逐字真值） |
| `executor.py` 60% | pyautogui 真实点击 / 输入 / 拖拽 | `scripts/verify_control.py`（12 点坐标链） |
| `emergency_stop.py` 64% | pynput 全局热键监听线程 | `scripts/verify_control.py` |

`pyautogui.click` 只能证明「我们调用了这个函数」，证明不了「点击真的落在了
那个像素上」。后者只有真机能证，而真机结果记录在 `docs/` 下的三份实测报告里：

| 能力 | 实测结果 | 出处 |
|---|---|---|
| 坐标链精度 | 12 个目标点最大偏差 **0.0 px** | `m1-control-verification.md` |
| OCR 准确率 | PaddleOCR 中/英/混排 **100%**，快 1.55 倍 | `m1-ocr-双引擎对照实验小结.md` |
| UI 元素召回 | 点击点判据 **100%**（50/50） | `m1-recall-evaluation.md` |

### 现场可复现的一例：`dpi.py` 与 `capture.py`

这两个模块的单元测试覆盖率分别是 **32%** 和 **80%**，而
`python scripts/diagnose_capture.py` 一条命令就能在真机上把它们跑通。
2026-08-26 在宿主机（2560×1600 / 150% 缩放）的实测输出：

```
DPI 144（缩放 150%，感知=True）

  dxcam      -> dxcam      2560x1600  中位     5.0ms  最快   4.3ms
                画面：非零像素 99.0%，均值 144.4   看起来正常
  mss        -> mss        2560x1600  中位    27.4ms  最快  26.9ms
  pyautogui  -> pyautogui  2560x1600  中位    64.4ms  最快  63.4ms
```

这四行分别验证了四件单元测试证不了的事：

| 输出 | 证明了什么 |
|---|---|
| `DPI 144（缩放 150%，**感知=True**）` | DPI 感知已生效。**不启用的话 Windows 会谎报成 1706×1066**，每次点击都偏 1.5 倍 |
| 三个后端都报 `2560x1600` | 它们对物理分辨率的判断一致，坐标系没有分歧 |
| `5.0 / 27.4 / 64.4 ms` | dxcam 比 mss 快 5.5 倍、比 pyautogui 快 12.9 倍——**这就是把 dxcam 设为首选、mss 作降级的实测依据** |
| `非零像素 99.0%…看起来正常` | 画面不是黑的。**截图路径坏掉时最典型的表现是返回全黑图而不是报错**，那种情况下速度和尺寸都正常，只有内容是空的 |

对照客机（`docs/m1-guest-environment.md`，1920×1080 / 100% 缩放 /
dxcam p50 0.043ms）：**同一份代码、两种分辨率、两种 DPI 缩放，都正确适配**
——这是大纲第 2 周任务 1「支持多分辨率适配」的直接证据，
而它恰恰落在单元测试覆盖率最低的那两个模块上。

已覆盖的部分则是**纯逻辑**：坐标换算、IoU 去重、动作参数校验、安全规则匹配、
后端降级判断——这些一旦错了，真机上表现为「莫名其妙点偏」，极难定位，
所以正是单元测试该守的地方。

## 4. 测试写法说明

本项目的测试有两条自定规矩，读代码时会看到：

**① 测试名与 docstring 用中文，且写明「为什么」而不只是「是什么」。**
例如 `test_图标高亮不算变` 的 docstring 记录了它守的具体场景与阈值来源。
交付对象是需要理解设计取舍的人，不是 CI。

**② 踩过的坑写成测试，而不是写成注释。**
`test_capture.py` 里关于 DPI 感知调用顺序的用例，对应的是
`m1-control-verification.md` 22:33 那次「DPI 记成 100%（实为 150%）」的
真实事故；`test_coordinate.py` 里关于屏幕四角的用例，对应 22:36 那次
「坐标链检查与 PyAutoGUI FAILSAFE 在四角冲突」。

## 5. 复现

```bash
cd <本交付目录>

# 全部用例
python -m pytest -v

# 覆盖率（本报告 §3 的表由它生成）
python -m pytest --cov=perception --cov=control --cov-report=term-missing

# 用例清单
python -m pytest --collect-only -q

# 真机验证：截图后端与 DPI（§3 末尾那段输出由它生成，需要真实桌面）
python scripts/diagnose_capture.py
```

**无需安装。** `pyproject.toml` 已配置 `pythonpath = ["src"]`。
单元测试只依赖 `pytest` / `numpy` / `pillow`，OCR、UIA、dxcam 等可选依赖
缺失时相关用例走降级路径，不会失败。
