# 里程碑 4：错误恢复与系统鲁棒性优化

## 周期与验收要求

- 周期：2026-09-21 ~ 2026-09-27（第 6 周），投入强度 20-30 小时/周。
- 验收要求：需在 2026-09-27 前完成里程碑验收。
- 验收方式：错误恢复过程实机演示 + 代码走读 + 鲁棒性测试数据评审。
- 汇报材料：里程碑汇报 PPT（10-12 页）+ 错误恢复过程录屏 + 实时监控面板演示。

## 阶段目标

把系统从"能跑通简单任务"提升到"能跑完较长任务且能从常见错误中恢复"，产出系统 v2.0。

本阶段不做新的模型实验，重点是**系统能力的实质提升**，且每一项改进都要有 M2、M3 积累的真实失败数据作为依据。

## 设计思路

本里程碑的核心方法论是：**不凭直觉加功能**。所有优化必须先从 M2 和 M3 积累的失败轨迹中归纳出错误分类，再针对每一类设计检测手段与恢复策略。没有分类依据支撑的优化一律不做——这既是工程纪律，也是技术报告里最有分量的一段内容。

**关于错误分类的重要说明。** 下文列出的 E1-E8 是**预期分类假设**，用于给打标提供起步词表，不是结论。真实数据大概率会呈现三种偏差：某几类高频、某几类一次未出现、以及出现假设外的新类型。本阶段的正确做法是**按实测频次重建分类体系**，删掉零频次类别、合并近似类别、补上新发现类别，并在报告中说明每一处增删的理由。一份"和预设完全吻合"的分类表反而说明打标不认真。

**Reflector 采用级联判定，不做三 Agent 协作。** M2 的子任务完成判定用的是简单规则，在较长任务上不够用，但完整的三 Agent 架构（含子任务 DAG 与全局重规划）在本周投入强度下装不下，且与延迟目标冲突——每个子任务都做一次语义判定会显著拉长单步耗时。因此采用三级级联：

1. **OpenCV 帧差**（免费、毫秒级）：界面完全没变 → 直接判定动作未生效
2. **程序化判据**（免费、毫秒级）：进程 / 窗口标题 / 文件存在性 / UIA 控件存在性，命中即出结论
3. **语义判定**（仅在前两级结论冲突或均无法判定时触发）：**优先用 M3 已在本地部署的 Qwen2.5-VL-3B**——它已经常驻显存，边际成本为零，只增加一次本地推理的延迟；本地模型判不准时才升级到 API 模型

绝大多数步骤应在前两级就出结论，语义判定的触发率是本阶段要记录的一项关键指标。**把语义判定放在本地模型上，是本项目全开源路线带来的一个实打实的好处**——用前沿 API 的方案在这里必须精打细算触发率，本方案不必。

**成本优化不做专项。** M3 的模式 B 分流（高分辨率截图不出本地）已经承担了主要降本职责，本阶段只做上下文裁剪的收尾，把节省数据汇总成表即可。本阶段真正要优化的是**延迟**，见下条。

**延迟优化要打在实处。** 单步延迟由四段构成：API 调用（数秒）、本地 grounding 推理（1-3 秒）、动作执行（毫秒级）、截图（15ms）。截图只占 0.2%，继续优化毫无收益。两个真正的可压缩项：

- **每个动作后的固定 sleep 0.5-1.5 秒** → 改为自适应帧稳定检测（连续两帧帧差低于阈值即认为界面稳定），可节省接近 1 秒/步
- **本地 grounding 模型常驻显存**，避免每次调用重新加载权重（冷加载可达数十秒）

本阶段的延迟对比表要按四段分解，让优化收益可归因。

## 模块与目的

1. Reflector 判定模块 `agent/reflector.py`
   目的：以级联方式判定子任务是否达成，输出结构化失败原因，驱动重试或终止。

2. 执行器升级 `agent/executor.py`
   目的：携带当前子任务目标而非全局目标进入 Agent Loop，缩小上下文、降低跑偏概率。

3. 错误恢复模块 `core/recovery.py`
   目的：实现实测高频错误类型的检测与对应恢复策略，含指数退避、回滚动作与全局步数约束。

4. 感知优化 `perception/`
   目的：两条线并行——依据实测错误分类调参以**提升识别准确率**；通过实例复用、OCR 缓存与自适应等待**降低单步延迟**。

5. 可观测模块 `core/monitor.py`
   目的：结构化日志、日志轮转与 Rich 实时监控面板，支撑调试与 M5 演示视频素材。

## 交付物

1. 错误分类体系文档（基于实测频次重建，每类含定义、检测手段、恢复策略、典型案例截图）。
2. Reflector 级联判定实现，含各级触发率统计。
3. 错误恢复模块实现，含重试策略与回滚动作。
4. 较长任务测试集（3 个，8 步以上，同应用内）。
5. 《系统鲁棒性测试报告》，约 2500 字，基于不少于 200 步真实执行数据。
6. 感知优化对比表（**元素识别召回率**、单步延迟四段分解、OCR 调用次数、单任务成本，v1.0 vs v2.0），准确率改动逐条附失败案例依据。
7. Rich 实时监控面板与演示录屏。
8. 系统 v2.0。

## 任务拆解

1. 失败轨迹汇总与错误分类重建（D1）
   - 汇总 M2 与 M3 已用 `label` 命令打标的全部失败轨迹（打标在 M2/M3 跑的时候已完成，本日只做汇总归纳，**不做集中人工复盘**）。
   - 统计各类型实测频次，按数据重建分类体系：删零频次类、合并近似类、补新发现类。
   - 预期分类假设（起步词表）：E1 定位偏移 / E2 界面未响应 / E3 意外弹窗 / E4 状态误判 / E5 幻觉动作 / E6 加载超时 / E7 焦点丢失 / E8 路径偏离。
   - 每类记录出现频次、典型截图、当时的模型思考内容。
   - 输出错误分类体系文档初稿，**并明确记录相对预期假设的每一处增删及理由**。

2. Reflector 级联判定实现（D2-D3）
   - 第一级：OpenCV 帧差，动作前后截图差异低于阈值即判定动作未生效。
   - 第二级：程序化判据，按子任务类型选择进程检查 / 窗口标题 / 文件存在性 / UIA 控件存在性。
   - 第三级：语义判定，**优先用本地常驻的 Qwen2.5-VL-3B** 看截图判断，本地判不准时才升级到 API 模型；**仅在前两级冲突或均无法判定时触发**。
   - 输出「成功 / 重试 / 放弃」三选一决策与失败原因（不做重规划，见明确不做）。
   - 记录三级各自的触发率与最终判定分布。
   - 升级 Executor：携带当前子任务目标而非全局目标进入 Agent Loop。

3. 错误检测与恢复机制（D3-D4）
   - **按 D1 重建后的分类实现**，优先覆盖频次最高的 4-5 类，低频类别记录但不实现恢复。
   - 检测手段：帧差阈值判定、UIA 控件存在性校验、新增大面积矩形区域检测（弹窗）、窗口标题检查、超时阈值、Reflector 语义判定。
   - 恢复策略：本地 grounding 重定位、指数退避（1s/2s/4s）、弹窗关闭子流程、强制重新截图确认、回传"该位置无可交互元素"、延长等待、重新激活目标窗口、回滚动作（Alt+← / Esc）。
   - 全局约束：单步最多重试 3 次，单任务最多 30 步，超限即终止并记录。
   - 定义 3 个较长任务用于验证（8 步以上，**限同应用内**）：浏览器内多步搜索与结果保存、文件管理器内批量按类型整理、文档编辑后另存为指定格式。

4. 感知优化：准确率与速度两条线（D5）

   **① 准确率**（大纲 W6 明确要求"提升 UI 元素识别的准确率"，且直接对应 D1 归纳出的定位偏移类错误）：
   - 从 D1 的错误分类中筛出所有因**识别错误**导致的失败案例，逐条定位是 OCR 漏检、UIA 抓取不全、还是融合去重误删。
   - 按定位到的具体问题调参：OCR 预处理链（CLAHE 强度、超分倍率、二值化阈值）、UIA 遍历深度与控件类型过滤、双通道融合的 IoU 去重阈值。
   - **改动必须有失败案例支撑**，禁止凭直觉调参数。在 M1 的 20 张测试截图上回归验证，确认召回率未因调参而倒退。
   - 记录优化前后的召回率变化与对应的错误类型频次变化。

   **② 速度**：
   - **自适应等待**：固定 sleep 0.5-1.5 秒改为帧稳定检测（连续两帧帧差低于阈值即继续），这是本项优化的主要收益来源。
   - **本地模型常驻**：grounding 模型与语义判定模型加载一次后保持在显存中，避免重复冷加载。
   - mss 实例复用 + 区域截图替代全屏。
   - 帧差检测，界面未变化时复用上次 OCR 结果（LRU 缓存），目标减少 40% 以上 OCR 调用。
   - 上下文收尾优化：历史截图窗口 k=3、旧截图降采样、更早步骤只保留文本摘要。
   - 逐项记录优化前后数据，**延迟按 API / grounding / 执行 / 截图 四段分解**；成本部分汇总模式 B 的既有收益，不做新的专项优化。

5. 可观测性建设与鲁棒性测试（D6-D7）
   - Python logging + JSON formatter 结构化日志，分级 DEBUG/INFO/WARNING/ERROR。
   - `RotatingFileHandler` 日志轮转，单文件 10MB 保留 10 份。
   - Rich Live 实时监控面板：左侧截图缩略图 + 中间步骤日志流 + 右侧统计（步数/耗时/token/成本/重试次数）。
   - 跑通鲁棒性测试：累计不少于 200 步真实执行（大部分可挂机），统计各类错误分布与恢复率。
   - 完善错误分类体系文档，补全每类的修复前后对比数据。
   - **续写技术报告"讨论"章节初稿**（滚动写作）。

## 验收标准

1. 错误分类体系基于不少于 200 步真实执行数据**重建**，每类有频次统计与典型案例佐证，相对预期假设的增删有理由说明。
2. Reflector 级联判定实现完成，三级触发率有数据记录，**语义判定触发率不高于 30%**——语义判定虽走本地模型、无额外费用，但每次增加 1-3 秒推理延迟，触发过频会拖垮单步耗时。
3. Reflector 的子任务判定准确率与人工判定对照，**报告**实测一致率。
4. 较长任务（8 步以上）在 v2.0 上可稳定跑完，**报告**相对 v1.0 的成功率变化及样本量说明。
5. **报告**错误自动恢复率（可恢复错误中被成功恢复的比例），按错误类型分项。
6. 单步平均延迟较 v1.0 下降不低于 20%，延迟按 API / grounding / 执行 / 截图 四段分解，优化来源可归因到自适应等待、模型常驻、OCR 缓存等具体项。
7. OCR 调用次数较 v1.0 减少不低于 40%。
8. **元素识别召回率较 v1.0 有提升**（在 M1 的 20 张测试截图上回归验证），每一处参数改动都能对应到 D1 错误分类中的具体失败案例。
9. 单任务平均 API 成本较 v1.0 有下降，收益来源（模式 B 分流 / 上下文裁剪 / 语义判定走本地模型）可分项归因。
10. 系统连续运行 1 小时无崩溃、无内存泄漏。
11. 现场能实机演示一次完整的「失败 → 检测 → 恢复 → 成功」过程。

## 明确不做

1. 不做任何模型训练或微调相关工作，M3 已完成。
2. 不新增 LLM 后端或 grounding 后端。
3. **不做三 Agent 协作架构。** Planner 维持线性子任务列表，不做子任务 DAG；Reflector 只输出「成功 / 重试 / 放弃」，不做失败重规划。
4. 不做跨应用复杂任务，较长任务限定在同一应用内。
5. **不做截图延迟专项优化（15ms → 5ms）。** 截图仅占单步延迟 0.2%，优化无实际收益，改为优化动作后等待。
6. 不做成本优化专项，收益由 M3 的模式 B 分流承担，本阶段只做上下文裁剪收尾与数据汇总；本阶段的优化重点是延迟，不是成本。
7. 不新增模型部署，语义判定复用 M3 已部署的本地模型。
8. 不做正式的 15 任务全面评估与消融实验，留到 M5。
9. 不做人工介入（human-in-the-loop）交互设计。
10. 不做多任务并发与任务队列调度。
11. 不做 Web 前端界面，监控面板仅限终端。
12. 不做无限重试与自适应策略学习，重试次数与退避参数为固定配置。
13. 不追求全部错误类型可恢复，幻觉动作与路径偏离类允许直接终止并记录。
