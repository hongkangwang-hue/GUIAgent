# 里程碑 3：模型微调、多模型横评与模式 B 接入

## 周期与验收要求

- 周期：2026-09-14 ~ 2026-09-20（第 5 周），投入强度 20-30 小时/周（不含挂机时间）。
- 验收要求：需在 2026-09-20 前完成里程碑验收。
- 验收方式：训练日志与 loss 曲线检查 + 横评数据评审 + 模式 A/B 对比数据评审 + 评测脚本复现验证。
- 汇报材料：里程碑汇报 PPT（10-12 页）+ 定位准确率对比图表。

## 阶段目标

完成一次轻量 LoRA 微调，产出专用 grounding 模型；**把它接入系统成为模式 B**；并在统一评测口径下横向对比官方大纲点名的三个开源多模态模型的定位能力。

本阶段的核心不是"做完一次微调"，而是**让微调成果在系统里承重**。一个跑完就归档的微调实验对项目价值有限；一个被系统真正用起来、并且有明确对照数据的 grounding 模块，才是这个项目在"模型微调"这项能力上最有说服力的证据。

## 设计思路

**本周有两条线，一条吃人力，一条吃挂机时间，必须并行安排。**

- **挂机线**：LoRA 训练、三个模型的 ScreenSpot 批量评测、提示词消融批量执行。这些都不需要盯着，应排在上课与夜间。
- **人力线**：模型部署调试 + `LocalVLMGrounding` 的实现与接入。接入是本周成败所在，**必须给到两个完整白天**。

**微调对象收窄为 Qwen2.5-VL-3B。** GUI 场景的显存瓶颈不在权重而在视觉 token，一张高分辨率截图会产生 2000-2600 个视觉 token。3B 级模型 4-bit 量化后权重估算 2-3GB，**但 8GB 卡是否够用取决于激活显存，以 M2 前置件的峰值实测为准**（可能需要通过 `max_pixels` 限制视觉 token 数）；训练放在 Colab 或短租 GPU 上（笔记本连续满载 5-8 小时会降频，且这期间机器无法使用）。目标单一（提升"指令 → 坐标"定位准确率），指标单一（ScreenSpot 命中率），结论干净可信。

**关于模型版本的选型说明。** 官方大纲写的是 Qwen-VL-Chat（初代版本），本项目改用 **Qwen2.5-VL** 系列。理由是初代 Qwen-VL-Chat 不具备可靠的坐标输出能力，而 GUI 定位任务的前提就是模型能输出坐标点。这一替换需在报告中作为技术选型论证写明——**这本身就是有价值的工程分析**。

**只自部署一个模型。** 判断标准是"这个模型别人跑不了才需要自己跑"：Qwen2.5-VL-7B、GLM-4V-9B、Llama 3.2 Vision 都是公开权重且不做微调，自部署除了拿到显存数字不产生独有产出，因此**横评全部走 API**，只用一次 3-4 小时的短租补齐显存与延迟实测。**唯一必须自部署的是微调后的 3B**——LoRA adapter 无法上传公共 API 平台。

**任务优先级必须明确。** 本周内容偏多，按以下顺序保：

| 优先级 | 内容 | 说明 |
|---|---|---|
| P0 | Qwen2.5-VL-3B 本地部署 + LoRA 微调 + ScreenSpot 档 1/2/4 评测 | 大纲 W5 的核心要求，不可降级。这三档即可支撑核心结论 |
| P0 | `LocalVLMGrounding` 实现与系统接入 | 决定微调成果是否承重，本周最吃人力 |
| P1 | 提示词消融（3 版本） | 大纲 W5 明确要求"优化提示词工程" |
| P1 | 横评 API 调用（7B / GLM-4V / Llama） | 挂机批量跑，人力成本很低 |
| P2 | 短租 3-4 小时补显存与延迟实测 | 让横评表全是自测数据，约 ¥10；受阻则改为估算+引用并说明 |

## 模式 B 的实现形态

以 M2 D1 的可行性验证结论为准，二选一：

| | 形态 1（首选） | 形态 2（降级） |
|---|---|---|
| 触发条件 | M2 验证确认规划模型能稳定输出结构化元素描述 | 描述输出不稳定或不够具体 |
| 规划模型职责 | 只做规划与语义决策，输出 `{action, target_description}` | 仍输出坐标 |
| 本地模型职责 | 由描述定位坐标（唯一坐标来源） | 独立复核坐标，偏差超阈值时纠偏 |
| 送 API 截图 | 可降分辨率（省 token） | 维持原分辨率 |
| 成本收益 | 大 | 小 |

两种形态都能支撑 M5 的消融对比，形态 2 只是收益变小，不影响里程碑成立。

## 模块与目的

1. 微调数据构建模块 `finetune/data/`
   目的：把 M2 统一 schema 后的数据转换为 grounding 训练格式，切分训练/验证集。

2. 开源模型后端 `llm/qwen_vl_local.py`（本地）、`llm/glm4v_api.py`、`llm/llama_vision_api.py`
   目的：补齐 M2 预留的多后端实现。本地实现满足官方大纲"本地部署"要求，API 实现满足"API 调用"要求，共同验证 `LLMBackend` 抽象的可扩展性。

3. LoRA 微调模块 `finetune/`
   目的：用 PEFT 对 Qwen2.5-VL-3B 做 QLoRA 微调，产出可复现的训练脚本与 adapter 权重。

4. **本地 grounding 后端 `grounding/local_vlm.py`（本里程碑核心）**
   目的：实现 `GroundingBackend` 接口，把微调模型接入系统，使模式 B 可用。

5. 定位评测模块 `eval/grounding.py`
   目的：在 ScreenSpot 上统一评测各模型的定位准确率，判定标准为预测点落入真值 bbox。

6. 提示词消融模块 `agent/prompts/`
   目的：对 M2 建立的提示词模板库做版本化消融，确定最优模板并固化。

## 任务拆解

### 挂机线（尽早启动，占用日历时间但不占人力）

1. 构建微调数据集（D1 上午）
   - 从 ScreenAgent Desktop 子集抽样构建 grounding 样本，格式为「截图 + 元素描述 → 坐标点」。
   - 训练集 3000-4000 条，验证集 500 条。**三分划定后即冻结，本周不得再动**（划分工作已提前到 M2 后半段完成）。
   - **ScreenSpot 固定为零样本测试集**：不参与训练、不参与验证、不参与提示词版本选择、不参与超参数调优。任何一项沾上都构成测试泄漏，本周全部结论作废。M2 已完成截图级 / 站点级重叠检查。
   - **调参与提示词选型只能看验证集**（从 ScreenAgent 划出，与训练集不重叠）。ScreenSpot 只在最终确定配置后跑一次。
   - 用 Pandas 输出分布统计，确认元素尺寸与分辨率覆盖均衡。

2. LoRA 微调（D1 晚间启动，D2-D3 挂机）
   - 工具链：**Transformers**（模型加载）+ **PEFT**（LoRA）+ **bitsandbytes**（4-bit 量化与 `paged_adamw_8bit` 优化器）+ **Accelerate**（训练循环、混合精度与设备编排）+ **Datasets**（训练集组织）。完整走通这条链路本身就是大纲"掌握模型微调核心算法能力"的落点。
   - PEFT 配置：`r=16`、`lora_alpha=32`、`lora_dropout=0.05`，target 覆盖 q/k/v/o/gate/up/down proj。
   - 训练参数：batch=1、梯度累积 8、gradient_checkpointing 开启、图像最大边 896px、lr=1e-4、2 epoch、`paged_adamw_8bit`。
   - 精度按硬件选择：30 系及以上卡用 bf16，T4 只能用 fp16。
   - 每 200 步保存 checkpoint，防止训练中断。
   - 全程记录 loss 曲线与显存占用。

3. 提示词工程消融（D2-D3 本地挂机，与训练并行）
   - **3 个版本**：P1 零样本基线 / P2 +角色设定与动作规范 +few-shot 示例 / P3 +CoT 显式推理。
   - 每版本在 5 个基础任务 × 3 次上评测，共 45 次执行，记录成功率、平均步数、平均耗时。
   - **提示词版本选择不得参考 ScreenSpot 分数**——这是端到端任务集上的选型，与定位测试集互不接触。
   - **预期 P2 的提升幅度会明显大于使用前沿模型时**——开源模型对 few-shot 示例的依赖更强。这个对比结论要写进报告。
   - 确定最优版本，固化为默认提示词交给 M4。
   - 失败轨迹用 `label` 命令当场打标，并入 M4 错误分类数据基础。

### 人力线

4. Qwen2.5-VL-3B 本地部署（D1 下午）
   - 用 **Transformers** 加载 Qwen2.5-VL-3B-Instruct，配 **bitsandbytes** NF4 4-bit 量化。**权重估算 2-3GB，但峰值显存以 M2 前置件的实测值为准**——Qwen2.5-VL 动态分辨率下，一张 2560×1600 截图产生 2000+ 视觉 token，视觉塔与注意力激活可能超过权重本身。M2 已用真实分辨率截图测过峰值并据此确定 `max_pixels` 上限，本任务直接沿用该配置。
   - **前置**：确认 PyTorch cu128+ 与 bitsandbytes 的 Blackwell 支持已就绪（M1 的警告项在此必须转为通过）。若仍不可用，立即改为在租用 GPU 上部署，不要在本机死磕。
   - 实现 `QwenVLLocalBackend`，验证可通过 M2 的统一接口调用。
   - 记录显存峰值、单次推理延迟、模型冷加载耗时，形成实测数据。**报告中一律用实测值，不写"约 3GB"这类估算。**

   **本任务的前置件已在 M2 后半段完成**（见 M0《M3 前置件提前到 M2》）：三分划定与冻结、LoRA 100-step smoke test、3B 4-bit 单图推理 + 峰值显存实测、`target_description` 结构化输出验证。**本周开工第一件事是核对这四项的记录是否齐全**；若 M2 未完成任一项，当天补做，并按降级路径评估是否收缩本周范围。

5. 横评 API 后端接入（D2 上午，约 2 小时）
   - 实现 `GLM4VAPIBackend`（智谱开放平台）与 `LlamaVisionAPIBackend`（若国内平台有托管；无托管则并入 4c 的短租实测）。
   - 规划层使用的 Qwen-VL 大档位 API 复用 M2 已有的 `QwenVLAPIBackend`。
   - **验证三个 API 后端均能通过 M2 的统一接口调用，无需改动 Agent 层**——这是对双抽象设计的真实检验。

6. 短租实测（D2 下午，3-4 小时）
   - 租一台 24GB GPU，一次性完成三件事：
     1. 部署 GLM-4V-9B 与 Llama 3.2 Vision 11B（4-bit），记录**显存峰值、推理延迟、冷加载耗时**
     2. 若国内 API 无 Llama 托管，在此机器上完成它的 ScreenSpot 评测
     3. **顺手验证 Qwen2.5-VL-7B 自部署可通过统一接口驱动规划层**——两小时的事，报告里就能写"全链路自部署已验证可行，本项目出于成本考虑默认使用 API"
   - 用完即关机。数据盘需求约 60-80GB，开机第一件事确认容量。

7. **实现并接入 `LocalVLMGrounding`（D3-D4，本周重点，需两个完整白天）**
   - 按 M2 D1 验证结论选定形态 1 或形态 2。
   - 实现 `locate(screenshot, target_description) -> Point`：加载 base 模型 + LoRA adapter，构造 grounding 提示词，解析模型输出坐标。
   - 处理坐标系差异：本地模型看高分辨率截图，输出需经 `CoordinateScaler` 转回真实坐标（M1 的多坐标系注册能力在此使用）。
   - 定位失败兜底：本地模型无输出或坐标越界时，回落到 M1 的 UIA + OCR 元素列表做文本匹配；仍失败则回落模式 A。
   - **配置开关**：`grounding.backend: native | local_vlm`，切换不需改代码。
   - 端到端联调：在 5 个基础任务上确认模式 B 能完整跑通。

8. 定位准确率横评（D2 起挂机批量跑，D5 汇总）
   - 在 ScreenSpot 上评测以下档位，**除档 1、2 外全部走 API，挂机批量执行，人力成本很低**：

   | 档 | 模型 | 运行方式 | 作用 |
   |---|---|---|---|
   | 1 | Qwen2.5-VL-3B 零样本 | 本地 | 微调前基线 |
   | 2 | **Qwen2.5-VL-3B + LoRA** | 本地 | 微调成果 |
   | 3 | Qwen2.5-VL-7B | API（或短租实测） | 同族大模型参照 |
   | 4 | Qwen-VL 大档位（规划层同款） | API | 商用级上限参照 |
   | 5 | GLM-4V-9B | API | 大纲点名模型对照 |
   | 6 | Llama 3.2 Vision 11B | API 或短租 | 大纲点名模型，最小验证 |

   - 判定标准：预测点落入真值 bbox 内即为正确。
   - 分 Desktop / Web 两个子集分别统计，并按元素尺寸分档分析（小目标是难点）。
   - **档 1→2 证明微调是否有效；档 2 vs 3/4 是本项目的核心结论**——3B 专用微调模型能否逼近同族 7B 乃至商用大档位的定位精度，成本与延迟差多少倍。
   - **Llama 3.2 Vision 的预期结论是"不可用"**：它未经过坐标输出训练，且中文与图内文字识别能力较弱。验证到能得出这个结论即收工，不投入调优时间。**这是一个合法且有价值的横评发现**，写进报告即可满足大纲对该模型的评估要求。
   - 引用 UI-TARS 的公开 ScreenSpot 分数列入对照表，明确标注为「引用值，非本项目实测」。

9. 模式 A/B 端到端对比与报告（D6-D7）
   - 在 5 个基础任务上跑模式 A 与模式 B 各 3 次，对比成功率、平均步数、单任务成本、单步延迟。
   - 重点记录**成本与延迟的权衡**：模式 B 的 API 侧 token 消耗应显著下降，本地推理延迟上升，两者画成图。
   - 撰写分析报告与技术选型论证文档。
   - **续写技术报告"实验与评估"章节初稿**（滚动写作）。

## 降级路径

本里程碑有明确的失败容忍设计，按顺序执行：

1. **训练集样本量不足**（M2 已预警）→ 下调训练集到 2000 条，并在报告中说明数据受限对结论的影响。
2. **LoRA 未收敛或提升不明显** → 如实报告。微调无显著提升是一个合法结论，只要训练过程可复现、超参记录完整，本项目"模型微调"能力项即算走通。
3. **模式 B 接入超时（D5 结束仍未跑通）** → 停止接入，`LocalVLMGrounding` 降级为离线评测组件，M4/M5 系统维持模式 A。M5 消融改为纯 ScreenSpot 离线对比。**此时须在报告中说明接入受阻的具体技术原因**。
4. **模式 B 跑通但成功率低于模式 A** → **不视为失败**。作为负面结论写入报告，分析原因（描述粒度不够 / 本地模型泛化不足 / 延迟拖累），系统默认配置回落模式 A，M5 照常呈现对比数据。
5. **GLM-4V-9B 或 Llama 3.2 Vision 的 API 无托管、且短租实测也受阻** → 记录具体原因（平台无该模型、依赖冲突、显存、模型许可），引用公开分数替代实测，显存数据改为按参数量与量化位宽估算并标注为估算值。二者均非主链路，**不允许为其挤占 P0 任务时间**。
6. **本机 Blackwell 工具链在 M3 开始时仍未打通** → grounding 模型改在租用 GPU 上部署，多花约 ¥50 机时。不在本机死磕。

## 验收标准

1. Qwen2.5-VL-3B 完成本地 4-bit 部署，可通过 M2 统一接口调用，显存与延迟实测数据完整。
2. LoRA 训练完整跑完，训练脚本与超参配置可一键复现，loss 曲线与训练日志齐备。
3. ScreenSpot 评测**档 1、2、4 必须完成**（这三档支撑核心结论），其余三档尽量覆盖、目标六档全覆盖；**评测脚本可一键复现**，已完成档位数据无缺失。
4. **报告** Qwen2.5-VL-3B 微调前后在 ScreenSpot-Desktop 上的准确率变化实测值（不设硬性提升门槛，见降级路径 2）。**微调前的基线必须是自己用同一套评测脚本跑出来的实测值**，不得直接引用官方模型卡数字当基线——拿官方数字当基线、自测数字当结果，是无效对比。
5. **基线复现设置已说明。** Qwen 官方模型卡报告 Qwen2.5-VL-3B 的 ScreenSpot 分数为 55.5；报告中须给出本项目复现的实测值，并在与官方值有差距时写明评测设置差异：prompt 模板、坐标归一化方式（绝对像素 / 千分比）、输入分辨率与 `max_pixels`、命中判据（点落入 bbox）、评测子集划分。**差距本身不是问题，说不清差距在哪才是。**
6. ScreenSpot 全程未参与训练、验证、提示词选型与超参调优，重叠检查记录可查。
