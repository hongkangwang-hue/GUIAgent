# 里程碑 5：系统全面评估与作品集交付

## 周期与验收要求

- 周期：2026-09-28 ~ 2026-10-11（第 7-8 周），投入强度 20-30 小时/周（不含挂机时间）。
- 验收要求：需在 2026-10-11 前完成里程碑验收。
- 验收方式：评估报告评审 + 演示视频放映 + 仓库复现检查（他人 clone 后 30 分钟内跑通）。
- 汇报材料：结项汇报 PPT（20-25 页）+ 现场演示 + 技术报告与视频提交。

## 阶段目标

对系统 v2.0 做完整定量评估，产出可信、可复现、可对外展示的实验结论，并把整个项目整理为求职作品集。

本阶段不再新增功能，重点是**把已经做出来的东西说清楚**：数据要经得起追问，图表要能独立看懂，代码要能被别人跑起来。

## 设计思路

**所有成功判定必须程序化。** 人工目测的成功率没有说服力，也无法复现。每个任务都必须配一个 `success_check`（进程检查 / 文件内容检查 / 窗口标题检查）和一个 `reset_script`（恢复初始状态），这样同一个任务跑 3 次的环境才是一致的。这一思路直接来自 M1 调研阶段读的 WebArena 的功能正确性评测方法。

**评测规模对齐官方大纲。** 大纲 W7 明确要求「设计包含 **20 个**不同难度桌面任务的测试集」，因此主评估为 20 任务 × 3 次 = 60 次，加上两组消融，总执行量约 105 次。这个规模的绝大部分是挂机时间，应排在夜间与上课时段；人力主要花在测试集设计、失败排查与数据分析上。

**两组消融，一组是官方要求，一组是本项目独有。**

| 消融 | 来源 | 说明 |
|---|---|---|
| **模式 A vs 模式 B** | 本项目核心贡献 | 通用大模型原生 grounding vs 本地微调 3B 模型 grounding。M3 已在 5 个基础任务上开了头，M5 扩展到中等难度任务并加入延迟维度 |
| **屏幕分辨率** | 官方大纲 W7 硬要求 | "分析系统在不同应用和不同分辨率下的表现差异" |

上下文窗口 k 值消融已砍（见明确不做）。

**⚠️ 模式 A/B 端到端消融不是单变量实验，写作时必须守住归因边界。** 两种模式在链路上同时改变了四件事：输出格式（`{action,x,y}` vs `{action,target_description}`）、单步模型调用次数（1 次 vs 2 次）、送规划模型的截图分辨率、以及提示词。本实验控制的是**规划模型、任务集、执行环境三者一致**，能支持的结论只到系统级：

| 可以写 | 不可以写 |
|---|---|
| "模式 B 的端到端成功率为 X%（n=45），模式 A 为 Y%" | "模式 B 成功率高 X 个百分点，说明微调 3B 的定位能力超过了通用大模型" |
| "模式 B 单步平均耗时 X 秒，其中 grounding 占 Y 秒" | 把耗时差异归因于任一单一因素 |
| "两模式的失败类型分布差异见表 N" | 用端到端数字替代定位准确率结论 |

**"定位能力孰强孰弱"只由 M3 的离线 ScreenSpot 实验回答**（同一批图、同一条指令、只换谁输出坐标，那才是单变量）。报告中这两个实验必须分节呈现，不能合并成一张"模式 B 更好"的表。

**样本量要诚实。** 20 任务 × 3 次的规模下，困难任务只有 4 个 × 3 次 = 12 次试验，单个任务的运气就能让成功率移动 8 个百分点。因此本阶段所有成功率结论都**报告点估计并标注样本量**，不做"提升 X 个百分点"式的强断言。能说清自己的数字有多硬，比数字本身更能体现工程判断力。

**与主流方案的对比要诚实。** 自建测试集与 OSWorld 不可直接比较，公开分数只能作技术水平参照。

**交付物形态围绕"求职作品集"组织。** 真正被人看的顺序是：演示视频（第一印象）→ README（30 秒决定要不要往下看）→ 代码（技术面试时被翻）→ 技术报告（导师通读）。投入应按这个顺序分配，**不追求文档字数**。

## 模块与目的

1. 基准测试集模块 `tasks/benchmark_20.yaml` + `scripts/reset/`
   目的：提供难度分层、判据程序化、环境可重置的标准评测集。

2. 评测执行模块 `eval/runner.py`
   目的：批量执行任务、自动重置环境、聚合指标，全程无人值守。

3. 数据分析模块 `eval/analysis.py`
   目的：用 Pandas 聚合轨迹日志，输出结构化指标表与 Excel 原始数据。

4. 可视化模块 `eval/plots.py`
   目的：用 Matplotlib / Seaborn 生成可直接放入报告与简历的图表。

5. 文档与作品集
   目的：把技术工作转化为可被评审、可被复现、可被面试官快速理解的材料。

## 任务拆解

### 评估线（第 7 周）

1. 设计 20 任务基准测试集（D1）
   - 难度分层：简单 8 个（2-5 步）、中等 8 个（6-12 步）、困难 4 个（13-25 步）。
   - 覆盖 5 类应用：浏览器、文件管理器、文本编辑、办公软件、系统设置；中英文界面各半。
   - 每个任务定义：`instruction` / `max_steps` / `timeout_sec` / `success_check`（类型 + 校验参数）/ `reset_script`。
   - 逐个验证重置脚本能把环境恢复到一致初始状态。**重置脚本不可靠会污染全部数据，这一天必须做扎实。**

2. 主评估执行（D2-D3，以挂机为主）
   - 每任务运行 3 次，共 60 次执行，全程无人值守，使用 M3 确定的最优配置。
   - **大纲 W7 要求的三项（必做）**：任务成功率 SR、平均执行时间（拆分 API / grounding / 执行 / 截图）、各类错误率。
   - **本项目自加（可选，时间不够先砍）**：步骤效率 SPL（人类最短步数 / 实际步数）、平均步数、重试恢复率、首次成功率、单任务成本。

     大纲原文是「从任务成功率、平均执行时间、错误率**等**维度」，「等」字容得下补充指标，
     但它们不是硬性要求。**其中平均步数与 SPL 最值得留**——M2 实测显示
     「成功率满分而步数是理论下限 5 倍」的任务真实存在（`发送消息` 4/4、21.8 步、
     理论下限约 4 步），**只报成功率会把这件事整个盖住**。
     单任务成本需要 `.env` 里的计费单价，见 M2 交付物 11 的说明。
   - 所有数据从轨迹日志自动聚合，**禁止人工统计**。
   - 人力主要花在盯崩溃与排查异常轨迹上，不需要全程值守。

3. 两组消融实验（D4，以挂机为主）
   - **模式 A vs 模式 B 消融**：中等难度 8 个任务 × 2 模式 × 3 次。模式 B 的数据可复用主评估结果，实际新增约 24 次执行。对比维度：成功率、单任务成本、单步延迟、定位失败率。**这是本项目最有工程价值的一组数据。**
   - **屏幕分辨率消融**：1920×1080 / 1600×900 / 1366×768 三档 × 4 个任务 × 2 次，约 24 次执行。**主实验基线固定 1920×1080 / 100% 缩放，只有这组消融允许改分辨率。**消融数据**单独成表，不与主实验的 60 次合并统计**——合并平均等于把「系统有多强」和「系统有多稳」搅成一个数。每次改完分辨率须重启 Agent 进程，`CoordinateScaler` 在进程启动时按当前屏幕建立映射。
   - 附加（不额外跑）：按 5 类应用分组统计主评估成功率，分析哪类界面最难。
   - 若 M3 的模式 B 未跑通，第一组消融改为呈现 M3 的 ScreenSpot 离线对比数据，并说明系统级对比未能完成的原因。

4. 与主流方案对比（D5）
   - 维度：技术路线、是否需训练、硬件门槛、自建 20 任务成功率、公开基准分数、单任务成本、跨平台支持。
   - 对比对象：本项目 v2.0（模式 A / 模式 B 两行）、UI-TARS-2、Claude Computer Use。
   - **本项目未使用闭源模型，因此与 UI-TARS / Claude Computer Use 的对比是三条不同技术路线之间的对比**，而非自我对比——这是开放权重路线带来的一个论证优势，要在报告中点明。
   - **明确标注可比性边界**：自建测试集与 OSWorld 不可直接比较；UI-TARS 与 Claude Computer Use 的分数为引用值而非本项目实测。
   - 说明三条路线的取舍：端到端原生训练（UI-TARS，能力最强、门槛最高）、闭源前沿模型驱动（Claude CU，开箱即用、不可自托管）、开放权重模型 + 专用微调（本项目，可自托管、能力上限受限）。
   - **"可私有部署"须附许可证限定**：本项目的权重可下载、可本地部署、可微调，但并非全部可商用（Qwen2.5-VL-3B 为 Qwen-Research，仅限研究）。报告写"可私有部署（研究用途；商用须逐项核对许可证）"，不写无条件可商用。引用 M2 建立的《模型与数据集许可证对照表》。

5. 数据统计与可视化（D6-D7）
   - Pandas 聚合全部执行轨迹，openpyxl 导出 Excel 原始数据表。
   - 出图不少于 6 张：三难度成功率柱状图（含样本量标注）、**模式 A vs B 成功率—成本对比图**、错误类型分布堆叠柱状图、延迟分解堆叠图、分辨率—成功率曲线、v1.0 vs v2.0 对比雷达图。
   - 图表要求：含标题、轴标签、图例、关键数据标注、**样本量 n 标注**。
   - 撰写《系统全面评估报告》。

### 交付线（第 8 周）

6. 整合技术报告（D1-D3）
   - 章节：摘要 / 1 引言 / 2 相关工作 / 3 系统设计 / 4 关键技术实现 / 5 实验与评估 / 6 讨论 / 7 结论与展望 / 参考文献（不少于 15 篇）。
   - **M1-M4 已滚动写出各章节初稿，本阶段的工作是补入 M5 数据、统稿、统一术语与图表编号**，不是从零撰写。
   - 创新点提炼四条：
     1. **双模式 grounding 架构**——通用大模型做语义规划 + 本地微调 3B 模型做像素定位，同族模型控制变量，含完整消融对照

7. 制作演示视频（D4-D5）

   - 剪映处理：中文字幕（自动识别 + 手动校对）、关键操作放大镜与箭头标注、等待片段 4× 加速并标注、背景音乐控制在 -25dB 以下。
   - **错误恢复片段是最出彩的部分**，务必完整保留一次真实的失败—检测—恢复过程。

   - 安全检查：仓库内无任何 API Key，日志与截图样本已脱敏。
   - 发布 GitHub Release v1.0，附 LoRA 权重与评测数据。

9. 求职材料整合与缓冲（D7）

## 验收标准

1. 20 个任务 × 3 次 = 60 次主评估全部完成，数据无缺失，全程程序化判定。
2. 两组消融实验完成，均得出明确结论并有数据支撑，权衡曲线可读。
3. **报告**三个难度档的成功率实测值，每个数字附样本量标注；不设硬性成功率门槛。
4. 所有图表可独立看懂：含标题、轴标签、图例、关键数据标注、样本量 n。
5. 技术报告结构完整，所有数据可追溯到原始日志，参考文献不少于 15 篇。
6. 演示视频能在无讲解情况下让非专业观众理解系统能力。
7. 他人 clone 仓库后按 README 能在 30 分钟内跑通一个基础任务。
8. 简历描述中每一个数字都能在报告中找到出处。
9. 仓库通过安全检查：无密钥泄露，样本已脱敏；报告中说明"云端 API 会接收截图"这一数据边界，不把虚拟机隔离宣称为隐私保障。

   **关于个人数据（2026-08-24 修订）。** 原文写的是「不含真实个人账号与个人数据」，
   与现状不符：客机登录了开发者本人的微软账号，OneDrive 正在同步个人文件。
   M2 实测期间 Agent 曾对着该账号的登录框连按 12 次回车，并修改保存了含
   API key 的 `.env`。

   这不只是违反本项目自加的 M0 约束——**大纲「合规与落地说明」第 5 条原文就是
   「项目中涉及的所有操作均在本地计算机上进行，不包含任何个人数据或敏感信息」**。

   两条路，**必须二选一，不能含糊**：

   - **(a) 清理客机**：改用本地账户 → 修改显示名（开始菜单会显示真实姓名，
     而多个测试任务经过开始菜单）→ 卸载 OneDrive → 删除已同步文件 → 重拍快照。
     之后本条验收标准按原文成立。
   - **(b) 不清理**：本条验收标准改为如实表述，且技术报告**不得引用大纲第 5 条
     声称合规**。准确写法：

     > 评测在隔离虚拟机内进行，客机使用开发者本人的 Windows 账号；
     > 规划层调用云端 API，客机截图会传输至模型服务方。
     > 未对客机内的个人数据做剥离。

   选 (b) 时，M2 报告 §7.5 记录的两起事件（Agent 修改保存 `.env`、
   对身份验证界面连续输入）应一并写入报告的安全章节——**有证据的风险记录
   比一句合规声明有价值**。
10. 与官方大纲的全部偏差（模型版本、平台支持、交互界面、评估规模、数据集处理深度）在技术报告中有显式说明与理由。

## 明确不做

1. 不新增任何系统功能，本阶段只做评估与整理。
2. 不做性能调优（除非评估中发现明显 bug）。
3. 不扩充测试集规模到 20 个以上。
4. **不做 OSWorld 子集评测。** 8 周周期内不现实，引用其公开分数作参照即可。
5. **不做上下文窗口 k 值消融。** 两组消融已覆盖官方要求与本项目核心贡献，k=3 的选择在报告中以 M4 的延迟与成本数据佐证即可。
6. 不做 Dockerfile。复现路径为 conda 环境说明 + `env_check.py` 自检脚本。
7. 不做 A4 项目 Poster。
8. 不做用户研究、可用性测试等人因实验。
9. 不做论文投稿准备（技术报告以工程报告形式呈现）。
10. 不做生产级部署、监控告警、CI/CD 流水线。
11. 不做商业化可行性分析。
