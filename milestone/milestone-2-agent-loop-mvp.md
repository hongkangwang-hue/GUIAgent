# 里程碑 2：端到端任务闭环打通（系统 v1.0）

## 周期与验收要求

- 周期：2026-08-31 ~ 2026-09-13（第 3-4 周），投入强度 20-30 小时/周。
- 验收要求：需在 2026-09-13 前完成里程碑验收。
- 验收方式：功能演示（现场跑通 5 个基础任务）+ 代码走读 + 轨迹日志复盘 + 本地启动检查。
- 汇报材料：里程碑汇报 PPT（10-12 页）+ 现场实机演示 + 任务执行 GIF。

## 阶段目标

完成最小可用智能体，打通"用户指令 → 屏幕感知 → 任务规划 → 动作执行 → 结果反馈"的完整主链路，产出**系统 v1.0（模式 A）**。

本阶段不追求复杂任务与错误恢复能力，重点是确认 agent loop 可以稳定驱动 M1 的感知控制模块，并形成后续接入本地 grounding、多模型横评与评测体系的代码结构。

## 设计思路

本阶段以模式 A（规划模型原生 grounding 直接出坐标）跑通闭环，但**接口层必须按双模式与多后端设计**，否则 M3 的横评与模式 B 无法开展。

建议设计：

1. **两层后端抽象，缺一不可：**
   - `LLMBackend`：负责"看截图 + 历史 → 决定下一步动作"。M2 的唯一实现是 `QwenVLAPIBackend`（阿里云百炼），M3 补齐 GLM-4V、Llama 3.2 Vision 的实现。
   - `GroundingBackend`：负责"元素描述 → 像素坐标"。M2 的唯一实现是 `NativeGrounding`（直接透传规划模型给出的坐标）。M3 新增 `LocalVLMGrounding`。
   - 这两层的切换必须是配置项，Agent 层代码对切换无感知。
2. Agent Loop 独立成 `core/loop.py`：只负责"发请求 → 拿动作意图 → 交给 grounding 定位 → 交给执行器 → 回传截图"。
3. 模型坐标一律经 `CoordinateScaler` 转换后再执行，这是 M1 已经建好的唯一出入口。
4. **工具定义直接复用 M1 为每个动作写好的 JSON Schema**，不做二次映射。
5. 会话与轨迹落盘为 JSONL + 截图帧目录，先不上数据库。
6. 交互入口为 CLI（typer + rich），不做 Web 页面。

M2 的关键不是任务成功率有多高，而是**系统分层清楚、每一步都有据可查**。每一步动作的截图、思考、坐标、耗时、token、成本全部落盘。轨迹日志是 M3、M4、M5 全部分析的唯一数据源。

### LangChain 的使用边界

框架确定采用 **LangChain**（官方大纲为"LangChain / LlamaIndex"，二选一即可）。但**边界必须划死**——只用它成熟且真正省事的部分，Agent Loop 自己写。

| 用 | 不用 |
|---|---|
| `ChatPromptTemplate` — 提示词模板与 few-shot 组织，YAML 外置 | `AgentExecutor` / LangGraph — 循环自己写，理由见下 |
| `PydanticOutputParser` — 强制结构化动作输出 | Retrieval / VectorStore — 知识库已砍 |
| `CallbackHandler` — token、耗时、请求 ID 自动落盘 | Memory 抽象 — 上下文窗口自己管，要精确控制 k 与旧帧降采样 |
| `ChatOpenAI` + 自定义 `base_url` — 多模态消息构造 | `ChatTongyi` / `ChatZhipuAI` 等社区封装 — 多模态支持成熟度不确定 |

**为什么 Agent Loop 不用 LangChain 的 Agent 抽象**——这一取舍须写入技术报告，否则"基于 LangChain 搭建 Agent 框架"这句会被追问：

1. **交互形态不匹配。** `AgentExecutor` 的循环是"文本进 → 工具调用 → 文本结果回传"；GUI Agent 是"截图进 → 动作出 → 执行后重新截图回传"，每轮反馈是图像而非文本，套进去要与抽象打架。
2. **轨迹日志需要循环内部的完全控制。** 每步要记录前后截图、模型坐标与真实坐标两套、延迟四段拆分、grounding 来源——这些字段散落在循环的不同位置，`AgentExecutor` 的回调接口够不着。而轨迹日志是 M3/M4/M5 全部分析的唯一数据源。
3. **模式 A/B 切换发生在单步内部**，在"拿到动作意图"与"执行动作"之间，不是工具层面的切换。

自写循环约 150 行，换来完全控制，这个交换是划算的。

**多模态消息走 OpenAI 兼容接口。** `langchain-community` 中各家国产模型的封装对图像内容块的支持成熟度不一（构造方式、base64 还是 URL、多图顺序各有差异），而截图传递是主链路、每步都要走，不能赌。多数国产平台提供 OpenAI 兼容端点，用 `ChatOpenAI(base_url=...)` 接入走的是 LangChain 里被验证最充分的那条代码路径。**此方案须在 M1 D1 的选型验证中一并测通**。

### 两条针对开源模型的必要设计

**开源模型的规划能力弱于闭源前沿模型，以下两条不是优化项，是能不能跑起来的前提。**

**1. 子任务粒度必须切到原子动作级。** 不要给模型"完成整个任务"这种大目标——它扛不住。Planner 把任务拆成一串小到只需一两步就能完成的子目标，Executor 一次只带**一个**子目标进 Agent Loop，完成后由主循环推进到下一个。这一条原计划在 M4，现在必须在 M2 就做。

**2. 提示词内置 few-shot 示例。** 在提示词模板里直接放 2-3 组"截图描述 → 正确动作输出"的示例，帮助模型稳定输出格式与合理动作。M3 的提示词消融中，few-shot 这一档预计会显示出比使用前沿模型时大得多的效果——这本身就是一个有价值的结论。

## 模块与目的

1. 数据集处理模块 `data/`
   目的：把公开 GUI 数据集统一为同一 schema，为 M3 的 grounding 训练集与评测集做准备。

2. LLM 后端抽象层 `llm/`
   目的：隔离不同多模态模型的调用差异，让 M3 只需新增实现类即可完成横评。

3. **Grounding 后端抽象层 `grounding/`**
   目的：把"元素描述 → 坐标"这一步从模型调用中解耦，使模式 A / 模式 B 可配置切换，这是 M3 与 M5 消融的结构前提。

4. Agent 编排模块 `agent/`
   目的：承接用户指令，完成细粒度任务拆解与提示词组织，管理历史上下文窗口。

5. Agent Loop 核心 `core/loop.py`
   目的：实现请求-定位-执行-回传循环，是整个系统的心脏。

6. 轨迹日志模块 `core/trajectory.py`
   目的：结构化记录每一步执行，支撑回放、调试、成本核算与后续全部评测分析。

7. CLI 交互模块 `cli/`
   目的：提供统一的任务发起、配置查看、轨迹回放与**失败打标**入口。

## 任务拆解

1. 公开数据集处理（第 3 周 D1-D2）
   - **深度处理**：ScreenSpot / ScreenSpot-v2（M3 定位评测集）、ScreenAgent Dataset（M3 grounding 训练样本来源）。
   - **仅抽样查看**：Mind2Web、WebArena。在报告中说明这两者是**网页**数据，与桌面目标不对齐，仅作方法论与提示词参考，不深度处理。
   - 用 Datasets + Pandas 统一 schema：`sample_id / screenshot_path / resolution / instruction / action_type / bbox / point / platform / app`。
   - 清洗：剔除 bbox 越界、面积小于 100px²、无文本且无类型的样本。
   - 统计分析：分辨率分布、动作类型分布、平台分布、元素尺寸分布，输出 4 张图表。
   - **M3 前置确认（必做）** —— ✅ **已于 2026-08-23 完成，结论是样本量不足**：
     ScreenAgent train 的 2000 个标注步展开成 3073 个动作，其中只有 **716 个带坐标**（其余是规划 / 子任务评估 / 键盘动作）。按会话切分后训练集 **569** 条，缺口约 2400 条。更糟的是这 716 条**配得上的指令只有整体任务目标，且只有 169 条不重复**，作为 grounding 监督信号比条数看起来弱得多。
     泄漏检查同步完成：ScreenAgent 与 ScreenSpot / ScreenSpot-v2 的截图重叠均为 **0**；但 **ScreenSpot 与 ScreenSpot-v2 之间重叠 586 张（占 v1 的 96.1%）**，两者不能当作两个独立评测集报告平均分。
     全部数据与补救方案见 `docs/m3-prereq/README.md`。**补充来源的决定须在本周内定案。**
   - **建立《模型与数据集许可证对照表》**：逐项记录每个模型权重与数据集的许可证名称、是否允许商用、是否允许再分发、是否要求署名。**不用"全部开源、禁止商用"这类笼统口径**——各来源许可并不一致（ScreenAgent 数据集为 Apache-2.0，本身不禁止商用；Qwen2.5-VL-3B 权重为仅限研究的 Qwen-Research；Llama 3.2 走 Llama Community License）。M5 报告中"可私有部署"的表述引用此表，不做无条件断言。

2. 双层后端抽象（第 3 周 D3）
   - 定义 `LLMBackend`：`predict_action(instruction, screenshot, history) -> ActionIntent`，`get_cost() -> CostInfo`。
   - 定义 `GroundingBackend`：`locate(screenshot, target_description) -> Point | None`。
   - 实现 `QwenVLAPIBackend`：经 LangChain 调用阿里云百炼的 Qwen-VL 系列，**多模态消息用 M1 D1 已验证的方式构造**（优先 `ChatOpenAI` + 兼容 `base_url`），工具定义直接复用 M1 的动作 JSON Schema。
   - 实现 `NativeGrounding`：透传模型输出坐标，`locate()` 为空实现，仅用于满足接口。
   - **接口设计要点**：多数国产大模型平台提供 OpenAI 兼容接口，`LLMBackend` 的实现应尽量走通用协议，让 M3 新增 GLM-4V / Llama 后端时只需改配置与少量适配代码。
   - 若平台支持上下文缓存，接入并记录命中带来的计费差异；不支持则记录为已知限制。
   - 从响应中读取 token 用量，实时累加成本。
   - 异常处理：网络超时、限流、余额不足、输出不可解析，均返回可理解错误。

3. Agent 编排层（第 3 周 D4-D5）
   - 用 LangChain `ChatPromptTemplate` 建立提示词模板库，YAML 外置（`prompts/planner_v1.yaml` 等），为 M3 消融做准备。
   - **模板中内置 2-3 组 few-shot 示例**（截图描述 → 正确动作输出）。
   - 实现 Planner：接收自然语言指令，输出**细粒度线性子任务列表**（每个子任务只需 1-2 步动作），用 `PydanticOutputParser` 强制格式。
   - 实现 Executor：一次只携带**一个**子任务目标进入 Agent Loop。
   - 实现上下文管理：历史截图窗口 `k` 可配置（默认 3），旧帧降采样。
   - 配置 `CallbackHandler` 自动记录每次调用的 token、耗时、请求 ID。

4. Agent Loop 实现（第 3 周 D6-D7）
   - 实现循环骨架：发送消息 → 解析动作意图 → 经 `GroundingBackend` 得到坐标 → `CoordinateScaler` 转换 → 执行 → 重新截图 → 回传。
   - 截图回传按平台要求编码（base64 或 URL）。
   - 每个动作后等待 0.5-1.5 秒再截图，避免拿到界面中间态。
   - 设置 `max_iterations`（默认 25，**调试期降到 8**）防止无限循环；设置单任务成本上限熔断。
   - **输出解析要容错**：开源模型的结构化输出稳定性低于前沿模型，解析失败时应重试一次并记录，而非直接崩溃。

5. **模式 B 可行性验证（第 4 周 D1，关键前置）**
   - 调整工具定义，让规划模型输出 `{action, target_description}`（元素描述）而非坐标，测试它能否稳定给出足够具体的描述。
   - 至少在 3 个界面场景下各测 10 次，统计描述的可解析率与描述质量（是否具体到能定位）。
   - **产出结论**：模式 B 可行 / 需降级为"模型出坐标 + 本地模型复核纠偏"形态。此结论直接决定 M3 的实现方案。

6. 轨迹日志系统（第 4 周 D2-D3）
   - 定义 JSONL 记录格式：`trajectory_id / step / subtask_id / timestamp / screenshot_before / screenshot_after / model_thinking / action_intent / grounding_source / action(模型坐标+真实坐标) / execution_status / latency_ms(api/grounding/execute/screenshot) / tokens / cost_cny / error`。
   - 截图帧按轨迹 ID 分目录存储。
   - 实现 `replay` 命令：逐帧回放历史轨迹，用于调试与 M4 演示视频素材。
   - **实现 `label` 命令**：在回放过程中为失败步骤打错误类型标签，标注结果写回轨迹文件。**M2 与 M3 跑出的每一条失败轨迹都要当场打标**，不允许攒到 M4 集中人工复盘。

7. CLI 与集成（第 4 周 D4）
   - 命令：`run`（执行任务）、`run --task-file`（批量）、`replay`（回放）、`label`（打标）、`config --show`。
   - Rich 实时面板：任务进度条、当前子任务、动作日志表格、token/成本计数器。
   - 打通完整链路：指令 → Planner 拆解 → 逐子任务进入 Agent Loop → 落盘 → 返回结果。

8. 基础任务测试与调试（第 4 周 D5-D7）
   - 定义 5 个基础任务：打开浏览器 / 搜索指定内容 / 打开指定文件 / 发送消息（本地模拟程序）/ 关闭应用。
   - **成功判定必须程序化**：进程检查、窗口标题检查、文件内容检查，不用人工目测。
   - 每个任务运行 5 次，记录成功率、平均步数、平均耗时。
   - 失败轨迹用 `label` 命令当场打标。
   - 录制至少 1 个任务的完整执行 GIF。
   - **续写技术报告"关键技术实现"章节初稿**（滚动写作）。

## 验收标准

1. 本地能通过一条命令启动并执行任务，导师可按 README 复现。
2. **报告** 5 个基础任务的成功率实测值。其中"打开浏览器"与"关闭应用"两个单步任务应接近 100%；多步任务不设硬性门槛——开源规划模型在多步任务上的能力边界正是本项目要测量的对象之一。
3. 单步平均延迟已记录，并按 API / grounding / 执行 / 截图 四段分解。
4. Planner 输出的子任务粒度可验证：每个子任务在 1-2 步内可完成。
5. 同一任务的多个子任务可连续执行，上下文正确传递。
6. 轨迹日志字段完整，任意一条轨迹可通过 `replay` 完整回放，失败步骤已通过 `label` 打标。
7. 模型输出坐标与实际点击坐标的映射关系在日志中可追溯，无坐标错位。
8. **`LLMBackend` 与 `GroundingBackend` 双抽象经代码走读确认可扩展**：新增一个模型后端或 grounding 实现不需要改动 Agent 层与 Loop 层。
9. 模式 B 可行性验证完成并给出明确结论。
10. 系统在虚拟机中连续运行 30 分钟无崩溃。
11. ScreenSpot 与 ScreenAgent 完成下载与 schema 统一，统计报告与图表齐备，M3 训练样本量与泄漏风险已确认。

13. **M3 四项前置件全部完成并归档到 `docs/m3-prereq/`**：三分冻结（含种子）、LoRA 100-step smoke test 跑通、3B 4-bit 真实分辨率截图的峰值显存实测值与选定 `max_pixels`、`target_description` 结构化输出的字段缺失率统计。

## 明确不做

1. 只接入一个规划模型后端，GLM-4V 与 Llama 3.2 Vision 留到 M3。
2. 不实现 `LocalVLMGrounding`，M2 只需保证接口位置留好。
3. **不做正式的模型部署与微调**——任务 9 的 smoke test 与单图推理只验流程与显存，不训练可用模型、不产出任何评测结果、不调超参。正式训练与部署在 M3。
4. 不做错误检测、自动重试与失败重规划，失败即终止并记录。
5. 不做 Reflector 反思模块，子任务完成判定用简单规则。
6. 不做复杂任务（超过 8 步 / 跨应用）支持。
7. **不做 LlamaIndex 软件操作知识库。** 官方大纲为"LangChain / LlamaIndex"，框架确定采用 LangChain；对开源规划模型而言，提示词内的 few-shot 示例比外部检索更直接有效。
8. **不用 LangChain 的 `AgentExecutor` / LangGraph / Memory / Retrieval 抽象**，Agent Loop 与上下文管理自己写，理由见「LangChain 的使用边界」。
9. 不做感知性能优化与深度成本优化，留到 M4。
10. 不做 Web 前端界面，交互仅限 CLI。
11. 不做数据库存储，会话与轨迹落盘为 JSONL 文件。
12. 不做并发执行与任务队列。
