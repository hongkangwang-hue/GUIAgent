## 阶段目标

完成最小可用感知-控制骨架，打通"截图 → 元素识别 → 坐标映射 → 键鼠执行"的本地主链路。

本阶段自研代码不接入大模型，重点是确认桌面感知与控制在目标平台上稳定可用，并把**坐标系统**这一后续所有模块共同依赖的地基做扎实。

## 设计思路

本阶段采用固定分辨率目标（1024×768 模型坐标系）启动系统，先避免过早抽象多分辨率适配策略。感知侧封装 `ScreenCapturer` 与 `ElementDetector`，控制侧封装 `ActionExecutor`，两者之间由 `CoordinateScaler` 做唯一的坐标转换出入口。

建议设计：

1. 截图统一走 mss，PyAutoGUI 仅作 fallback，接口层屏蔽差异。
2. 真实屏幕坐标与模型坐标之间的转换**只允许通过 `CoordinateScaler` 一个类**，任何模块不得自行换算。
3. 元素识别采用**双通道**并行 + 融合去重：无障碍树（UIA）→ OCR（PaddleOCR）。CV 轮廓检测通道不在本阶段实现，留待 M4 确有需要时再补。
4. **动作空间自行定义**，覆盖 GUI 操作所需的完整动作集，并保证可被 JSON Schema 描述——M2 会把它转成大模型的工具定义，因此参数命名要清晰、无歧义。
5. 所有动作执行前经过安全白名单校验，坐标越界直接拒绝。
6. 每次识别结果输出一张带编号边界框的调试图，人工可核验。

M1 的关键不是识别准确率有多高，而是**坐标不会错、动作不会失控、结果可以肉眼核验**。

> **元素识别在本项目中的定位需要说清楚**：由于 M3 将引入本地 grounding 模型直接输出坐标（模式 B），UIA + OCR 的识别结果**不是主链路的定位来源**，而是服务于三件事——M4 Reflector 的程序化判据（控件存在性校验）、grounding 结果的兜底与纠偏、以及全程的调试可视化。因此本阶段不为识别准确率设置硬性门槛。

## 模块与目的

1. 截图模块 `perception/capture.py`
   目的：提供跨平台、低延迟、支持多显示器与区域截取的统一截图入口。

2. 坐标系统模块 `perception/coordinate.py`
   目的：隔离真实屏幕坐标与模型坐标的转换细节，处理 DPI 缩放与多显示器偏移。

3. 元素识别模块 `perception/element_detector.py`
   目的：将屏幕像素转换为结构化 UI 元素列表，为 Reflector 程序化判据与 grounding 纠偏提供基础。

4. 动作执行模块 `control/executor.py`
   目的：把结构化动作指令翻译为实际键鼠事件，并承担安全拦截职责。

5. 调试可视化模块 `perception/visualizer.py`
   目的：把识别结果画回截图，让感知效果在没有大模型的情况下可被人工评估。

## 任务拆解

1. 截图与坐标系统（D1-D2）
   - 实现 `ScreenCapturer`：全屏 / 区域 / 指定显示器截图，mss 主引擎 + PyAutoGUI fallback。
   - 实现 `CoordinateScaler`：真实坐标 ↔ 模型坐标双向映射，提供 `to_model()` 与 `to_real()`。
   - **预留多目标分辨率支持**：模式 B 下送规划模型的截图与送本地 grounding 模型的截图分辨率不同，`CoordinateScaler` 需支持按命名坐标系注册与转换，而非硬编码单一目标。
   - 处理 Windows DPI：调用 `SetProcessDpiAwareness(2)`，验证 100%/125%/150% 三档缩放下坐标正确。
   - 基准测试：单帧截图延迟目标低于 15ms。

2. 元素识别（D3-D4）
   - 实现 `OCREngine` 抽象基类与 `PaddleOCREngine`、`EasyOCREngine` 两个实现。
   - 实现 OpenCV 预处理链：灰度化 → CLAHE 增强 → 2× 超分 → 自适应二值化。
   - 实现 `uia_tree.py`：Windows UIA 抓取控件 Name / ControlType / BoundingRectangle。
   - 实现双通道融合：UIA 优先 → OCR 补充，IoU 去重，统一输出 `UIElement` 数据类。

3. 动作执行（D5）
   - 实现核心动作：`screenshot`/`left_click`/`right_click`/`double_click`/`left_click_drag`/`mouse_move`/`scroll`/`key`/`type`/`wait`。
   - 低频动作（`middle_click`/`triple_click`/`hold_key`）实现接口桩，M4 按需补齐。
   - **为每个动作定义 JSON Schema**，M2 直接转成大模型的工具定义，避免二次映射。
   - 中文输入走剪贴板方案（pyperclip + Ctrl+V），PyAutoGUI 的 `typewrite()` 无法输入中文。
   - 人类化鼠标移动：`duration=0.3` + 缓动函数，避免瞬移导致 hover 不触发。
   - 安全白名单：拦截关机、格式化、系统目录删除等高危操作；坐标越界拒绝；开启 PyAutoGUI 的 `FAILSAFE`。
   - **用 pynput 实现全局热键急停**（如 `Ctrl+Alt+Q`）：PyAutoGUI 的 `FAILSAFE` 要求把鼠标甩到屏幕角落才触发，而此时鼠标正被 Agent 控制，人和程序会抢夺光标。全局键盘监听不依赖鼠标，是更可靠的第二道刹车。两者同时保留，互为兜底。

4. 可视化与测试（D6-D7）
   - 实现 `visualizer.py`：按来源着色绘制边界框与编号（UIA 绿 / OCR 蓝），中文标签用 PIL 绘制。
   - 采集 20 张真实截图测试集（浏览器、文件管理器、记事本、办公软件、系统设置各 4 张）。
   - 编写 25+ 个 pytest 用例：坐标往返一致性、多坐标系注册转换、DPI 检测、OCR 接口、动作参数校验、白名单拦截。
   - 运行 OCR 双引擎对照实验，记录中文准确率、英文准确率、平均耗时。
   - **起草技术报告的"相关工作"与"系统设计"章节初稿**（滚动写作，M5 不从零开始）。

## 验收标准

1. 截图延迟低于 15ms，真实分辨率与模型坐标系之间坐标往返误差不超过 2px。
2. `CoordinateScaler` 支持至少两个命名目标坐标系的注册与互转，经单元测试验证。
3. 在 100%/125%/150% 三档 DPI 缩放下，点击目标位置均正确。
4. 在 20 张测试截图上**报告**双通道融合后的 UI 元素召回率实测值，按来源分项统计（不设硬性门槛，见设计思路说明）。
5. 全部已实现的键鼠动作在虚拟机内验证通过，中文输入正常；每个动作有对应的 JSON Schema。
6. **在隔离虚拟机内，感知与控制的完整通路成立**——客机内能截图、识别、换算坐标并执行键鼠动作，`scripts/verify_control.py` 全项通过。这条打通了才算通路成立，是 M2 让 Agent 接管键鼠的前提。

   > **原文为「宿主机程序能对虚拟机执行截图与鼠标点击」，已修正为客机内执行。** 理由见 M0 环境表下的说明：宿主机侧执行与 M0 全局约束 1「宿主机不受控制」矛盾，且会使 UIA 通道与 M2 的程序化成功判定双双失效。本条的**意图**（通路成立、Agent 能接管键鼠）在客机内执行下同样满足，且隔离更彻底。
7. **两道急停均验证有效**：PyAutoGUI `FAILSAFE`（鼠标甩角）与 pynput 全局热键，后者在 Agent 正控制鼠标时仍能立即中断。
8. pytest 覆盖率不低于 60%，坐标与白名单模块接近全覆盖，GitHub Actions CI 通过。

## 明确不做

1. **自研代码不接入大模型。** 第 1 周的选型验证是在 API 控制台或简单脚本中手动进行，不构成系统功能。
2. 不做任务规划与动作决策，动作由测试脚本手工指定。
3. 不做 CV 轮廓检测通道，双通道（UIA + OCR）已足够支撑 Reflector 判据与调试可视化。
4. 不做 Set-of-Mark 编号标注。模式 B 下本地 grounding 模型直接输出坐标，编号方案不再需要。
5. 不做多分辨率自适应策略，固定以 1024×768 为主模型坐标系（但接口支持多坐标系注册）。
6. 不做元素语义分类（按钮 / 输入框 / 链接的精细判别），只区分来源与粗类型。
7. 不做 macOS / Linux 的完整适配，接口预留但只保证 Windows 通路可用。
8. 不做感知模块性能优化（缓存、帧差跳过），留到 M4。
9. 不做任何模型部署与微调工作，留到 M3。
