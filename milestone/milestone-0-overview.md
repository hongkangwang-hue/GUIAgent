# 项目里程碑总览：基于多模态大模型的桌面 GUI 智能体

> **本文档是项目计划的总览，可独立阅读。** 内容涵盖技术路线、技术栈落实对照、八周里程碑安排、全局约束（含隔离与数据边界、测试集纪律、许可证口径）、风险与降级路径，以及与官方大纲的偏差说明。
>
> 每个里程碑的详细任务拆解、交付物清单与验收标准另见 `milestone-1` 至 `milestone-5` 五份文档，本文不重复。文末列出三项需要导师确认的事项。



## 技术路线

以**开放权重多模态大模型**为核心，构建"感知 → 规划 → 定位 → 执行 → 反思"闭环。全部模型均为官方大纲点名的开放权重模型（Qwen-VL / GLM-4V / Llama 3.2 Vision），不使用闭源商业模型。

**用"开放权重"而非"开源"是准确性要求**：这三个模型系列权重公开可下载、可本地部署、可微调，但许可证并非统一的 OSI 开源协议——Llama 3.2 走 Llama Community License，Qwen2.5-VL 各尺寸许可不一致（7B/32B 为 Apache-2.0，**3B 为 Qwen-Research，仅限研究用途**），GLM-4V 另有自己的模型许可。本项目为学习与研究用途，均在许可范围内；但**报告中"可私有部署"的表述必须附上"须逐项核对许可证"的限定**，不能写成无条件可商用。各模型与数据集的许可证在 M2 数据调研阶段逐项记录归档。

### 三层模型分工

| 层 | 承担模型 | 部署方式 | 职责 |
|---|---|---|---|
| **规划层** | Qwen-VL 系列（阿里云百炼 API） | API 调用 | 看截图，输出下一步动作意图 |
| **Grounding 层** | **Qwen2.5-VL-3B + LoRA（自微调）** | **本地部署**，4-bit 权重约 2-3GB（估算，待实测） | 把元素描述转为像素坐标 |
| **横评对照** | Qwen2.5-VL-7B、GLM-4V-9B、Llama 3.2 Vision 11B | API 为主 + 一次短租实测 | ScreenSpot 定位能力对照 |

**部署方式的判断标准：自部署只在"这个模型别人跑不了"时才有价值。** 7B/9B/11B 都是公开权重且不做微调，自己部署一遍除了拿到显存数字不产生任何独有产出；**只有微调后的 3B 是本项目独有的**——LoRA adapter 无法上传到公共 API 平台，必须自部署。因此本项目只自部署一个模型，其余走 API。

这一分工满足官方大纲 W3 的两项要求：**开放权重多模态模型的本地部署**（微调后的 grounding 模型）与 **API 调用**（规划层与横评对照）。

**"约 2-3GB"只是权重估算，不是峰值显存。** Qwen2.5-VL 采用动态分辨率，一张 2560×1600 的桌面截图会产生 2000+ 视觉 token，视觉塔与注意力的激活显存有可能超过权重本身。**8GB 卡够不够用，必须以实测峰值为准**——该实测提前到 M2 后半段完成（见《M3 前置件提前到 M2 后半段》）。

### 硬件与部署环境

| 环境 | 配置 | 承担任务 |
|---|---|---|
| 本机（ROG 幻16 Air） | 32GB LPDDR5X + RTX 5060 Laptop 8GB GDDR7 + 1TB SSD | 全部开发调试、隔离虚拟机、grounding 模型推理 |
| Colab / 短租 GPU | 24GB 级别，约 10 机时 | LoRA 训练（一次性 5-8h）+ 横评模型部署实测（3-4h） |

**⚠️ RTX 5060 是 Blackwell 架构（sm_120）。** `cu121` 及更早的 PyTorch 构建不含 sm_120 kernel，必须用 **PyTorch 2.7+ 配 cu128 或更高**；bitsandbytes 也需要支持 Blackwell 的版本。**但 M1/M2 阶段几乎不依赖 GPU**（PaddleOCR 可跑 CPU，规划层走 API），因此这条不阻塞前四周进度，M3 前解决即可。

**内存分配**：虚拟机客机 12GB，其余留给宿主机与模型加载。**GPU 无需给虚拟机直通**。

**执行位置：Agent 整体运行在客机内**（感知、规划调用、坐标换算、键鼠执行全在客机）。本地 grounding 模型仍跑在宿主机 / 服务器上，客机经 HTTP 调用其 OpenAI 兼容端点——权重在本地硬件上运行，这仍是「本地部署」，只是换了传输方式。

> **此处原写的是「宿主机截 VM 的屏、算坐标、往 VM 发键鼠事件」，已修正。** 那个实现与本文档全局约束 1「宿主机不受控制」直接矛盾：宿主机往 VM 发键鼠事件，用的就是宿主机的鼠标，一旦移出 VM 窗口点的就是真实桌面。
>
> 除隔离性外，宿主机侧执行还有两处硬伤：**UIA 无法穿透虚拟机边界**（宿主机只能看到 VM 窗口这一个不透明控件，M1 的双通道识别退化为纯 OCR，M4 Reflector 的控件存在性判据无法实现）；**宿主机查不到客机内的进程与文件**（M2 任务 8 要求的程序化成功判定做不了）。
>
> 官方大纲对执行位置无要求（唯一相关约束是合规说明第 5 条「所有操作均在本地计算机上进行」，客机运行同样满足）。

### 双模式 grounding 架构（本项目的核心设计）

| | 模式 A（基线） | 模式 B（本项目方案） |
|---|---|---|
| 坐标来源 | 规划模型原生 grounding 直接输出 | 微调后的 Qwen2.5-VL-3B 由描述定位 |
| 模型输出 | `{action, x, y}` | `{action, target_description}` |
| 送模型截图 | 需较高分辨率保证定位 | 可降分辨率，仅需语义可辨 |
| 单步上传数据量 | 大 | 小（高分辨率图不出本地） |

Qwen2.5-VL 本身具备原生 grounding 能力（可直接输出坐标点），因此模式 A 成立。两种模式在系统内通过配置切换，构成 M5 的核心消融。

**这一设计的关键价值**：两种模式使用同一模型家族，使"定位由谁做"成为可控对比。但**这个对比必须拆成两层实验，不能笼统地说"唯一变量是定位"**——模式 A 与模式 B 在端到端链路上同时改变了输出格式、调用次数、送模型的截图分辨率与提示词，把成功率差异全部归因于 grounding 能力是不成立的。

| 实验 | 所在里程碑 | 变量 | 可下的结论 |
|---|---|---|---|
| **离线定位实验** | M3 | 同一批 ScreenSpot 图与指令，只换"谁输出坐标" | 单变量干净。可直接比较定位准确率 |
| **端到端系统实验** | M5 | 整条链路差异（输出格式、调用次数、分辨率、提示词一并改变） | 只能报告成功率、耗时、错误类型的**系统级**差异，**不得将差异归因于 grounding 单一因素** |

端到端实验控制的是**规划模型、任务集与执行环境三者一致**，而非单变量。核心产出结论是"3B 级专用微调模型能否逼近通用大模型的定位精度"——由离线实验回答；系统实验回答的是"这套架构换上去之后整体表现如何"。这也让 M3 的微调成果成为系统承重模块，而非跑完即归档的孤立实验。

本项目定位为 **GUI Agent 系统工程与评测**，不训练端到端原生模型（硬件条件不支持），核心产出是可运行系统、grounding 微调效果验证与失败模式分析。

### M3 前置件提前到 M2 后半段

M3 是全项目**唯一一个单周里程碑却要装下五件事**的阶段：数据整理、LoRA 训练、六档横评、本地部署、模式 B 接入。以下四项与 M3 主线解耦、单独耗时都不长，**但任何一项在 M3 当周才暴露问题都会连锁阻塞整周**，因此固定提前到 M2 后半段（第 4 周 D6–D7）完成：

| 前置件 | 提前的理由 |
|---|---|
| 训练 / 验证 / 测试三分划定并冻结 | 划分错了 M3 整周的训练结果全部作废；且验证集是全局约束 2 要求的唯一合法调参依据 |
| LoRA 100-step smoke test | 只验流程能否跑通（数据加载 → 前向 → 反向 → 存 checkpoint → 重载 adapter），不看效果、不调超参。跑通了 M3 才敢启动 5-8 小时的正式训练 |
| **3B 4-bit 单图推理 + 峰值显存实测** | 直接回答"8GB 卡到底够不够"。**必须用真实分辨率截图**——权重只占 2-3GB，溢出风险来自视觉 token 的激活，用小图测等于没测。**另外要按"可用显存"而非"标称显存"算**：Windows 桌面（explorer / 浏览器 / 开始菜单）本身常驻约 1.5-1.7GB 显存，8GB 卡实际可用约 6.3GB。实测须记录 `nvidia-smi` 的 `memory.free` 而非 `memory.total` |
| `target_description` 结构化输出验证 | 模式 B 的接口契约。规划模型若无法稳定产出该字段，模式 B 从设计上就不成立，越早知道越好 |

四项都是**验证性质、不产出最终结果**，合计约一个白天，M2 有余量吸收；记录归档到 `docs/m3-prereq/`，M3 开工第一件事是核对齐全。

## 全局约束

1. **隔离与数据边界（两条独立约束，不可混为一谈）：**
   - **执行隔离**：Agent 的一切键鼠执行只发生在隔离虚拟机 / 容器内，宿主机不受控制。这是 M1 的硬性前置条件，任何里程碑都不得绕过。
   - **数据边界**：规划层走云端 API，**意味着截图会离开本机**，隔离虚拟机不提供数据保护。因此虚拟机内**只安装测试用软件、只使用为本项目新建的测试账号、只操作预置的测试文件**；不登录任何真实个人账号，不处理真实聊天记录、邮件、通讯录、支付信息或含个人身份信息的文档。M5 的 20 个评测任务与演示视频全部构建在这个预置测试环境上。
   - 模式 B 下高分辨率截图不出本机，但**这是架构的副产品，不能当作隐私保障来宣称**——模式 A 与规划层始终需要上传截图。
   - 大纲 W1 要求"使用真实桌面截图"做模型选型验证——此处的"真实"指真实的桌面 UI 布局，用测试环境截图即可满足，不需要个人数据。
   - **合规说明第 5 条"所有操作均在本地计算机上进行"的准确含义**：指被操作的电脑在本地，以及测试环境不含个人数据；**不是**指数据处理不得离开本机——大纲 W3 任务 4 本身就要求"支持……API 调用"，两处不可能互相矛盾。报告中的准确表述见`docs/模型与数据集许可证对照表.md`「报告里应当怎么写」一节，**不要笼统写"所有操作均在本地进行"**。
2. **ScreenSpot 固定为零样本测试集。** 不参与训练、不参与验证、不参与提示词版本选择、不参与超参数调优——任何一项沾上都构成测试泄漏，结论即作废。M2 需完成 ScreenAgent 训练来源与 ScreenSpot 的截图级 / 站点级重叠检查。**调参与提示词选型只能用独立验证集**（从 ScreenAgent 中划出，与训练集不重叠）。
3. **微调结论必须报告基线复现设置。** Qwen 官方模型卡给出 Qwen2.5-VL-3B 的 ScreenSpot 分数为 55.5，本项目须先用自己的评测脚本复现该基线并报告实测值；若与官方值有差距，**必须写明评测设置差异**（prompt 模板、坐标归一化方式、输入分辨率、命中判据、评测子集划分）。**"微调提升了多少"只有在"基线是自己同一套脚本跑出来的"前提下才成立**——拿官方数字当基线、拿自测数字当结果，是无效对比。
4. **规划层 API 可用性必须在 D1 验证通过。** 用桌面截图测试模型能否准确描述界面元素并判断下一步动作——这是整条路线的能力前提，未通过则需在 M1 内调整模型选型。
5. **轨迹日志必须从 M2 第一天就完整落盘**，M3、M4、M5 的全部分析依赖它。禁止为了看结果重跑任务。
6. **M3 不做鲁棒性，M4 不做实验。** 两个单周里程碑的边界必须守住。
7. **每个里程碑结束前完成一次代码走读与文档更新**，不留到最后集中补。
8. **API 调用与 GPU 租用均为按量使用，不用即关机**，全部资源由本人自行准备。
9. **模型与数据集许可证逐项核对归档。** 不使用"全部开源、禁止商用"这类笼统口径——各来源许可证不一致（例如 ScreenAgent 数据集为 Apache-2.0，本身并不禁止商用；而 Qwen2.5-VL-3B 权重为仅限研究的 Qwen-Research）。M2 数据调研时建立一张《模型与数据集许可证对照表》，报告中引用该表而非笼统表述。

## 全局明确不做

1. 不使用闭源商业模型（Claude / GPT 等），全部模型为官方大纲点名的开放权重模型。UI-TARS 与 Claude Computer Use 仅作技术对照，引用其公开分数。
2. 不训练端到端原生 GUI 模型（UI-TARS 路线）。
3. 不微调 7B 及以上模型，微调对象固定为 Qwen2.5-VL-3B。
4. 不做三 Agent 协作架构。Planner 输出线性子任务列表，Reflector 为轻量级级联判定，不做子任务 DAG 与全局重规划。
5. 不做移动端（Android/iOS）与 Web 端 Agent。
6. 不做登录、权限、多用户系统；不做生产级部署、高可用、容器编排。
7. 不做前端可视化界面，交互统一走 CLI + Rich 终端面板。
8. 不做 Set-of-Mark 编号标注（模式 B 下本地模型直接输出坐标）。
9. 不做 macOS / Linux 的**实机验证**。代码层面截图（mss）、鼠标键盘（pyautogui）、OCR（PaddleOCR / EasyOCR）都是跨平台的，没有 `sys.platform` 分支；UIA 识别通道为 Windows 专有，非 Windows 上自动降级为 OCR 单通道。**须在技术报告中写明：架构跨平台，但只在 Windows 上做过实机验证**——不声称三平台支持，也不自贬为「仅 Windows 通路」。
10. **不在虚拟机内处理任何真实个人数据**，评测任务与演示视频一律构建在预置测试环境上（见全局约束 1）。
11. **不把 ScreenSpot 用于测试以外的任何环节**——训练、验证、提示词选型、超参调优一律禁止（见全局约束 2）。
12. **不宣称本项目方案"可商用"**。权重可自托管，但许可证不统一；对外表述一律加"须逐项核对许可证"的限定（见全局约束 9）。

## 风险、降级触发条件与缓冲

本项目 8 周排满、无独立缓冲周，因此缓冲以**降级触发条件**的形式内置到每个里程碑。到点未达成即执行降级，不允许顺延。

| 风险 | 影响 | 降级触发条件与方案 |
|---|---|---|
| 规划模型看不懂 GUI 截图 | 全项目 | **D1 手动验证不通过** → 换用其他国产多模态 API（GLM-4V / 豆包）重测；三家都不行则技术路线重评估 |
| DPI / 多显示器坐标问题超预期 | M1 | **W2 D3 前未通过三档 DPI 验证** → 只保证 100% 缩放，其余记为已知限制 |
| 元素识别效果不达预期 | M1 | 召回率不设硬门槛，报告实测值即可；识别模块在模式 B 下只服务于 Reflector 判据与调试可视化，非主链路 |
| 规划模型无法稳定输出结构化 target_description | M3 | **M2 后半段的前置件 ④ 须做一次可行性验证**；失败则模式 B 改为"模型出坐标 + 本地模型复核纠偏"的降级形态 |
| **8GB 显存装不下 3B 的真实分辨率推理** | M3 | 权重只占 2-3GB，但动态分辨率下的视觉 token 激活可能溢出；且**实际可用只有约 6.3GB**（Windows 桌面常驻约 1.7GB）。**M2 前置件 ③ 用真实分辨率截图实测峰值**；溢出则依次降级：训练/推理前关闭浏览器与 IDE → 笔记本切 iGPU 驱动显示（可腾出约 1.7GB） → 限制 `max_pixels` → 截图分块定位 → grounding 模型改在租用 GPU 上部署 |
| **开放权重规划模型多步任务能力不足，系统跑不通** | M2/M3 | 提高子任务拆解粒度（一次一个原子动作）+ 补充 few-shot 示例；仍不行则换用更大档位的 API 模型 |
| GLM-4V-9B / Llama 3.2 Vision 部署或 API 受阻 | M3 | 二者仅为横评对照，非主链路。短租实测受阻即改走 API；API 也无托管则记录具体原因（依赖冲突、显存、模型许可）并引用公开分数替代 |
| **Blackwell（sm_120）工具链不兼容** | M3 | M1/M2 不受影响。M3 前若 PyTorch/bitsandbytes 仍无法在本机跑通 4-bit 加载 → grounding 模型改为在租用 GPU 上部署，代价是多占用一段机时 |
| **规划层 API 不可用 / 限流 / 网络抖动** | M2-M5 | 系统离线不可运行。批量评测加重试与断点续跑；**M5 录制演示视频前预留重录余量** |
| Colab 断连导致微调中断 | M3 | 每 200 步存 checkpoint；或直接在租用 GPU 上训练 |
| 模式 B 成功率低于模式 A | M3/M5 | **不视为失败**。作为负面结论写入报告，系统默认回落模式 A，M5 消融照常呈现对比数据 |
| M4 单周装不下鲁棒性全部工作 | M4 | 优先级：错误分类 > 重试与退避 > Reflector > 感知优化 > 监控面板 |
| M5 评估执行超时 | M5 | 20 任务 × 3 次可降为 20 任务 × 2 次（保住大纲要求的任务数，降重复次数）；再不够则降为 15 任务 × 3 次并在报告中说明偏差；消融组数不可再降 |
| 整体进度落后一周以上 | 全局 | 与项目方沟通延期至 10 周，优于交付残缺版本 |
