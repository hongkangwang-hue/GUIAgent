# M3 微调效果对比分析报告

> 对应大纲 W5 任务 3「对比微调前后模型在 GUI 任务理解与动作生成上的效果」
> 与交付物「微调后的模型权重 + 微调效果对比分析报告」。
> 全部数据为本机实测，原始记录在 `docs/m3-action/`。撰写日期 2026-08-24。

---

## 摘要

对 Qwen2.5-VL-3B-Instruct 做了一次 QLoRA 微调（543 条训练样本，2 epoch，
136 步），在同分布的 142 条验证集上对比微调前后的动作生成能力。

**主结果：**

| 指标 | 微调前 | 微调后 | |
|---|---|---|---|
| 输出格式合规率 | 2.1% | **100.0%** | ▲ 97.9pp |
| 动作类型准确率 | 41.5% | **85.2%** | ▲ 43.7pp |
| 坐标误差中位数 | 227.7 | **143.4** | ▼ 37% |
| 联合命中率 @ r=50 | 2.8% | **30.3%** | ▲ 10.8× |

**但这张表用的是 bf16，而 8GB 显存装不下它——实际部署（含 §7 那 50 轮
端到端）跑的一直是 4-bit NF4。** 同口径重测：

| 指标 | 微调前 4-bit | 微调后 4-bit | |
|---|---|---|---|
| 输出格式合规率 | **0.0%** | **97.9%** | ▲ 97.9pp |
| 动作类型准确率 | **7.0%** | **76.1%** | ▲ 69.1pp |
| 联合命中率 @ r=50 | 1.4% | **27.5%** | ▲ 19.5× |
| 单次推理延迟 (p50) | 1656 ms | 2923 ms | ▲ 1.77× |

**量化对两者的伤害相差近 4 倍**（基座动作类型掉 34.5pp，微调只掉
9.1pp）——微调把输出格式刻进权重后，模型对 4-bit 噪声变得鲁棒。
在真正装得下的配置里，微调的价值比 bf16 那张表显示的**更大**（69.1pp
vs 43.7pp）。详见 §2.2、§2.3、§5。

**bf16 那四个数字里有两个还需要打折看**，见 §3。诚实的结论是：

1. **格式学得彻底。** 142 条输出全部合规，这一项没有水分。
2. **动作类型的提升被高估了。** 43.7pp 里有约 25pp 来自「命名对齐」而非
   语义理解——基座模型输出 `click` 43 次，语义正确但不是动作空间里的词。
   按语义算，提升是 66.2% → 85.2%（+19pp）。
3. **坐标提升是真的，但只在「本来就接近」的样本上。** 误差 p25 从 116
   降到 41，而 p75 从 405 只降到 383——**近的变得很准，远的没救回来。**
4. **有一类动作完全没学会。** `mouse_move` 16 条全错，模型一次都没预测过它。

### 端到端：这些数字在真实任务上值多少（§7）

验证集回答「模型学会了吗」，回答不了「学会了有用吗」。把三档模型接进
完整 Agent、在 M2 的 5 个基础任务上各跑 25 轮：

| | 在线 8B（API） | 离线-基座 3B | 离线-微调 3B |
|---|---|---|---|
| 任务成功率 | **24/25 = 96%** | **0/25 = 0%** | **4/24 = 17%** |
| 其中「关闭应用」 | 5/5 | 0/5 | **4/4** |

**微调把离线版从 0% 抬到 17%，增量全部来自唯一的单步任务。** 机制可归因：

- 格式合规 2.1%→100% 让动作**能被执行**——B 组连一次有效点击都发不出去
- 但单次点击的联合命中率只有 30.3%，需要连点 3-4 处的任务在概率上做不成
  （0.3³ ≈ 2.7%，与实测的 0/5 对得上）

一句话：**微调修好了「能不能动手」，没修好「准不准」。**

⚠️ 这句话后半段原本写的是「瓶颈既不在格式也不在任务理解（3B 的任务拆解
完全合格），而在坐标精度」——**§10.6 推翻了它**。3B 的拆解粒度全面偏粗
（3.6 → 2.1 个子任务），`send_message` 上彻底失效（5.4 → 1.0）。

### 在线 8B 对照：单步几乎打平，端到端差 5.6 倍（§10）

§7 的比较藏着一个混淆——A 组是 **8B + API**，B/C 组是 **3B + 本地**，
两个变量绑在一起变了。把 A 组的模型拉到同一批 142 条验证集上：

| 联合命中 @50（分母均 142） | |
|---|---:|
| 3B 基座（本地） | 1.4% |
| **3B 微调**（本地） | **27.5%** |
| **8B**（API） | **30.3%** |

**只差 2.8pp，而端到端是 96% 对 17%。所以 96% 不是靠单步坐标准换来的。**

两个模型强在完全不同的地方：8B 坐标误差 41.3（3B 是 118.4）但格式合规
只有 38.7%（3B 是 97.9%）——**眼力好但不守规矩 vs 守规矩但眼力差**。

5.6 倍至少由三件事叠成：**拆解粒度**、**每子任务的收敛能力**
（A 3.2 步/子任务、C 5.9 步且不收敛，而两组总步数几乎相同：294 vs 302），
以及**验证集给 3B 让了分**（同分布留出集 vs 8B 从没见过）。

由此**否掉**了「模型体量是瓶颈、应租 GPU 部署 7B/8B」这个决定（§10.7）。

### 而离线组那 17% 本身就是被污染的（§10.8）

客机 243 条轨迹逐步拆开之后：

| | 重复率 | `(470, 750)` 占全部动作 |
|---|---:|---:|
| 在线 8B | 30.6% | **0.06%** |
| **离线 3B** | **75.3%** | **64.0%** |

`(470, 750)` 是 `prompts/executor_v1.yaml` **few-shot 示例里的坐标**，
而 `agent/session.py` 默认就用这份模板。**离线组近三分之二的动作是在
逐字背诵提示词里的例子，没有在看屏幕。**

46 个子任务卡在这个坐标上跑满了 `max_steps`，烧掉离线组 **73% 的总步数**。

**所以 §7 那 17% 测到的是「微调 3B + 一个会诱导它背诵的提示词」，
是模型能力的下界，不是它的水平。** 修法几乎免费：微调模型格式合规已达
97.9%，**不需要 few-shot**（§8 量过它只值 4.9pp，且那是对基座而言）。

### 对照面：不微调，光靠提示词能走多远（§8）

同一个基座 3B，三档提示词各跑满 142 条验证集：

| | 格式合规率 |
|---|---|
| 零样本 | **0.0%** |
| + few-shot 示例 | 4.9%（p=0.0145，显著） |
| + few-shot + 思维链 | **6.3%**（相对上一档 p=0.798，看不出） |
| **微调后** | **100%** |

**基座零样本 142 条里合规 0 条**——不是做得差，是根本不会这个输出格式。
提示词工程做满推到 6.3%，微调一次推到 100%，**差一个数量级**。

这否定了 §3.1 留下的假设（「很多错误其实是格式问题，few-shot 也许不必
微调就能拿到相当一部分提升」）：判断「是格式问题」对了，
判断「提示词修得动」错了。

### 瓶颈在哪：坐标精度高度依赖分辨率（§9）

把验证集的图**降**到 0.75 / 0.5 / 0.375 倍，两个模型各跑一遍：

| 坐标误差中位数 | ×1.00 | ×0.75 | ×0.50 | ×0.375 |
|---|---:|---:|---:|---:|
| 基座 | 196.4 | 286.8 | 378.1 | 391.1 |
| **微调** | **118.4** | **239.7** | 346.4 | **423.3** |

**两条曲线收敛了**——原生分辨率下微调好 40%，缩到 ×0.375 就分不出谁好。

> **微调在坐标上的全部优势，都是分辨率给的。图一小，微调就白做了。**

而语义通道完全不受影响：微调版动作类型 108/142 → 107/142 纹丝不动，
格式合规 97.9% → 95.8%。逐样本看，×1.00 与 ×0.75 之间 **97.2% 的样本
动作类型完全相同、只有 1.4% 的坐标相同**——模型说的还是同一件事，
但手指到了别处。

由此**撤回**原来「把送图分辨率升到 1536×1152」的建议（§9.6）：
数据只证明了往下走很贵，对往上走一无所知，而往上走还会破坏训练与推理
同构。改为**把客机屏幕调到 1024×768**——那样送模型时不缩也不压，
`resize()` 整步跳过。（先前写的 2560×1600→1280×800 有两处错：客机实际是
**1920×1080**，而 1280×800 是 16:10，解决不了 33% 的横向形变。）

## 1. 实验设置

| 项 | 值 |
|---|---|
| 基座模型 | `Qwen/Qwen2.5-VL-3B-Instruct` |
| 微调方法 | QLoRA（4-bit NF4 + LoRA） |
| LoRA 配置 | `r=16, alpha=32, dropout=0.05`，挂在 q/k/v/o/gate/up/down proj |
| 可训练参数 | **37,152,768 / 2,071,177,216 = 1.79%** |
| 训练集 | 543 条（ScreenAgent，冻结划分指纹 `f1d58b429c13cb30`） |
| 验证集 | 142 条（同划分，会话级切分，与训练集无截图重叠） |
| 超参 | batch 1 + 梯度累积 8，lr 1e-4，cosine，warmup 4 步，2 epoch |
| 精度 | bf16（RTX 5060 Laptop，Blackwell sm_120） |
| `max_pixels` | 802,816（896×896；数据集原生 1024×768=786,432，几乎不压缩） |
| 硬件 | RTX 5060 Laptop，8151 MiB |

### 训练实测

| 项 | 值 |
|---|---|
| 总步数 | 136（543 ÷ 梯度累积 8 × 2 epoch） |
| 训练耗时 | **5886.7s = 98 分钟** |
| **峰值显存** | **7096.6 MB**（占 8151 MiB 的 **87%**） |
| loss | **0.8069 → 0.4987**（降 38%） |
| adapter 大小 | 148 MB |

> **8GB 显存能不能微调 3B 多模态模型？** 能，但没有余量。7096.6MB 是
> `torch.cuda.max_memory_allocated()` 的读数，**只统计 torch 分配的部分**，
> 不含 CUDA 上下文与显存碎片，真实占用还要再高 500MB–1GB。训练期间
> 开一个浏览器就可能 OOM。这是本项目对「推荐 8GB 以上显存」这条
> 技术栈要求的一手回答。

### 任务定义

一条样本给「截图 + 任务目标」，模型输出「动作类型 + 坐标」：

```
输入：截图 + "Find relevant information about von Neumann on the Internet"
输出：{"action": "left_click", "x": 475, "y": 251}
```

坐标归一化到 [0,1000)，与 `SessionConfig.coordinate_space` 一致。
输出格式与 `ActionIntent` 的解析路径完全相同——**训练与推理同构**。

动作分布（训练集）：`left_click` 75.9% / `double_click` 13.3% /
`mouse_move` 10.8%。**类别极不均衡**，这是真实 GUI 轨迹的固有特征。

### 评测口径

不设单一「成功率」。动作生成只有一个真值坐标点，**「差多少算对」是人定的**，
所以分开报三组：

- **输出格式合规率** —— 合法 JSON + 动作在允许集合内 + 整数 x/y。无歧义。
- **动作类型准确率** —— 无歧义。
- **坐标误差** —— 报中位数与分位数，**不设阈值**。
- **联合命中率 @ r** —— 动作类型对且坐标在 r 内，**r 显式给出且同时报三个**。

最后一条是吸取 M2 的教训：稳定性测试里句柄斜率 +9.9 而阈值定在 10.0，
差 0.1 就翻转结论。**能随阈值变号的数字不该当结论。**

### 2.3 量化对两个模型的伤害完全不对等

这是重测顺出来的，不是原本要测的：

| | bf16 → 4-bit |
|---|---|
| 基座 动作类型 | 41.5% → **7.0%**（掉 34.5pp） |
| 微调 动作类型 | 85.2% → **76.1%**（掉 9.1pp） |

**基座模型量化后基本报废，微调后的模型扛得住。**

这对「8GB 显存能不能跑本地 GUI Agent」是个直接相关的结论：不能只看
bf16 下的基座能力，因为那个配置根本装不进去。**在真正能部署的配置里，
基座与微调的差距比 §2.1 显示的还要大**（69.1pp vs 43.7pp）。

一个合理的解释是：微调把输出格式与动作空间**刻进了权重**，
这类「窄而确定」的行为对量化噪声不敏感；而基座依赖的是通用指令跟随
能力，那是分布更宽、更容易被 4-bit 扰动的东西。**这只是解释，没有做
实验去证。**

## 3. 三项必须打折的解读

**报告最有价值的部分在这一节。** 上面那张表如果直接拿去写简历，
有两处会站不住脚。

### 3.1 动作类型的 43.7pp 里，约 25pp 是「命名对齐」而非语义理解

基座模型的预测分布：

```
left_click 76 / click 43 / type 12 / terminate 5 / (空) 3 / right_click 2 / key 1
```

**它输出 `click` 43 次**——语义完全正确（那 43 条里 35 条真值就是
`left_click`），只是没用动作空间里的那个词。系统提示词明确列了
`left_click / double_click / right_click / mouse_move` 四个动作，
它仍然自造了 `click`、`type`、`terminate`、`key`。

把 `click` 按 `left_click` 计入：

| | 严格 | 把 `click` 算作 `left_click` |
|---|---|---|
| before | 41.5% | **66.2%** |

所以**语义层面的真实提升是 66.2% → 85.2%（+19pp）**，不是 +43.7pp。

> 这不意味着 41.5% 那个数字造假——**动作名不对就是执行不了**，
> `ActionIntent` 解析出 `click` 会直接被动作白名单拦下。
> 但报告里必须两个数都给，否则读的人会以为微调让模型的**语义判断**
> 提升了一倍，而实际上大半是**输出规范**。

### 3.2 85.2% 要跟「永远输出 left_click」比，不是跟 0 比

验证集里 `left_click` 占 110/142 = **77.5%**。一个什么都不做、
永远输出 `left_click` 的模型能拿 77.5%。

| | 类型准确率 |
|---|---|
| 多数类基线（永远 `left_click`） | 77.5% |
| **after** | **85.2%** |
| 超出部分 | **+7.7pp** |

那 7.7pp 全部来自 `double_click`：**16 条里预测对 15 条**。
微调确实教会了模型区分单击与双击，但这是在一个小类（n=16）上的结论，
**置信区间很宽**。

而 before 的 41.5% **低于多数类基线**——原因就是 §3.1 的命名问题。

### 3.3 `mouse_move` 完全没学会

16 条真值 `mouse_move`，**模型一次都没预测过这个动作**：

```
after 对这 16 条的预测：left_click 14 次 / double_click 2 次
```

而且坐标误差**从 338.3 涨到 423.8**——比微调前更差。

原因是类别不均衡：`mouse_move` 在训练集里只占 10.8%（74/543），
LoRA 在 136 步内塌缩到了两个多数类。

**这是一个诚实的负面结果**，也说明「85.2%」这个总数掩盖了一整类动作
的完全失败——正是 §1 那条「按动作类型分开报」的价值所在。

## 4. 坐标：近的变准了，远的没救回来

分位数比中位数更能说明发生了什么：

| | p25 | p50 | p75 |
|---|---:|---:|---:|
| before | 116 | 228 | 405 |
| after | **41**（▼65%） | **143**（▼37%） | 383（▼5%） |

**p25 降了 65%，p75 只降了 5%。**

读法：微调把**本来就大致找对区域**的那批样本，从「差不多」推到了「相当准」
（41 在归一化 1000 空间里约等于屏幕宽度的 4%，1920 宽的屏上约 79px，
差不多一个按钮的尺度）。但**本来就完全找错地方**的那批，几乎没有改善。

这符合直觉：543 条样本能教会模型「这类任务通常点界面的哪个区域」，
教不会它「读懂这个具体界面上的这个具体控件」。后者需要的数据量是
另一个量级。

`double_click` 那一档最亮眼——**误差中位数 32.4，16 条里 10 条落在 r=50 内**。
但 n=16，不宜过度解读。

## 5. 延迟：微调让单次推理慢 1.77 倍

### 5.1 结论（4-bit NF4，即实际部署配置）

| | p25 | **p50** | p75 |
|---|---:|---:|---:|
| before-4bit | 1597 ms | **1656 ms** | 1727 ms |
| after-4bit | 2893 ms | **2923 ms** | 3054 ms |

**1656 → 2923 ms，慢 1.77 倍。** 分位区间很窄（p25/p75 相差不到 6%），
这不是个别慢样本拉出来的。

代价换回来的是格式合规 0.0% → 97.9%。**一个发不出合法动作的模型快
1.3 秒没有意义**，这个交换在 §7 的端到端实测里是划算的（0/25 → 4/24）。

输出长度不解释这个差距：`raw` 字段长度 p50 是 37（before）vs 44（after）
字符，差 19%，而延迟差 77%。**主要开销来自 adapter 本身的额外前向计算。**

### 5.2 之前那组数字为什么错得离谱

报告最初给的是这一组，并且判定为「不可用」：

| | 中位延迟 |
|---|---|
| before (bf16) | 4,674 ms |
| after (bf16) | **23,470 ms** |

看上去是「微调让模型慢了 5 倍」。**真实原因是显存不够。**

bf16 全精度约 6.2GB 权重，显卡装不下，`device_map="auto"` 把一部分层
卸载到内存，每次前向都要在 CPU↔GPU 之间搬数据。加 adapter 后占用更高、
被卸载的层更多，于是慢得更夸张。日志里的原话：

```
Some parameters are on the meta device because they were offloaded to the cpu.
```

**这曾是本报告的一处方法论缺陷**：训练用 4-bit NF4，评测却用 bf16，
两者没有对齐。当时的处理是补上 `--load-4bit` 但**不给延迟结论**——
因为同一组对比里前后必须用同一种加载方式，中途改会把量化的影响混进差值。

2026-08-25 把 before / after **都**用 `--load-4bit` 重跑了一遍，
5.02 倍塌到 1.77 倍。**其中 3.25 倍是显存卸载的产物，与微调无关。**

### 5.3 重测顺带改写了 §2

重跑不只修好了延迟。它暴露出 §2.1 那张主结果表用的 bf16
**是一个从没部署过的配置**——见 §2.2 与 §2.3，后者是这次重测里
最有价值的发现（量化对基座和微调模型的伤害相差近 4 倍）。

**教训是通用的：一个被判定为「不可用」的数据，重测的收益往往不止于
它本身。** 拖着不测，等于让一个已知错的数字留在交付物里，
同时把它连带的问题也一起留着。

## 6. 一个方法论插曲：口径搞错了会让数据「看起来不够」

本里程碑原先把微调目标定为 **grounding（元素描述 → 坐标）**，
指标定为 ScreenSpot 命中率。按那个口径，训练数据严重不足——
ScreenAgent 只能提供 569 条，而 569 条里只有 **135 个不重复的描述**，
「Insert a circle」出现 17 次对应 **17 个不同的坐标**。

**对 grounding 而言那是矛盾监督**：同一个输入对应多个互斥的正确答案。
当时的结论是「必须补充 2400 条数据」，并规划了三路补数据方案
（UIA 自建 / OS-Atlas / ScreenAgent 全量）。

对照大纲后发现口径本身就错了。大纲 W5 任务 3 的原文是：

> 对比微调前后模型在 **GUI 任务理解与动作生成** 上的效果

而 ScreenAgent 提供的正是「截图 + 任务目标 → 动作坐标」三元组——
**恰好是动作生成**。是我们把目标窄化成 grounding 之后，数据才变得不匹配。

改回大纲口径后，同样这 543 条立刻够用，补数据方案全部作废，
而且训练出了本报告的结果。

> **教训：数据与指标不匹配时，先怀疑指标是不是自己改的，
> 而不是先去找更多数据。**

## 7. 端到端：微调在真实桌面任务上值多少

前六节全部基于**验证集**——同分布的 142 条 ScreenAgent 样本。它回答的是
「模型学会了吗」，回答不了「学会了有用吗」。

本节把三档模型接进完整的 Agent 系统，在 M2 的 5 个基础任务上各跑 25 轮，
用**程序化判定**（查进程 / 窗口 / 文件）算成功率。撰写日期 2026-08-25。

### 7.1 三组的差别只有一处

| 组 | 规划模型 | 部署方式 | 数据边界 |
|---|---|---|---|
| **A 在线** | qwen3-vl-8b-instruct | 阿里云百炼 API | 截图上传平台服务器 |
| **B 离线-基座** | Qwen2.5-VL-3B-Instruct | 宿主机 GPU，客机经 HTTP 调 | 截图不出本机 |
| **C 离线-微调** | 同上 + 本次的 LoRA adapter | 同上 | 截图不出本机 |

同一个脚本、同一份任务清单、同一套提示词、同一个坐标空间。B 与 C 之间
**只差一个 adapter**，A 与 C 之间只差模型与部署位置。

> 拓扑说明：GPU 在宿主机、客机无直通，而全局约束要求键鼠执行只发生在
> 客机内，两条约束逼出「宿主机跑权重、客机 HTTP 调用」这个结构。
> 宿主机与客机是同一台物理机（VMware NAT / VMnet8），**这条 HTTP 不出本机**，
> 仍属大纲 W3 的「本地部署」。见 `milestone-0-overview.md`。

### 7.2 主结果

| 任务 | A 在线 8B | B 离线-基座 3B | C 离线-微调 3B |
|---|---|---|---|
| 打开浏览器 | 5/5 | 0/5 | 0/5 |
| 搜索指定内容 | 4/5 | 0/5 | 0/5 |
| 打开指定文件 | 5/5 | 0/5 | 0/5 |
| 发送消息 | 5/5 | 0/5 | 0/5 |
| **关闭应用** | 5/5 | **0/5** | **4/4** |
| **合计** | **24/25 = 96%** | **0/25 = 0%** | **4/24 = 17%** |

**微调把离线版从 0% 抬到 17%，全部增量来自「关闭应用」一个任务。**

其余指标：

| | A 在线 | B 基座 | C 微调 |
|---|---|---|---|
| 平均步数 | 11.8 | 9.6 | 12.6 |
| 平均每轮耗时 | 37.4s | 274.9s | 415.4s |
| 每步模型延迟 | 1553ms | 25280ms | 30005ms |
| API 费用 | 未配单价，**未知** | 0（确认值） | 0（确认值） |

> 成本一栏的两种 0 必须分开：离线版的 API 费用是**查证过的 0**，在线版
> 显示 0 是因为没配单价、属于**未知**。拿确认的 0 去比未知的 0 得不出
> 「离线更省」——何况离线版每轮多花 6-11 倍的时间，成本只是换了形态。

### 7.3 为什么偏偏是「关闭应用」

因为它**只需要点对一次**（关闭按钮），而其余四个任务要连着点对 3-4 处。

用 **§2.2 的 4-bit 联合命中率 27.5%** 做个粗算（本节三组跑的都是
4-bit NF4，`load_4bit` 默认为 True，所以口径必须用 4-bit 那张表，
不是 §2.1 的 bf16）：

| 任务需要连点几处 | 单轮成功的粗略概率 |
|---|---|
| 1 处 | 27.5%，而 Loop 有 6 步重试机会 ⇒ 接近 90% |
| 3 处 | 0.275³ ≈ **2.1%** |

**实测的 4/4 与 0/5 与这个量级对得上。** 这也说明验证集上那个
「联合命中 27.5%」不是一个抽象指标——它直接决定了哪些任务做得成。

B 组的 0/25 在 4-bit 口径下有了一个**字面意义上**的解释：
`before-4bit` 的格式合规率是 **0.0%**——142 条验证样本里合规 0 条。
不是「很少发得出动作」，是**一条都发不出**。
（§2.1 的 bf16 给的是 2.1%，方向相同但没这么绝对。）

因此本节的结论不是「微调有效/无效」，而是更具体的一句：

> **微调修好了「能不能动手」，没修好「准不准」。**
> 单步任务因此从不可能变成可行，多步任务仍受限于坐标精度。

⚠️ **「多步任务仍受限于坐标精度」这半句在 §10 被证明是不完整的。**
同一批验证集上，8B 的联合命中只比微调 3B 高 2.8pp，端到端却高 5.6 倍——
说明多步任务的失败不主要在坐标。§10.5 用同一批存档拆出了真正的差别：
**任务拆解粒度**（A 3.6 vs C 2.1 个子任务，`send_message` 上 5.4 vs 1.0）
与**每子任务的收敛能力**（3.2 vs 5.9 步，总步数几乎相同：294 vs 302）。

本节的粗算（0.275³ ≈ 2.1%）仍然成立，但它解释的是**坐标这一层的下界**，
不是全部原因。

### 7.4 两个方向都不可信的自我判断

C 组「关闭应用」的 4 次成功里，**有 3 次是跑满 6 步、模型自报「没做完」**：

| 轮次 | 判定 | 步数 | 模型自报完成 |
|---|---|---|---|
| 第 2 次 | ✓ | 6（上限） | **False** |
| 第 3 次 | ✓ | 6（上限） | **False** |
| 第 4 次 | ✓ | 3 | True |
| 第 5 次 | ✓ | 6（上限） | **False** |

**它把计算器关掉了，自己却不知道**，于是继续操作到步数上限。

反方向也有：C 组另有 **3 轮「模型自报完成但判定未通过」**（全部是
「打开指定文件」）。而 B 组一次都没自报过完成——它连动作都发不出去。

| 组 | 自报完成但没做成 | 做成了却不自报 |
|---|---|---|
| A 在线 | 0 | 打开指定文件 3/5（M2 报告 §10 已记） |
| B 基座 | 0 | 0（一次都没做成） |
| C 微调 | **3** | **3** |

**模型的自我判断在两个方向上都不可信**，而这正是不能用模型自报当成功
判据的直接证据——M2 定的「程序化判定」在这里兑现了价值。这批数据是
M4（大纲 W6「错误检测与自动重试」）的一手素材。

### 7.5 这一节数据的四条限制

1. **与验证集的数不能互推。** 走 HTTP 时截图经 JPEG q85 压缩，
   而 `eval/action.py --local` 是无损的。85.2% 与 17% 之间没有换算关系。
2. **C 组有 1 轮无效**（关闭应用第 1 次，起点未建立），分母因此是 24 而非 25。
   原因是 reset 里 `taskkill` 之后只等 3 秒，而 UWP 计算器冷启动更久。
   已改为轮询（`tasks/wait_for_process.py`），但**本次数据保持原样**。
3. **A 组的 5 轮「发送消息」无效**（模拟消息程序未启动），已补跑，
   两份存档合并统计。
4. **B 组另有一次整体作废的运行**（`20260824-223451`）：客户端超时 90 秒
   而本机生成 1024 token 需 140 秒，25 轮里 15 轮连规划都没完成。
   **存档保留作为缺陷证据，不进本表。** 修复见 `serve_local_model.py`
   的生成上限与 `llm/factory.py` 的本地超时。

## 8. 提示词工程消融（大纲 W5 任务 4）

前面七节都在问「微调值多少」。这一节问的是它的对照面：**不微调，光靠
提示词能走多远？** §9 遗留项 4 给过一个具体假设——§3.1 发现基座模型的
很多「错误」其实是格式问题，那么**一个带 few-shot 示例的提示词，也许
不必微调就能拿到相当一部分提升**。

这一节把那个假设测了。

### 8.1 三档只差一个变量

| 档 | 模板 | 相对上一档多了什么 |
|---|---|---|
| P1 | `executor_v0` | —— 零样本基线 |
| P2 | `executor_v1` | **3 条 few-shot 示例** |
| P3 | `executor_v2` | **显式思维链**（在 `thinking` 里按三步推理） |

**三份模板的系统提示逐字相同**，差异只在 few-shot 段与 CoT 段。因此
P1→P2 的差就是 few-shot 的净效果，P2→P3 的差就是 CoT 的净效果。

这一点不是靠人工核对保证的：`tests/test_prompt_ablation.py` 把
「P1 与 P2 的系统提示逐字相同」「P3 的系统提示是 P2 加一段而不是改写」
写成了断言。**任何一档被顺手改了措辞就会红。** 做过一次变异测试：
往 v1 的系统提示里加两个字，两条用例立刻失败。

这类污染在结果表上是**完全看不出来**的——三列数字照样整整齐齐。

### 8.2 主结果（基座 3B，验证集 142 条全量）

| 指标 | P1 零样本 | P2 +few-shot | P3 +思维链 |
|---|---|---|---|
| 样本数 | 142 | 142 | 142 |
| **格式合规率** | **0.0%** | **4.9%** | **6.3%** |
| 动作类型准确率 | 3.5% | 7.7% | 9.9% |
| 坐标误差中位数 | 310.1 | 230.4 | 265.2 |
| 联合命中 @50 | 0.7% | 1.4% | 1.4% |
| 逐字照抄示例 | 0.0% | 0.0% | 0.0% |
| 中位延迟 (ms) | 2456 | 2561 | 2767 |

显著性（Fisher 精确检验）：

| 对比 | | p | |
|---|---|---|---|
| 格式 P1→P2（few-shot） | 0/142 → 7/142 | **0.0145** | 显著 |
| 格式 P2→P3（CoT） | 7/142 → 9/142 | 0.798 | 看不出 |
| 格式 P1→P3（合起来） | 0/142 → 9/142 | **0.0034** | 显著 |
| 动作类型 P1→P3 | 5/142 → 14/142 | 0.055 | 差一点 |

**站得住的只有一条：few-shot 让格式合规率从「一条都没有」变成「有几条」。**
CoT 那一档在 142 条上什么都没证明——格式 +1.4pp、坐标反而变差、
联合命中持平。

### 8.3 结论：假设被否定了

| | 格式合规率 |
|---|---|
| 基座 + 零样本 | 0% |
| 基座 + 提示词工程做满（few-shot + CoT） | **6.3%** |
| **微调后**（§2） | **100%** |

**基座 3B 零样本 142 条里合规 0 条**——这不是「做得差」，是根本不会这个
输出格式。提示词工程能把它推到 6.3%，**微调一次推到 100%**。

所以 §9 遗留项 4 的假设**否定得很彻底**：格式问题确实是基座失败的主要
形态（§3.1 判断正确），但**提示词修不动它**。差着一个数量级。

大纲 W5 任务 4 问「优化提示词工程能否提升模型的任务执行准确率」——
答案是能，从 0% 到 6.3%；而**同一件事微调能做到 100%**。有这组对照，
这句话才敢说。

### 8.4 一处必须记下的方法论错误

**第一次跑的是 `--limit 20`（取文件前 20 条）作为探路，结论完全相反。**

| | 前 20 条 | 后 122 条 |
|---|---|---|
| P2 格式合规 | **5/20 = 25%** | **2/122 = 1.6%** |
| P3 格式合规 | **7/20 = 35%** | **2/122 = 1.6%** |

原因：`val.jsonl` **按 session_id 排序**，同一会话的十几条样本连在一起。
切前 20 条拿到的不是 20 个样本，是 **6 个 session**（全集 43 个），
而其中一两个会话的界面恰好是模型应付得了的。

于是「few-shot 的效果」被放大了约 **15 倍**，还配上了一个 p=0.047 的
显著性检验——**检验本身没错，错的是送进去的样本**。跑满 142 条才发现
真值是 4.9%。

探路样本的用途正是「先看个大概」。**它给出系统性偏高的数，比不跑更糟。**

已修：`eval/action.py` 的 `--limit` 改为 `spread_by_session()` 轮流取，
N 条来自 N 个不同 session，且是确定性的。`tests/test_prompt_ablation.py`
的 `TestLimitSampling` 钉住这个行为，改回切前缀会红（已做变异测试）。

### 8.5 一个没有兑现的担心

§9 遗留项 4 记过一条反向证据：探针里撞见 3B **逐字照抄 few-shot 示例**，
吐出示例里的常数坐标 `(470, 750)`——格式 100% 合规、位置全错。
`format_acc` 和 `action_acc` 一个都拦不住这种输出。

为此在 `eval/action.py` 加了 `parrot_rate` 单独量它。**本轮三档全是 0.0%。**

指标保留：它拦的是另外两个指标结构上拦不住的东西，成本只是一列数。
本轮 few-shot 那 4.9pp 是真的，不是抄来的。

> ⚠️ **更正（2026-08-25）：上面那句「担心没有兑现」只在验证集上成立。**
>
> §10.8 的轨迹探针查出：**实机运行时，离线组 64% 的动作就是
> `(470, 750)`**——正是 few-shot 示例里的那个常数。
>
> | | 照抄率 |
> |---|---:|
> | ScreenAgent 验证集（同分布、4:3、无形变） | **0%** |
> | 真实桌面（分布外、横向压扁 33%） | **64%** |
>
> **照抄是分布相关的**：图越陌生，模型越退回背例子。而验证集恰恰是它
> 最熟悉的那批图——**我们用最不可能触发这个问题的数据去测这个问题。**
>
> 这是本报告方法论上最值得记住的一条：**一个指标在某批数据上等于零，
> 不代表这件事没发生，可能只说明那批数据测不出它。**

```bash
python scripts/ablate_prompts.py --local Qwen/Qwen2.5-VL-3B-Instruct --load-4bit
python scripts/ablate_prompts.py --report        # 只汇总
```

原始数据：`docs/m3-action/executor_v0.jsonl` / `executor_v1.jsonl` /
`executor_v2.jsonl`，各 142 条逐条预测。

## 9. 分辨率消融：微调在坐标上的优势全是分辨率给的

§7.3 把端到端瓶颈定位到**坐标精度**，§8 排除了提示词这条路。这一节问
剩下的那个我们能控的变量：**送图缩太狠，是不是坐标不准的原因之一？**

客机屏幕 **1920×1080**，送模型前缩到 1024×768（`SessionConfig.image_size`）。

> **更正（2026-08-25）：本报告先前写的是「客机屏幕 2560×1600，缩了 2.5 倍」，
> 那是宿主机的屏幕。** 客机实际是 1920×1080——由 `scripts/probe_retries.py`
> 从 243 条轨迹的 `meta.json` 读出（`environment.resolution`），
> 且**全部 243 条一致**，见 §10.9。

而真实情况比「缩 2.5 倍」更麻烦，因为**两条路都是直接拉伸，不保宽高比**
（`llm/qwen_vl_local.py` 的 `_prepare_image`、`perception/capture.py` 的
`resize_to`）：

```
客机     1920×1080   16:9  = 1.778
送模型   1024×768     4:3  = 1.333

横向  1024/1920 = ×0.533
纵向   768/1080 = ×0.711
```

**不是等比缩小，是横向压得比纵向狠——形变 33%。** 一个圆按钮到模型眼里
是个扁 33% 的椭圆，而 ScreenAgent 的训练图原生就是 4:3，从没被压过。
这是一个**独立于分辨率**的分布偏移，本节的梯子没有覆盖到它
（梯子缩的是 4:3 的图，等比，无形变）。

坐标映射不受影响：模型答的是归一化 1000 空间，回映射时逐轴还原，形变会
被抵消。**受影响的是模型能不能认出那是个按钮。**

### 9.1 原来的实验设计是错的

§10 遗留项 5 原本写的是「1024×768 → 1536×1152，用历史帧数换分辨率」。
落地时发现两个问题：

1. **验证集根本测不了。** ScreenAgent 的截图**原生就是 1024×768**——
   训练集 543 条、验证集 142 条无一例外。没有更高分辨率的源可以喂，
   放大不产生细节。
2. **会把分辨率效果和分布偏移混在一起。** `image_size = (1024, 768)`
   精确匹配训练分布；改成 1536×1152 等于把微调模型喂进一个**它从没
   见过的分辨率**，违反本项目一直在守的「训练与推理同构」。

所以那个设计只能开虚拟机端到端跑（每档 25 轮、几小时），而且结果不可归因。

**改成反着做**：把验证集的图**降**到 0.75 / 0.5 / 0.375 倍，看坐标精度
掉多少。便宜（142 条 × 四档 ≈ 25 分钟，不碰键鼠）、有真值、方向可控。

真值坐标存的是**归一化 1000 空间**（`point_norm`），模型也被要求在 1000
空间作答，所以**缩图不动真值、不动输出口径**，差值干净地归给分辨率。
`tests/test_resolution_ablation.py` 把这条前提钉成了断言——真值哪天改成
像素坐标，这套消融会**静默地全错**（每档误差按缩放倍数虚高，而表格照样
打印得整整齐齐）。

### 9.2 微调模型：语义通道不动，空间通道塌掉

| 指标 | ×1.00 原生 | ×0.75 | ×0.50 | ×0.375 |
|---|---:|---:|---:|---:|
| 格式合规率 | 97.9% | 97.9% | 96.5% | 95.8% |
| 动作类型准确率 | 76.1% | 76.1% | 73.2% | 75.4% |
| **坐标误差 p25** | **37.4** | **128.6** | 212.9 | 233.4 |
| **坐标误差 p50** | **118.4** | **239.7** | 346.4 | 423.3 |
| 坐标误差 p75 | 339.7 | 385.2 | 510.4 | 651.3 |
| **联合命中 @50** | **27.5%** | **8.5%** | 3.5% | 5.6% |

**格式与动作类型几乎不动，坐标误差涨 3.6 倍。**

逐样本对比 ×1.00 与 ×0.75：

```
预测动作类型完全相同   138/142 = 97.2%
预测坐标完全相同         2/142 =  1.4%
坐标位移中位数                   167.9
```

**同一批图缩小 25%，模型说的还是同一件事，但手指到了别处。**
这排除了「低分辨率只是把模型整体搞糊涂了」这个替代解释——
语义通道没受影响，只有空间通道塌了。

最陡的一段在最前面：`p25` 从 37.4 跳到 128.6（**仅 ×0.75 就涨 3.4 倍**），
联合命中 39/142 → 12/142（p < 0.0001）。而后面三档两两之间**全都看不出
差异**（p=0.13 / 0.57）——掉到某个程度以下就都一样烂了。

这与 §4 的发现互为表里。§4 说「近的变准了，远的没救回来」，
现在知道**「近的那部分」正是分辨率买来的**：`p25` 崩得最狠，`p75` 只从
340 到 385。

### 9.3 但这里有个混淆，必须用第二把梯子排除

微调模型**只见过 1024×768**。所以 ×0.75 已经是分布外了——那道悬崖到底是
**分辨率**造成的，还是**偏离训练分辨率**造成的？在 §9.2 的数据里分不开。

**同一把梯子在基座模型上再跑一遍。** 基座没被 1024×768 微调过，
Qwen2.5-VL 原生支持动态分辨率——**它没有「训练分辨率」可以偏离**。

| 坐标误差 p50 | ×1.00 | ×0.75 | ×0.50 | ×0.375 | 恶化 |
|---|---:|---:|---:|---:|---|
| **基座** | 196.4 | 286.8 | 378.1 | 391.1 | **+99%** |
| **微调** | 118.4 | 239.7 | 346.4 | 423.3 | **+258%** |

**基座那 +99% 不可能是分布偏移造成的，因为没有分布可偏离。**
分辨率是真的有因果作用，假设活下来了。

微调那多出来的部分里有多少是分布偏移——**分不开，本报告不给数**。

### 9.4 两条曲线收敛了，这是本节最重要的一句

```
              基座    微调
×1.00 原生     196     118      ← 微调好 40%
×0.75          287     240
×0.50          378     346
×0.375         391     423      ← 已经分不出谁好
```

> **微调在坐标上的全部优势，都是分辨率给的。图一小，微调就白做了。**

两个通道的命运完全不同：

| | ×1.00 | ×0.375 | |
|---|---|---|---|
| 基座 动作类型 | 10/142 | **0/142** | p=0.0017，全塌 |
| 微调 动作类型 | 108/142 | **107/142** | 纹丝不动 |
| 微调 坐标误差 | 118 | **423** | 塌了 |

**微调让「说什么」不吃分辨率了，但没让「指哪里」不吃。** 基座是两个通道
一起塌。这和 §9.2 那个逐样本对比是同一件事的两面。

### 9.5 一个必须给的参照，和一行不可解读的数

**随机瞎猜的误差中位数 ≈ 512**（1000×1000 空间内两点距离的中位数，
20 万次采样）。×0.375 时两个模型都在 391 / 423，**已经接近瞎猜**。

所以最低那一档被地板压着，**基座能测出的恶化幅度是被低估的**——
它起点（196）就离地板近，往下掉的空间本来就小。

另外，基座的格式合规率那一行是 0.0% → 1.4% → 4.2% → 2.1%，
计数为 0 / 2 / 6 / 3，非单调。**这行样本量太小，不可解读，本报告不用它
说任何事。**

### 9.6 结论指向的改法，和原计划相反

这批数据留下一个**方向不对称**：

> 我们现在有很硬的证据说「**偏离 1024×768 往下走**很贵」。
> 我们对「**往上走**」**一无所知**。

§10 原来提的「客机升到 1536×1152」是往上走。**在这批数据之后，
它变成了一个赌博**——也可能像往下走一样翻车，而且会同时破坏训练与推理
同构。**本报告撤回那个建议。**

数据支持的是反过来的改法：**把客机屏幕分辨率调低。**

```
现在：客机 1920×1080  ──横 ×0.53 / 纵 ×0.71，形变 33%──→  1024×768
改成：客机 1024×768   ──不缩、不压，resize() 整步跳过──→  1024×768
```

**必须是 4:3。** 先前这里写的是 1280×800——那是 16:10，只解决了缩放倍数、
**没解决形变**，压扁一模一样。1024×768 下 `_prepare_image` 的
`if (image.width, image.height) != (width, height)` 直接不成立，
一次插值都不做。

不选 1280×960（也是 4:3、缩 ×0.8）的理由在 §9.2：**最陡的一段就在最前面**，
仅 ×0.75 坐标误差就翻倍，所以「差不多就行」在这里不成立。

代价是 Windows 11 在 1024×768 下桌面很挤。但那正是 ScreenAgent 训练图里
桌面的样子，而五个测试任务都不需要大屏幕。留给 M4 的端到端复跑验证。

### 9.7 这一节证不了什么

它量的是**低于** 1024 的衰减。客机的问题是 2560 的细节被压进 1024 ——
两者在「界面元素在输入里变小」这一点上同向，但**不是同一件事**：
前者整张图变糊，后者是图清晰而元素小。

严格说，本节证明的是：**这个模型的坐标精度对界面元素的像素尺寸高度敏感，
而语义判断不敏感。** 「客机降分辨率会让端到端变好」仍是一个**未验证的
推论**，要靠 §9.6 那个实机对照来定。

便宜的筛选排在昂贵的验证前面——这是本节全部的用途。

## 10. 在线 8B 对照：单步几乎打平，端到端差 5.6 倍

§7 的三组比较里藏着一个混淆：**A 组是 8B + API，B/C 组是 3B + 本地**，
模型体量和部署方式**绑在一起变了**。「96% vs 17%」里有多少是 8B 的功劳、
多少是 API 的功劳，§7 答不了。

本节把 A 组的模型拉到**同一批 142 条验证集**上跑，提示词、解析、真值全部
相同，只有模型不同。

### 10.1 先修一个口径缺陷：分母不一致

首次汇总报出「调用失败 22」。查下来那 22 条**不是网络失败**，是
`模型输出中找不到可解析的 JSON 对象`——**格式失败**。而 `summarize()`
按 `error` 把它们剔出了分母。

根因是同一种失败在两条评测路径上被记成了两件事：

| | 输出解析不出来时 |
|---|---|
| 本地路径 | `extract()` 静默返回 None → **留在分母里**，记 `format_ok=False` |
| API 路径 | `predict_action` 抛异常 → 记 `error`，**被剔出分母** |

后果是 8B 的 15.5% 格式失败凭空消失：

| | 分母 120（错） | **分母 142（可比）** |
|---|---:|---:|
| 格式合规率 | 45.8% | **38.7%** |
| 动作类型准确率 | 69.2% | **58.5%** |
| 联合命中 @25 | 26.7% | **22.5%** |
| 联合命中 @50 | 35.8% | **30.3%** |

**而它正要跟本地那组 142/142、0 error 的数字并排比较。**
分母不一致的两列数摆在一起，看不出任何异常。

已修：`LLMBackendError` 现在带 `raw`（`llm/base.py` 的注释一直写着
「解析失败要带着原文抛……这正是 M3 比较各模型格式稳定性的依据」，
但代码没兑现——22 条失败样本的 `raw` 全是空串）；API 路径吞掉
`parse_error` 走正常记录。**只吞 `parse_error`**——网络超时、限流、
余额不足仍然记 error，那些确实不是模型的失败，剔出分母才对。
`tests/test_eval_denominator.py` 钉住这条。

### 10.2 主结果：单步只差 2.8pp

| 联合命中 @50（分母均为 142） | |
|---|---:|
| 3B 基座（本地 4-bit） | 1.4% |
| **3B 微调**（本地 4-bit） | **27.5%** |
| **8B**（API） | **30.3%** |

**8B 只比微调后的 3B 高 2.8 个百分点。而端到端是 96% 对 17%。**

这足以否掉一句话：**96% 不是靠单步坐标准换来的。**

### 10.3 两个模型强在完全不同的地方

| | 8B | 3B 微调 |
|---|---:|---:|
| **坐标误差中位数** | **41.3** | 118.4 |
| 动作类型准确率 | 58.5% | **76.1%** |
| **格式合规率** | 38.7% | **97.9%** |
| 中位延迟 | 4387 ms | 2923 ms |

**8B 眼力好但不守规矩；微调 3B 守规矩但眼力差。** 联合命中要两条同时
满足，所以打平。

8B 的毛病很具体——它几乎只会输出 `left_click`：

| 真值动作 | n | 类型准确率 | 坐标误差中位数 |
|---|---:|---:|---:|
| `left_click` | 110 | 74.5% | 46.7 |
| `mouse_move` | 16 | 6.2% | 94.8 |
| **`double_click`** | 16 | **0.0%** | **13.9** |

`double_click` 一次都没预测对，**而坐标误差是全表最低的 13.9**——
它看懂了要点哪儿，没看懂要双击。这恰恰是微调 3B 学会的东西（§3.2）。

### 10.4 这个比较仍然偏向 3B

验证集是 **ScreenAgent 的留出划分**：

| | 验证集对它是什么 |
|---|---|
| 微调 3B | **同分布**（同一批语料，会话级切分的留出集） |
| 8B | **完全没见过** |

**所以「只差 2.8pp」是让了分的。** 换到真实 Windows 桌面——对两个模型
都是分布外，但 8B 的通用预训练覆盖得多——差距才拉开。

这也意味着：**本报告的单步指标系统性地高估微调 3B 的实战能力。**
§2 的所有数字都带着这个偏向。要去掉它，需要一批**真实桌面截图 + 人工
标注的点击真值**，本项目没有做。

### 10.5 那 5.6 倍在哪：拆解粒度

回到 §7 的端到端存档，按任务拆开看：

| 任务 | A 子任务 | C 子任务 | A 步/子任务 | C 步/子任务 |
|---|---:|---:|---:|---:|
| open_browser | 2.0 | 2.2 | 2.1 | 5.3 |
| search_content | 3.2 | 2.2 | 4.0 | 8.0 |
| open_file | 6.6 | 4.0 | 2.9 | 3.8 |
| **send_message** | **5.4** | **1.0** | 3.8 | **12.0** |
| close_app | 1.0 | 1.0 | 2.0 | 5.2 |
| **合计** | **3.6** | **2.1** | **3.2** | **5.9** |

**`send_message`：A 拆成 5.4 个子任务，C 拆成 1 个**，然后在这一个子任务
上烧掉 12 步。它不是在「一步步做」，是在**对着整个任务反复试**。

而步数预算几乎相同：

```
A：294 步  →  24 次成功
C：302 步  →   4 次成功
```

**C 不是步数不够，是它的步数不产生进展。**

### 10.6 由此修正 §7 的一句话

摘要与 §7 原来写着：

> 瓶颈既不在格式也不在任务理解（**3B 的任务拆解完全合格**），而在坐标精度。

**「任务拆解完全合格」是错的**，本节的数据推翻了它。3B 的拆解粒度全面
偏粗（3.6 → 2.1），`send_message` 上彻底失效（5.4 → 1.0）。

修正后的说法：

> 5.6 倍的差距至少由三件事叠成——**拆解粒度**（3.6 vs 2.1 子任务）、
> **每子任务的收敛能力**（3.2 vs 5.9 步且不收敛）、以及
> **验证集给 3B 让了分**（同分布 vs 从没见过）。坐标精度是其中之一，
> 但不是全部，甚至可能不是主要的那个。

### 10.7 一个被这批数据否掉的决定

§11 结论原本写着「**模型体量而非架构是瓶颈**」，并据此考虑租 GPU 部署
7B/8B。**这批数据否掉了它。**

换更大的本地模型能买到的是**单步坐标精度**，而 8B 在这项上只领先 2.8pp
（§10.2），端到端却领先 5.6 倍——**那 5.6 倍在拆解和收敛上，换模型买不到。**
§10.4 更进一步：7B 在这个验证集上的分数**只会比 3B 更低**（它同样没见过
ScreenAgent），拿它做对照反而更难解释。

**结论：不租 GPU 部署更大的模型。** 大纲 W5 明确允许云 GPU
（「本地 GPU 或 Google Colab GPU 资源」），所以租机器做**训练与评测**
完全合规；但租机器跑**实机 Agent** 意味着每一帧屏幕截图出本机——
那在数据流上和调 API 是同一件事，报告里只能叫**「自托管」**，
不能叫「本地部署」，M0 那条数据边界它不满足。

### 10.8 轨迹探针：离线组 64% 的动作在背诵提示词里的例子

§10.5 只用了存档里的**汇总数**（步数、子任务数）。把客机的 243 条轨迹
逐步拆开之后，出现了一个比拆解粒度更直接的解释。

`scripts/probe_retries.py` 在客机里跑（`outputs/` 是 gitignore 的，
轨迹带整屏截图，**探针默认只导结构化数据**——动作类型、坐标、执行状态，
不导截图也不导模型对屏幕的描述，理由见脚本文档）。

#### 重复率：离线是在线的 2.5 倍

「同一次尝试」= 动作类型相同 **且** 坐标距离 ≤ 10（归一化 1000 空间）。
不按逐字相等算——GUI 按钮几十像素宽，抖动两三像素看着像改主意，
其实点的是同一个东西。

| | 轨迹 | 步数 | 不同的尝试 | **重复率** | 死循环子任务 |
|---|---:|---:|---:|---:|---|
| 在线 8B | 183 | 1763 | 1223 | **30.6%** | 42/514 = 8.2% |
| **离线 3B** | 60 | 583 | 144 | **75.3%** | **46/82 = 56.1%** |

**离线组每 4 步才产生 1 个新尝试。** 一半以上有重试的子任务是纯粹的
原地打转——每一次尝试都和上一次一模一样。

#### 卡在哪：`(470, 750)`

| | `(470, 750)` 出现次数 | 占该组全部动作 |
|---|---:|---:|
| 在线 8B | 1 / 1763 | **0.06%** |
| **离线 3B** | **373 / 583** | **64.0%** |

而 `(470, 750)` 是 `prompts/executor_v1.yaml:79` **few-shot 示例里的坐标**：

```yaml
{"action": "left_click", "x": 470, "y": 750, "thinking": "任务栏最左侧的 Windows 徽标就是开始按钮"}
```

`agent/session.py:56` 的 `executor_template` 默认就是 `executor_v1`。

**离线组 64% 的动作是在逐字背诵提示词里的例子，没有在看屏幕。**

46 个死循环子任务里 38 个卡在这个坐标上，步数分布是 12 步 × 25 个、
6 步 × 21 个——**正好是 `basic_tasks.yaml` 里两档 `max_steps`**。
它们全都跑满了上限，每一步点同一个地方。这 46 个子任务烧掉
**426 / 583 = 73%** 的离线组总步数。

执行状态是 `ok: 548 / failed: 4 / no_action: 31`——**点击在机械上都成功了，
只是点在错的地方。** 系统里没有任何一处能发现「它在原地打转」。

#### 这推翻了 §8.5

§8.5 报的 `parrot_rate` 三档**全是 0.0%**，当时写的是「之前担心的逐字
照抄本轮未复现」。

**那句话在验证集上成立，在实机上不成立：**

| | 照抄率 |
|---|---:|
| ScreenAgent 验证集（同分布、4:3、无形变） | **0%** |
| 真实桌面（分布外、横向压扁 33%） | **64%** |

**照抄是分布相关的**——图越陌生，模型越退回背例子。而验证集恰恰是它最
熟悉的那批图。**我们用最不可能触发这个问题的数据去测这个问题。**

这也和 §10.4 是同一件事的两个侧面：验证集对微调 3B 太友好了。

#### 于是 §7 的 17% 不再是模型的分数

§7 声称测的是「微调 3B 能做成几个任务」。**实际测到的是「微调 3B +
一个会诱导它背诵的提示词」。**

**那 17% 是模型能力的下界，不是它的水平。** 本报告不修改 §7 的数字
（它是真实跑出来的），但读者必须知道这一条。

#### 修法几乎免费，且 §8 已经量过代价

§8 量过 few-shot 值多少：**基座模型格式合规 +4.9pp**。而微调模型的格式
合规是 **97.9%**——**它根本不需要格式示例**。

```
微调模型带 few-shot：   收益 ≈ 0（格式已 97.9%）   代价 64% 的动作被污染
```

`prompts/executor_v0.yaml`（零样本档）§8 时已经建好，改一行
`executor_template` 即可切换。

#### 对 M4 任务 2 的直接影响

原来设想的「错误检测与自动重试」要重新定位：

| | |
|---|---|
| **根因** | 提示词诱导背诵——**改一行配置**，不是重试机制的问题 |
| **重试机制** | 仍要做，但它防的是剩下那 36%，不是主要矛盾 |
| **必须新增** | **检测「这一步与上一步相同」并强制换策略**——46 个子任务全都跑满步数上限，系统里没有任何机制发现它在原地打转 |

#### 顺带确认的一件事

243 条轨迹的屏幕设置**全部是 `1920×1080 @1.0x`**，无一例外。
**§7.1「三组的差别只有一处」在这一项上站得住**——分辨率从未在实验中途
变过。同时这也修正了本报告先前写错的客机分辨率（见 §9 开头的更正框）。

```bash
python scripts/probe_retries.py                           # §10.8，**在客机里跑**
```

## 11. 结论

**大纲 W5 的四项任务均已完成：**

1. ✅ 基于预处理后的公开 GUI 数据集构建了训练集与验证集（543 / 142，
   会话级切分，指纹冻结）
2. ✅ 用 PEFT 完成 LoRA 微调，产出 adapter 权重（148 MB）
3. ✅ 对比了微调前后在 GUI 任务理解与动作生成上的效果
4. ✅ 优化提示词工程：三档消融跑满验证集，量出提示词工程的上限（§8）

**能站住的结论：**

- **小样本 LoRA 对「输出规范」极其有效**：543 条、136 步、1.79% 的参数，
  把格式合规率从 2.1% 拉到 100%。
- **对「语义判断」有中等提升**：动作类型 66.2% → 85.2%（按语义口径），
  超出多数类基线 7.7pp，主要贡献来自学会了 `double_click`。
- **对「空间定位」的提升集中在近端**：误差 p25 降 65%，p75 只降 5%。
- **对小类动作无效**：`mouse_move` 0/16，模型一次都没预测过它。
- **微调让模型对 4-bit 量化变得鲁棒**（§2.3）：同样从 bf16 降到 4-bit，
  基座的动作类型准确率掉 34.5pp，微调后只掉 9.1pp。**这条对
  「8GB 显存能不能跑本地 GUI Agent」是直接相关的**——bf16 下的基座能力
  是个装不进显卡的数字，在装得下的配置里，微调的价值反而更大。
- **推理延迟的代价是 1.77 倍**（§5），不是曾经以为的 5 倍；
  其中 3.25 倍是显存卸载的产物，与微调无关。
- **8B 与微调 3B 在单步动作生成上几乎打平**（§10）：联合命中 @50
  30.3% vs 27.5%。两者强在不同地方——8B 坐标准（41.3 vs 118.4）
  但格式差（38.7% vs 97.9%）。**端到端那 5.6 倍不在单步能力上。**
- **§7 的 17% 是被污染的**（§10.8）：离线组 **64% 的动作**是在逐字背诵
  few-shot 示例里的坐标 `(470, 750)`，46 个子任务卡在那里跑满步数上限、
  烧掉 73% 的总步数。**那个数是模型能力的下界，不是它的水平。**
  修法几乎免费——微调模型格式合规已 97.9%，不需要 few-shot。
- **一个指标等于零，不代表那件事没发生**（§8.5 的更正）：`parrot_rate`
  在验证集上三档全 0%，实机上是 64%。**验证集恰恰是模型最熟悉的那批图，
  测不出「陌生时退回背例子」这种失败。**
- **本报告的单步指标系统性地高估微调 3B**（§10.4）：验证集是
  ScreenAgent 的留出划分，对微调 3B 是同分布，对 8B 是从没见过。
  去掉这个偏向需要真实桌面截图 + 人工标注的点击真值，本项目没有做。
- **微调在坐标上的优势完全依赖分辨率**（§9）：缩到 ×0.375 时，
  微调版与基座的坐标误差已经分不出谁好（423 vs 391）。而语义通道
  完全不受影响（动作类型 108/142 → 107/142）。**微调让「说什么」
  不吃分辨率了，但没让「指哪里」不吃。**

**这个结果与 M2 的实测互相印证。** M2 那 25 轮里模型的主要失败形态是
**不受输出约束**——零动作却报 `done`、输出动作空间外的 `type`。
本次微调恰好在这一维度上效果最好（格式合规 100%），
而在「看懂具体界面」这一维度上效果有限。**问题出在哪，微调就补在哪。**

**端到端实测（§7）验证了上面每一条，也修正了一条。**

验证了的：格式确实是当时的主要卡点——离线-基座在真实任务上 0/25，
失败机制正是输出不合规导致动作发不出去；微调后同一套系统拿到 4/24。

修正了的：§2 的「联合命中率 30.3%」当时只是一个数字，现在知道它是
**决定哪些任务做得成的那个数**——单步任务能做（4/4），多步不能（0/20）。
一个验证集指标能这样对应到端到端表现，比它本身涨了多少更有说服力。

**提示词消融（§8）给「微调值多少」定了下界。**

在此之前，「微调把格式合规从 2.1% 拉到 100%」这句话缺一个对照——
也许换个提示词就能拿到大半。现在知道不能：同一个基座，提示词工程
做满只有 **6.3%**。**微调的 100% 里，提示词能解释的部分不到十五分之一。**

同一节还记了一次方法论错误：用 `--limit 20` 探路，而 `val.jsonl` 按
session 排序，切前缀只覆盖 6 个会话，把 few-shot 的效果放大了约 15 倍
（25% vs 真值 4.9%）——**并且配了一个 p=0.047 的显著性检验**。
检验没错，错的是送进去的样本。已修并加了回归测试（§8.4）。

### 还不能下的三个结论

1. **不能说「微调无效」。** 0% → 17% 是真实提升，且机制可归因。
2. **不能说「微调够用」。** 96% 对 17%，离线版在这五个任务上不具备可用性。
3. **不能说「离线路线不可行」，但也不能把账算在模型体量上。**
   本项目只测了 3B——那是 8GB 显存能装下的最大尺寸（4-bit 实测已占
   7.7/8.1GB，7B 约需 10GB）。

   ⚠️ 这一条原本写的是「8B 走 API 时是 96%，**说明模型体量而非架构是
   瓶颈**」。**§10 推翻了后半句**：同一批验证集上 8B 的联合命中只比
   微调 3B 高 2.8pp（30.3% vs 27.5%），而端到端差 5.6 倍。
   那 5.6 倍在**拆解粒度**与**每子任务的收敛能力**上，换更大的模型
   买不到（§10.5）。

   所以离线路线的问题**不主要是模型不够大**。这也是不去租 GPU 部署
   7B/8B 的理由（§10.7）。

## 12. 遗留与后续

1. ~~**延迟需要重测**~~ **已完成（2026-08-25）。** before / after 均用
   `--load-4bit` 重跑，结论：**1.77 倍**，见 §5。重测还顺带暴露出
   §2.1 的主结果表用的是一个从没部署过的配置，由此产生了 §2.2、§2.3
   两节——**其中量化鲁棒性那条是本次重测最有价值的发现，且不在原计划里。**
2. **`mouse_move` 的失败值得一次针对性实验**：按类别加权采样或过采样
   小类，看能否救回来。**这是超出大纲的探索，时间不够可不做。**
3. **`double_click` 的 n=16 太小**，结论强度有限。扩大验证集需要更多
   ScreenAgent 会话，而那会动到冻结划分，不建议为此重新划分。
4. ~~**本次未做提示词工程消融**（大纲 W5 任务 4）~~ **已完成，见 §8。**
   §3.1 提的假设——「基座的很多错误其实是格式问题，带 few-shot 的提示词
   可能不必微调就能拿到相当一部分提升」——**被否定**：提示词工程做满是
   6.3%，微调是 100%。判断「是格式问题」对了，判断「提示词修得动」错了。

   同时记下的那条反向担心（3B 逐字照抄 few-shot 示例、吐出常数坐标
   `(470, 750)`）**本轮未复现**，三档 `parrot_rate` 全是 0.0%。指标保留。

5. ~~**图像分辨率可能是被忽略的一个变量。**~~ **已做，见 §9，且结论
   与原计划相反。** 原来提的「升到 1536×1152」**已撤回**：本次只证明了
   偏离 1024×768 **往下**走很贵，对**往上**走一无所知，而往上走还会破坏
   训练与推理同构。

   改为**把客机屏幕调到 1024×768**（§9.6）——不缩也不压，`resize()` 整步
   跳过。免费、安全、直接测那个假设。**留给 M4 的端到端复跑验证。**

   （先前写的「2560×1600 → 1280×800」有两处错：客机实际是 **1920×1080**
   （2560×1600 是宿主机的），而 1280×800 是 16:10，解决不了 33% 的横向
   形变。两处均由 2026-08-25 的轨迹探针查出。）

6. **去掉 few-shot 之后重跑离线-微调 25 轮。** §10.8 表明 §7 的 17% 被
   提示词污染了 64% 的动作。改一行 `executor_template`（`executor_v1`
   → `executor_v0`）即可，重跑约两小时。

   **重跑时不要同时改分辨率。** 客机现已改为 1024×768（先前 243 条轨迹
   全部是 1920×1080），两个变量一起变就无法归因。分辨率的效果 §9 已量过
   一部分，提示词的效果一点都没量过——**先只换提示词，拿到干净的对比，
   分辨率作为下一轮。**

7. **系统里没有任何机制能发现「Agent 在原地打转」。** §10.8：46 个子任务
   每一步点同一个坐标、一直点到 `max_steps`，执行状态全是 `ok`。
   **这是 M4 任务 2 必须补的第一件事**，而且比「加重试次数」优先——
   离线组每 4 步才产生 1 个新尝试，加次数只是把同一个错误多做几遍。

8. **任务拆解是新暴露出来的瓶颈，且没有专门的实验。** §10.5 显示
   3B 的拆解粒度全面偏粗，`send_message` 上把一个 5 步任务拆成 1 个
   子任务、烧掉 12 步。**这项能力我们从没单独评测过**——`agent/planner.py`
   只有单元测试，没有「拆得对不对」的量化指标。

   **这直接指向 M4 任务 1（复杂任务的自动拆解与分步执行）。** 做之前
   需要先有一个拆解质量的判据，否则又是「改了但说不清改好没有」。

9. **真实桌面截图上没有任何带真值的评测。** §10.4 指出本报告所有单步
   指标都在 ScreenAgent 留出集上，那对微调 3B 是**同分布**、对 8B 是
   从没见过——**系统性地偏向 3B**。

   要去掉这个偏向，需要一批客机截图 + 人工标注的点击真值（30-50 条
   就够看出方向）。**这是本报告最大的一块空白**，而且它会同时验证
   §9.6 那个「客机降到 1280×800」的推论。

10. **只试过一组 LoRA 超参，一次都没调过。** `r=16 / alpha=32 /
   dropout=0.05 / lr=1e-4 / 2 epoch` 是照里程碑文档抄下来的常量，
   前三个连命令行开关都没有（`finetune/train_lora.py:81`）。
   `finetune/outputs/` 下只有一次训练。

   **这不是对大纲的缺口**（W5 任务 2 要的是「实现 LoRA 微调」，不是调优），
   **但它是对结论的一条真实限制**：报告说「LoRA 在输出规范上极其有效、
   在坐标上有限」，而我们只试了参数空间里的**一个点**。

   优先级不高。§9 表明分辨率一个变量就值 2 倍坐标误差，而 543 条样本上
   调秩通常只值几个百分点——**数据量才是绑住手脚的那个**
   （`mouse_move` 59 条、`double_click` 72 条）。真要做，按性价比排：
   按类别加权采样（第 2 条）> `r=32` + 更多 epoch > 学习率扫。
