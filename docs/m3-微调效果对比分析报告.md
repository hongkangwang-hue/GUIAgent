# M3 微调效果对比分析报告

> 对应大纲 W5 任务 3「对比微调前后模型在 GUI 任务理解与动作生成上的效果」
> 与交付物「微调后的模型权重 + 微调效果对比分析报告」。
> 全部数据为本机实测，原始记录在 `docs/m3-action/`。撰写日期 2026-08-24。

---

## 摘要

对 Qwen2.5-VL-3B-Instruct 做了一次 QLoRA 微调（543 条训练样本，2 epoch，
136 步），在同分布的 142 条验证集上对比微调前后的动作生成能力。

**主结果：**

| 指标 | 微调前 | 微调后 | |
|---|---|---|---|
| 输出格式合规率 | 2.1% | **100.0%** | ▲ 97.9pp |
| 动作类型准确率 | 41.5% | **85.2%** | ▲ 43.7pp |
| 坐标误差中位数 | 227.7 | **143.4** | ▼ 37% |
| 联合命中率 @ r=50 | 2.8% | **30.3%** | ▲ 10.8× |

**但这四个数字里有两个需要打折看**，见 §3。诚实的结论是：

1. **格式学得彻底。** 142 条输出全部合规，这一项没有水分。
2. **动作类型的提升被高估了。** 43.7pp 里有约 25pp 来自「命名对齐」而非
   语义理解——基座模型输出 `click` 43 次，语义正确但不是动作空间里的词。
   按语义算，提升是 66.2% → 85.2%（+19pp）。
3. **坐标提升是真的，但只在「本来就接近」的样本上。** 误差 p25 从 116
   降到 41，而 p75 从 405 只降到 383——**近的变得很准，远的没救回来。**
4. **有一类动作完全没学会。** `mouse_move` 16 条全错，模型一次都没预测过它。

### 端到端：这些数字在真实任务上值多少（§7）

验证集回答「模型学会了吗」，回答不了「学会了有用吗」。把三档模型接进
完整 Agent、在 M2 的 5 个基础任务上各跑 25 轮：

| | 在线 8B（API） | 离线-基座 3B | 离线-微调 3B |
|---|---|---|---|
| 任务成功率 | **24/25 = 96%** | **0/25 = 0%** | **4/24 = 17%** |
| 其中「关闭应用」 | 5/5 | 0/5 | **4/4** |

**微调把离线版从 0% 抬到 17%，增量全部来自唯一的单步任务。** 机制可归因：

- 格式合规 2.1%→100% 让动作**能被执行**——B 组连一次有效点击都发不出去
- 但单次点击的联合命中率只有 30.3%，需要连点 3-4 处的任务在概率上做不成
  （0.3³ ≈ 2.7%，与实测的 0/5 对得上）

一句话：**微调修好了「能不能动手」，没修好「准不准」。**
瓶颈既不在格式也不在任务理解（3B 的任务拆解完全合格），而在坐标精度。

## 1. 实验设置

| 项 | 值 |
|---|---|
| 基座模型 | `Qwen/Qwen2.5-VL-3B-Instruct` |
| 微调方法 | QLoRA（4-bit NF4 + LoRA） |
| LoRA 配置 | `r=16, alpha=32, dropout=0.05`，挂在 q/k/v/o/gate/up/down proj |
| 可训练参数 | **37,152,768 / 2,071,177,216 = 1.79%** |
| 训练集 | 543 条（ScreenAgent，冻结划分指纹 `f1d58b429c13cb30`） |
| 验证集 | 142 条（同划分，会话级切分，与训练集无截图重叠） |
| 超参 | batch 1 + 梯度累积 8，lr 1e-4，cosine，warmup 4 步，2 epoch |
| 精度 | bf16（RTX 5060 Laptop，Blackwell sm_120） |
| `max_pixels` | 802,816（896×896；数据集原生 1024×768=786,432，几乎不压缩） |
| 硬件 | RTX 5060 Laptop，8151 MiB |

### 训练实测

| 项 | 值 |
|---|---|
| 总步数 | 136（543 ÷ 梯度累积 8 × 2 epoch） |
| 训练耗时 | **5886.7s = 98 分钟** |
| **峰值显存** | **7096.6 MB**（占 8151 MiB 的 **87%**） |
| loss | **0.8069 → 0.4987**（降 38%） |
| adapter 大小 | 148 MB |

> **8GB 显存能不能微调 3B 多模态模型？** 能，但没有余量。7096.6MB 是
> `torch.cuda.max_memory_allocated()` 的读数，**只统计 torch 分配的部分**，
> 不含 CUDA 上下文与显存碎片，真实占用还要再高 500MB–1GB。训练期间
> 开一个浏览器就可能 OOM。这是本项目对「推荐 8GB 以上显存」这条
> 技术栈要求的一手回答。

### 任务定义

一条样本给「截图 + 任务目标」，模型输出「动作类型 + 坐标」：

```
输入：截图 + "Find relevant information about von Neumann on the Internet"
输出：{"action": "left_click", "x": 475, "y": 251}
```

坐标归一化到 [0,1000)，与 `SessionConfig.coordinate_space` 一致。
输出格式与 `ActionIntent` 的解析路径完全相同——**训练与推理同构**。

动作分布（训练集）：`left_click` 75.9% / `double_click` 13.3% /
`mouse_move` 10.8%。**类别极不均衡**，这是真实 GUI 轨迹的固有特征。

### 评测口径

不设单一「成功率」。动作生成只有一个真值坐标点，**「差多少算对」是人定的**，
所以分开报三组：

- **输出格式合规率** —— 合法 JSON + 动作在允许集合内 + 整数 x/y。无歧义。
- **动作类型准确率** —— 无歧义。
- **坐标误差** —— 报中位数与分位数，**不设阈值**。
- **联合命中率 @ r** —— 动作类型对且坐标在 r 内，**r 显式给出且同时报三个**。

最后一条是吸取 M2 的教训：稳定性测试里句柄斜率 +9.9 而阈值定在 10.0，
差 0.1 就翻转结论。**能随阈值变号的数字不该当结论。**

## 3. 三项必须打折的解读

**报告最有价值的部分在这一节。** 上面那张表如果直接拿去写简历，
有两处会站不住脚。

### 3.1 动作类型的 43.7pp 里，约 25pp 是「命名对齐」而非语义理解

基座模型的预测分布：

```
left_click 76 / click 43 / type 12 / terminate 5 / (空) 3 / right_click 2 / key 1
```

**它输出 `click` 43 次**——语义完全正确（那 43 条里 35 条真值就是
`left_click`），只是没用动作空间里的那个词。系统提示词明确列了
`left_click / double_click / right_click / mouse_move` 四个动作，
它仍然自造了 `click`、`type`、`terminate`、`key`。

把 `click` 按 `left_click` 计入：

| | 严格 | 把 `click` 算作 `left_click` |
|---|---|---|
| before | 41.5% | **66.2%** |

所以**语义层面的真实提升是 66.2% → 85.2%（+19pp）**，不是 +43.7pp。

> 这不意味着 41.5% 那个数字造假——**动作名不对就是执行不了**，
> `ActionIntent` 解析出 `click` 会直接被动作白名单拦下。
> 但报告里必须两个数都给，否则读的人会以为微调让模型的**语义判断**
> 提升了一倍，而实际上大半是**输出规范**。

### 3.2 85.2% 要跟「永远输出 left_click」比，不是跟 0 比

验证集里 `left_click` 占 110/142 = **77.5%**。一个什么都不做、
永远输出 `left_click` 的模型能拿 77.5%。

| | 类型准确率 |
|---|---|
| 多数类基线（永远 `left_click`） | 77.5% |
| **after** | **85.2%** |
| 超出部分 | **+7.7pp** |

那 7.7pp 全部来自 `double_click`：**16 条里预测对 15 条**。
微调确实教会了模型区分单击与双击，但这是在一个小类（n=16）上的结论，
**置信区间很宽**。

而 before 的 41.5% **低于多数类基线**——原因就是 §3.1 的命名问题。

### 3.3 `mouse_move` 完全没学会

16 条真值 `mouse_move`，**模型一次都没预测过这个动作**：

```
after 对这 16 条的预测：left_click 14 次 / double_click 2 次
```

而且坐标误差**从 338.3 涨到 423.8**——比微调前更差。

原因是类别不均衡：`mouse_move` 在训练集里只占 10.8%（74/543），
LoRA 在 136 步内塌缩到了两个多数类。

**这是一个诚实的负面结果**，也说明「85.2%」这个总数掩盖了一整类动作
的完全失败——正是 §1 那条「按动作类型分开报」的价值所在。

---

## 4. 坐标：近的变准了，远的没救回来

分位数比中位数更能说明发生了什么：

| | p25 | p50 | p75 |
|---|---:|---:|---:|
| before | 116 | 228 | 405 |
| after | **41**（▼65%） | **143**（▼37%） | 383（▼5%） |

**p25 降了 65%，p75 只降了 5%。**

读法：微调把**本来就大致找对区域**的那批样本，从「差不多」推到了「相当准」
（41 在归一化 1000 空间里约等于屏幕宽度的 4%，1920 宽的屏上约 79px，
差不多一个按钮的尺度）。但**本来就完全找错地方**的那批，几乎没有改善。

这符合直觉：543 条样本能教会模型「这类任务通常点界面的哪个区域」，
教不会它「读懂这个具体界面上的这个具体控件」。后者需要的数据量是
另一个量级。

`double_click` 那一档最亮眼——**误差中位数 32.4，16 条里 10 条落在 r=50 内**。
但 n=16，不宜过度解读。

## 5. 延迟：本次数据不可用于比较

| | 中位延迟 |
|---|---|
| before | 4,674 ms |
| after | 23,470 ms |

**不要把这解读为「微调让模型慢了 5 倍」。** 这是评测配置的产物：

评测用 **bf16 全精度**加载（约 6.2GB 权重），而显卡可用显存不足，
`device_map="auto"` 把一部分层卸载到内存，每次前向都要在 CPU↔GPU 之间
搬运数据。加上 adapter 后占用更高，被卸载的层更多，于是慢得更明显。

日志里的原话：

```
Some parameters are on the meta device because they were offloaded to the cpu.
```

**这是本报告的一处方法论缺陷**：训练用 4-bit NF4，评测却用 bf16，
两者没有对齐。已在 `eval/action.py` 补上 `--load-4bit`，
但**本轮的 before 基线已按 bf16 跑完**——同一组对比里前后必须用同一种
加载方式，中途改会把量化的影响混进差值。

因此本报告**不给出延迟结论**。要测真实推理延迟，需要 before / after
都用 `--load-4bit` 重跑一次。

## 6. 一个方法论插曲：口径搞错了会让数据「看起来不够」

本里程碑原先把微调目标定为 **grounding（元素描述 → 坐标）**，
指标定为 ScreenSpot 命中率。按那个口径，训练数据严重不足——
ScreenAgent 只能提供 569 条，而 569 条里只有 **135 个不重复的描述**，
「Insert a circle」出现 17 次对应 **17 个不同的坐标**。

**对 grounding 而言那是矛盾监督**：同一个输入对应多个互斥的正确答案。
当时的结论是「必须补充 2400 条数据」，并规划了三路补数据方案
（UIA 自建 / OS-Atlas / ScreenAgent 全量）。

对照大纲后发现口径本身就错了。大纲 W5 任务 3 的原文是：

> 对比微调前后模型在 **GUI 任务理解与动作生成** 上的效果

而 ScreenAgent 提供的正是「截图 + 任务目标 → 动作坐标」三元组——
**恰好是动作生成**。是我们把目标窄化成 grounding 之后，数据才变得不匹配。

改回大纲口径后，同样这 543 条立刻够用，补数据方案全部作废，
而且训练出了本报告的结果。

> **教训：数据与指标不匹配时，先怀疑指标是不是自己改的，
> 而不是先去找更多数据。**

## 7. 端到端：微调在真实桌面任务上值多少

前六节全部基于**验证集**——同分布的 142 条 ScreenAgent 样本。它回答的是
「模型学会了吗」，回答不了「学会了有用吗」。

本节把三档模型接进完整的 Agent 系统，在 M2 的 5 个基础任务上各跑 25 轮，
用**程序化判定**（查进程 / 窗口 / 文件）算成功率。撰写日期 2026-08-25。

### 7.1 三组的差别只有一处

| 组 | 规划模型 | 部署方式 | 数据边界 |
|---|---|---|---|
| **A 在线** | qwen3-vl-8b-instruct | 阿里云百炼 API | 截图上传平台服务器 |
| **B 离线-基座** | Qwen2.5-VL-3B-Instruct | 宿主机 GPU，客机经 HTTP 调 | 截图不出本机 |
| **C 离线-微调** | 同上 + 本次的 LoRA adapter | 同上 | 截图不出本机 |

同一个脚本、同一份任务清单、同一套提示词、同一个坐标空间。B 与 C 之间
**只差一个 adapter**，A 与 C 之间只差模型与部署位置。

> 拓扑说明：GPU 在宿主机、客机无直通，而全局约束要求键鼠执行只发生在
> 客机内，两条约束逼出「宿主机跑权重、客机 HTTP 调用」这个结构。
> 宿主机与客机是同一台物理机（VMware NAT / VMnet8），**这条 HTTP 不出本机**，
> 仍属大纲 W3 的「本地部署」。见 `milestone-0-overview.md`。

### 7.2 主结果

| 任务 | A 在线 8B | B 离线-基座 3B | C 离线-微调 3B |
|---|---|---|---|
| 打开浏览器 | 5/5 | 0/5 | 0/5 |
| 搜索指定内容 | 4/5 | 0/5 | 0/5 |
| 打开指定文件 | 5/5 | 0/5 | 0/5 |
| 发送消息 | 5/5 | 0/5 | 0/5 |
| **关闭应用** | 5/5 | **0/5** | **4/4** |
| **合计** | **24/25 = 96%** | **0/25 = 0%** | **4/24 = 17%** |

**微调把离线版从 0% 抬到 17%，全部增量来自「关闭应用」一个任务。**

其余指标：

| | A 在线 | B 基座 | C 微调 |
|---|---|---|---|
| 平均步数 | 11.8 | 9.6 | 12.6 |
| 平均每轮耗时 | 37.4s | 274.9s | 415.4s |
| 每步模型延迟 | 1553ms | 25280ms | 30005ms |
| API 费用 | 未配单价，**未知** | 0（确认值） | 0（确认值） |

> 成本一栏的两种 0 必须分开：离线版的 API 费用是**查证过的 0**，在线版
> 显示 0 是因为没配单价、属于**未知**。拿确认的 0 去比未知的 0 得不出
> 「离线更省」——何况离线版每轮多花 6-11 倍的时间，成本只是换了形态。

### 7.3 为什么偏偏是「关闭应用」

因为它**只需要点对一次**（关闭按钮），而其余四个任务要连着点对 3-4 处。

用 §2 的联合命中率 30.3% 做个粗算：

| 任务需要连点几处 | 单轮成功的粗略概率 |
|---|---|
| 1 处 | 30%，而 Loop 有 6 步重试机会 ⇒ 接近 90% |
| 3 处 | 0.3³ ≈ **2.7%** |

**实测的 4/4 与 0/5 与这个量级对得上。** 这也说明验证集上那个
「联合命中 30.3%」不是一个抽象指标——它直接决定了哪些任务做得成。

因此本节的结论不是「微调有效/无效」，而是更具体的一句：

> **微调修好了「能不能动手」，没修好「准不准」。**
> 单步任务因此从不可能变成可行，多步任务仍受限于坐标精度。

### 7.4 两个方向都不可信的自我判断

C 组「关闭应用」的 4 次成功里，**有 3 次是跑满 6 步、模型自报「没做完」**：

| 轮次 | 判定 | 步数 | 模型自报完成 |
|---|---|---|---|
| 第 2 次 | ✓ | 6（上限） | **False** |
| 第 3 次 | ✓ | 6（上限） | **False** |
| 第 4 次 | ✓ | 3 | True |
| 第 5 次 | ✓ | 6（上限） | **False** |

**它把计算器关掉了，自己却不知道**，于是继续操作到步数上限。

反方向也有：C 组另有 **3 轮「模型自报完成但判定未通过」**（全部是
「打开指定文件」）。而 B 组一次都没自报过完成——它连动作都发不出去。

| 组 | 自报完成但没做成 | 做成了却不自报 |
|---|---|---|
| A 在线 | 0 | 打开指定文件 3/5（M2 报告 §10 已记） |
| B 基座 | 0 | 0（一次都没做成） |
| C 微调 | **3** | **3** |

**模型的自我判断在两个方向上都不可信**，而这正是不能用模型自报当成功
判据的直接证据——M2 定的「程序化判定」在这里兑现了价值。这批数据是
M4（大纲 W6「错误检测与自动重试」）的一手素材。

### 7.5 这一节数据的四条限制

1. **与验证集的数不能互推。** 走 HTTP 时截图经 JPEG q85 压缩，
   而 `eval/action.py --local` 是无损的。85.2% 与 17% 之间没有换算关系。
2. **C 组有 1 轮无效**（关闭应用第 1 次，起点未建立），分母因此是 24 而非 25。
   原因是 reset 里 `taskkill` 之后只等 3 秒，而 UWP 计算器冷启动更久。
   已改为轮询（`tasks/wait_for_process.py`），但**本次数据保持原样**。
3. **A 组的 5 轮「发送消息」无效**（模拟消息程序未启动），已补跑，
   两份存档合并统计。
4. **B 组另有一次整体作废的运行**（`20260824-223451`）：客户端超时 90 秒
   而本机生成 1024 token 需 140 秒，25 轮里 15 轮连规划都没完成。
   **存档保留作为缺陷证据，不进本表。** 修复见 `serve_local_model.py`
   的生成上限与 `llm/factory.py` 的本地超时。

### 7.6 复现

```bash
python scripts/compare_runs.py \
    --arm "在线 8B=online,online-send" \
    --arm "离线-基座 3B=base" \
    --arm "离线-微调 3B=lora" \
```

## 8. 结论

**大纲 W5 的三项要求均已完成：**

1. ✅ 基于预处理后的公开 GUI 数据集构建了训练集与验证集（543 / 142，
   会话级切分，指纹冻结）
2. ✅ 用 PEFT 完成 LoRA 微调，产出 adapter 权重（148 MB）
3. ✅ 对比了微调前后在 GUI 任务理解与动作生成上的效果

**能站住的结论：**

- **小样本 LoRA 对「输出规范」极其有效**：543 条、136 步、1.79% 的参数，
  把格式合规率从 2.1% 拉到 100%。
- **对「语义判断」有中等提升**：动作类型 66.2% → 85.2%（按语义口径），
  超出多数类基线 7.7pp，主要贡献来自学会了 `double_click`。
- **对「空间定位」的提升集中在近端**：误差 p25 降 65%，p75 只降 5%。
- **对小类动作无效**：`mouse_move` 0/16，模型一次都没预测过它。

**这个结果与 M2 的实测互相印证。** M2 那 25 轮里模型的主要失败形态是
**不受输出约束**——零动作却报 `done`、输出动作空间外的 `type`。
本次微调恰好在这一维度上效果最好（格式合规 100%），
而在「看懂具体界面」这一维度上效果有限。**问题出在哪，微调就补在哪。**

**端到端实测（§7）验证了上面每一条，也修正了一条。**

验证了的：格式确实是当时的主要卡点——离线-基座在真实任务上 0/25，
失败机制正是输出不合规导致动作发不出去；微调后同一套系统拿到 4/24。

修正了的：§2 的「联合命中率 30.3%」当时只是一个数字，现在知道它是
**决定哪些任务做得成的那个数**——单步任务能做（4/4），多步不能（0/20）。
一个验证集指标能这样对应到端到端表现，比它本身涨了多少更有说服力。

### 还不能下的三个结论

1. **不能说「微调无效」。** 0% → 17% 是真实提升，且机制可归因。
2. **不能说「微调够用」。** 96% 对 17%，离线版在这五个任务上不具备可用性。
3. **不能说「离线路线不可行」。** 本项目只测了 3B——那是 8GB 显存能装下的
   最大尺寸。8B 走 API 时是 96%，说明模型体量而非架构是瓶颈。
   本机跑 8B 需要约 12-16GB 显存（3B 4-bit 实测已占 7.7/8.1GB），
   超出本项目的硬件条件。

## 9. 遗留与后续

1. **延迟需要重测**：before / after 都用 `--load-4bit` 重跑，才能给出
   可比的推理延迟（见 §5）。
2. **`mouse_move` 的失败值得一次针对性实验**：按类别加权采样或过采样
   小类，看能否救回来。**这是超出大纲的探索，时间不够可不做。**
3. **`double_click` 的 n=16 太小**，结论强度有限。扩大验证集需要更多
   ScreenAgent 会话，而那会动到冻结划分，不建议为此重新划分。
4. **本次未做提示词工程消融**（大纲 W5 任务 4），属 M3 的下一步。
   §3.1 的发现给它一个具体假设：**基座模型的很多「错误」其实是格式问题，
   一个带 few-shot 示例的提示词可能不必微调就能拿到相当一部分提升。**
   这个对照做出来，才说得清「微调 vs 提示词工程」各自值多少。

   端到端实测又给它添了一条**反向**证据：3B 会**逐字照抄 few-shot 示例**。
   2026-08-24 的探针里，四个目标问下来微调版抄了 2 个、基座版抄了 1 个，
   抄出来的坐标是示例里的常数 `(470, 750)`——**格式 100% 合规、位置全错**。
   去掉 few-shot 后两者都降到 0 个。消融要专门量这一项。

5. **图像分辨率可能是被忽略的一个变量。** 客机屏幕 2560×1600，送模型前
   缩到 1024×768（`SessionConfig.image_size`），**缩了 2.5 倍**——一个
   20 像素的按钮到模型眼里只剩 8 像素。而 processor 的 `max_pixels`
   上限是 896×896 ≈ 802k 像素，1024×768 = 786k，**根本没碰到上限**，
   所以真正的限制是我们自己设的 `image_size`。

   §7.3 已把瓶颈定位到坐标精度，而分辨率是影响坐标精度的一个**我们能控**
   的变量（模型体量不能）。用「历史帧数换分辨率」（3 张 1024×768 →
   1 张 1536×1152，显存相当）是一个不花钱、在本机就能做的对照。
   **若有效，则「离线版失败」的部分原因是送图缩太狠，而非 3B 不行——
   那是一个完全不同的结论。**
