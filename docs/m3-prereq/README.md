## ① 三分划定并冻结 —— 已完成，但结论是「不够」

### 冻结结果

由 `python scripts/prepare_datasets.py` 生成，写入 `split-screenagent-desktop.json`。

| 项 | 值 |
|---|---|
| grounding 可用池 | **716 条** |
| 训练集 | **569 条** / 149 个会话 |
| 验证集 | **147 条** / 43 个会话 |
| 随机种子 | `20260913` |
| 划分指纹 | `f1d58b429c13cb30` |
| 划分单位 | **会话**（session），不是样本 |

**核对方法**：`FrozenSplit.read()` 会按内容重算指纹并与文件里记的比对，
不符就拒绝载入。文件被人改过而指纹还对得上是最危险的情况，所以这个校验
不是可选项。

### 为什么按会话切而不是按样本切

ScreenAgent 的一个会话是一串连续操作，**同一张截图会被同一会话里的多条
标注引用**。按样本随机切分会让同一张截图同时出现在训练集和验证集里——
验证分数会虚高，而且高得看不出来。

代价是验证集条数不会正好等于目标值（实得 147 而非 143）。**宁可条数不整，
不可泄漏。**

### 缺口：目标 3000-4000，实得 569

大纲给 M3 定的训练集是 3000-4000 条。实测可用池只有 716 条，
按 8:2 切分后训练集 569 条——**缺口约 2400 条，差 5 倍多。**

缺口是怎么来的，逐层核对过：

| 层级 | 数量 | 说明 |
|---|---:|---|
| ScreenAgent train 划分的标注文件 | 3,005 | 其中 1,005 个是 RLHF 负样本（模型的**错误**回答） |
| 有效标注步 | 2,000 | 203 个会话，平均 9.9 步 |
| 步内的动作总数 | 3,073 | 一步可含多个动作 |
| ├ EvaluateSubTaskAction | 897 | 判定子任务是否完成，**无坐标** |
| ├ PlanAction | 884 | 自然语言元素描述，**无坐标** |
| ├ KeyboardAction | 470 | 输入 / 按键，**无坐标** |
| ├ WaitAction | 65 | **无坐标** |
| └ MouseAction | 757 | 其中 **716 个带 `mouse_position`** |
| **可作 grounding 监督的动作** | **716** | 就是这个数 |

也就是说，ScreenAgent 标注的是「规划-执行-评估」三段循环，
**只有约 23% 的动作携带坐标**。把 2000 步误当成 2000 条 grounding 样本，
是这一层最容易犯的错。

还有两个必须知道的细节：

- **`clickable_area`（元素边界框）只有 test 划分有。** 实测 test 的 218 个
  带落点鼠标动作全都有框，train 的 757 个鼠标动作**一个也没有**。
  ScreenAgent 能给训练的监督信号只有点，没有框。
- ScreenAgent 全部截图都是 **1024×768**，与本项目客机的 1920×1080 不同。

### 比条数更糟的是指令质量（复查时才发现）

716 这个数字还高估了它的价值。这批点击**配得上的指令只有整体任务目标**，
而且 716 条里只有 **169 条不重复**的任务目标：

| | |
|---|---|
| 池内样本 | 716 |
| 不重复指令 | **169** |
| 指令形态 | "Find relevant information about von Neumann on the Internet" |
| 指令来源 | 100% 是 `task_prompt`（整体任务目标） |

也就是说，模型看到的是「在网上查冯诺依曼的资料」配一个点击坐标——
**指令根本没有描述被点的那个元素**。这不是 grounding 该有的监督信号。

**为什么不用 `PlanAction.element`。** 数据集里确实有 1168 条标注者手写的
自然语言描述（"点击save"、"Choose the blue color from the color palette"），
一眼看去正是我们想要的。但实测确认它用不了：

1. **Plan 与 Mouse 从不在同一步。** ScreenAgent 的一步只有一种动作类型。
   716 个带坐标的鼠标动作里，**同一步内前方有 PlanAction 的是 0 个**。
2. **跨步去找也不行——Plan 描述的是另一张截图。** 典型会话：
   Plan 写在 `255913.jpg` 上，点击发生在 `140419.jpg` 上。
3. **中英混杂且无语言变体。** 1168 条里 73% 中文、27% 英文，
   而这个字段不像 `task_prompt` 那样有 `_en` / `_zh` 两套。

> 这一条是代码复查时才查出来的：装载器里原本写了「用 element 当指令、
> 取不到再回落到任务目标」的逻辑，**而那段代码从未执行过**——单元测试的
> fixture 把 Plan 和 Mouse 编在了同一步里，于是测试印证的是我自己的误解，
> 不是数据。已修正，并把 fixture 改成真实结构。

**结论：ScreenAgent 作为 grounding 训练来源，比条数看起来弱得多。**
这进一步加强了补充其他来源的必要性。那 1168 条 element 文本已保留在
`meta["plan_element"]` 里，留给前置件④当模式 B 的参考语料。

### 泄漏检查（大纲要求项）

| 左 | 右 | 共有截图 | 结论 |
|---|---|---:|---|
| ScreenAgent | ScreenSpot | **0** | 无泄漏，可放心用作训练来源 |
| ScreenAgent | ScreenSpot-v2 | **0** | 同上 |
| ScreenSpot | ScreenSpot-v2 | **586** | ⚠ 见下 |

**ScreenSpot 与 ScreenSpot-v2 之间高度重叠**：v1 的 610 张截图中有 586 张
（96.1%）也在 v2 里。839 对同图同指令的标注，bbox IoU 中位数 1.000、
均值 0.993。

**这意味着两者不能当成两个独立评测集来报告平均分**——那等于把同一批题
算了两遍。M5 的横评表里要么只用 v2（v1 的标注错误 v2 已修正），要么明确
标注两者不独立。

## 缺口怎么补：四条路，建议 4 + 3

大纲允许下调目标（任务 1：「若样本量不足，M3 的微调目标需在本周内下调并
记录」）。但在下调之前，先确认补足是不是真的做不到——查下来是**做得到的**。

### 先厘清「本项目只做 Windows」这条约束管到哪一层

M0 第 260 行把平台收窄为**仅保证 Windows 通路可用**（官方大纲的技术栈其实
写的是「支持 Windows、macOS、Linux」，收窄是我们自己的取舍）。

**这条约束管的是执行通路**——`perception/` 与 `control/` 只保证 Windows
（dxcam、uiautomation、pyautogui）。它**不约束训练数据的来源 OS**：
grounding 学的是「按一句描述在一张截图里找元素」，训练语料用哪个桌面环境
截的图，是建模选择，不是合规问题。

不过有一个数字比上面这段推理更有说服力——**我们的评测集本身就有一半不是
Windows**：

| 评测集 | Windows | macOS | 其他 |
|---|---:|---:|---:|
| ScreenSpot desktop | 162 | **172** | — |
| ScreenSpot-v2 desktop | 159 | **147** | 28 |

所以「必须用 Windows 数据训练」这个要求，从我们要报告的那张榜单上也推不
出来。**纯 Windows 训练同样是错配的。**

真正成立的担忧是另一件事：**我们最终部署的环境是 Windows 11 中文、
1920×1080，而上面没有任何一个语料匹配这个组合。** 这正是下面路 4 的动机。

### 路 1：下调目标到 ~700 条

最省事，大纲也允许。但 569 条训练 LoRA，效果大概率不足以支撑 M5 的
「微调前后对比」这一档结论——那会让 M3 最主要的产出变成一句
「样本太少所以没提升」。**不建议单独走这条。**

### 路 2：加上 ScreenAgent 的 test 划分

我们的零样本测试集是 ScreenSpot，不是 ScreenAgent test，所以把它并进训练
池在方法上是干净的，还能多出 218 条**带边界框**的样本。

池子变成约 934 条。**仍然不够**，但这 218 条框是 train 划分完全没有的
监督形态，值得并进来。

### 路 3：补 OS-Atlas 桌面子集

`OS-Copilot/OS-Atlas-data`（Apache-2.0）的 `desktop_domain/` 有
Windows / Linux / macOS 三套。已实测核对过：

| 项 | 值 |
|---|---|
| Linux 标注文件 | `linux_splited.json`，14.3MB |
| 记录数 | 9,671 组 |
| **不重复截图** | **1,186 张** |
| **元素标注总数** | **43,156 条** |
| bbox 格式 | **归一化 xyxy**，与 ScreenSpot v1 一致，装载器可复用 |
| 与 ScreenSpot(+v2) 截图重叠 | **0 张**（已实测） |
| 图片包 | `linux_images.zip` **3.1GB** |

**为什么不用 Windows 那一套**：`windows_image_*` 四个分片合计约 **71GB**，
且是 `split` 切开的单个压缩包，取不了子集。macOS 5.5GB、Linux 3.1GB。
在项目时间与带宽下 Linux 是唯一现实选择——**这是被迫的，不是选出来的**。

两个代价要写清：

- **Linux 桌面 ≠ 我们的部署环境。** 但见上文，评测集本身也不是。
- **1,186 张不重复截图**意味着场景多样性远低于 43,156 这个数字的观感。
  抽样必须**按截图分组**，不能按元素随机抽，否则同一张图的几十个元素会
  散落到训练与验证两侧——和 ① 里按会话切是同一个道理。

### 路 4（建议，且这条是本项目独有的）：用 UIA 自动生成 Windows 中文语料

**这是唯一能精确匹配部署环境的来源，而且我们已经有现成的代码。**

`perception/uia_tree.py` 遍历 Windows UI Automation 树，每个控件直接给出
`Name`（控件文本）、`BoundingRectangle`（**控件的真实边界**）、
`ControlTypeName`。也就是说，**客机里每截一张图，就自动得到几十条
(元素描述, 精确边界框) 配对**，不需要任何人工标注。

| 维度 | UIA 自建语料 | 公开语料 |
|---|---|---|
| 操作系统 | **Windows 11**，与部署环境一致 | Linux / macOS 混杂 |
| 语言 | **中文**，与部署环境一致 | 全英文 |
| 分辨率 | **1920×1080**，与客机一致 | 1024×768 / 各式各样 |
| 监督信号 | 框（控件真实边界） | ScreenAgent train 只有点 |
| 数量 | 受限于截图张数，可持续扩充 | 固定 |
| 许可与泄漏风险 | **无**（自产） | 需逐项核对 |
| 成本 | 近似为零 | 3.1GB 下载 |

**监督信号的形态也更贴合用途**：UIA 给的是控件的真实可点区域，而不是
文字外接框——`perception/types.py` 里记过这个区别（OCR 的文字框往往比可
点击区域小）。至于它和 ScreenSpot 人工标注的框谁更准，**我没有核对过，
不做断言**；能确定的只是 UIA 的框来自控件本身的几何定义，不依赖标注者
的判断。

**唯一的真问题：UIA 给的是控件名（「关闭」「新建标签页」），
不是任务式指令（"close this window"）。** 这个差距有多大，我量了一下
ScreenSpot desktop 的指令：

- 词数中位数 **3**，**69% 的指令不超过 3 词**
- 实际样例：`close`、`help menu`、`minimize calculator`、`open the gallery`

也就是说 ScreenSpot 的指令本身就基本是**控件名加一层很薄的动词包装**。
用模板（「点击 X」「打开 X」「关闭 X」）或让我们已经跑通的 API 模型改写
一遍，就能贴到目标分布上。**这比它看起来容易得多。**

三个必须遵守的前提：

1. **必须在客机里生成，不能在宿主机。** 宿主机截图会包含你的真实文件、
   浏览器标签、聊天窗口——那违反 M0 的数据边界约束，而且这批数据是要
   进训练集的。客机里只有测试软件，干净。
2. 只读不写：生成过程只截图 + 读 UI 树，**不点击任何东西**，所以不受
   M1 那套安全闸门的限制，也不需要急停。
3. UIA 会给出大量不可见 / 零尺寸 / 重叠控件，需要过滤——
   `data/clean.py` 现成的 `bbox_too_small`、`bbox_degenerate`、
   `bbox_out_of_bounds` 三条规则直接可用。

### 建议的最终方案：路 4 + 路 3 + 路 2

| 来源 | 量级 | 作用 |
|---|---|---|
| UIA 自建（Windows 中文 1920×1080） | 目标 2000-3000 条 | **与部署环境同分布**，主力 |
| OS-Atlas Linux 抽样 | 约 1000-1500 条 | 补场景多样性，防止只会认 Windows 控件 |
| ScreenAgent 全量（train + test） | 约 934 条 | 唯一含真实多步任务语境的来源 |

合计约 4000-5000 条，落在大纲的目标区间内。

保留三个来源而不是只取一个，除了凑量，还有一个实打实的好处：
**M5 可以据此做一组消融——同域小样本 / 跨域大样本 / 自建语料各自的贡献。**
这比单纯报一个「微调后涨了几个点」有价值得多，而且成本只是多切几次训练集。

> **以上都尚未执行。** 路 4 需要客机建好之后才能采集；路 3 需要确认 3.1GB
> 的下载与解压开销。执行前请先确认这个方案。

## ②③ 未开始（依赖 GPU 环境）

- **② LoRA 100-step smoke test** —— 依赖 GPU 环境。只验流程能否跑通
  （数据加载 → 前向 → 反向 → 存 checkpoint → 重新载入 adapter），
  不看效果、不调超参。
- **③ 3B 4-bit 真实分辨率单图推理 + 峰值显存实测** —— 依赖 GPU 环境。
  **必须用真实分辨率的桌面截图**（1920×1080 或 2560×1600），
  小图测不出动态分辨率下 2000+ 视觉 token 的激活开销。
### ④ 已完成 —— 结论：模式 B 可行

2026-08-23 实测（`qwen3-vl-8b-instruct`，30 条指令覆盖 8 张界面 + 5 次重复）：

| 指标 | 结果 |
|---|---|
| JSON 可解析率 | 35/35（100%） |
| `target_description` 字段完备率 | **29/29（100%）** |
| 明显含糊的描述 | 0/29 |
| 同一指令重复 5 次 | 输出**逐字一致** |
| 描述线索密度 | 2.31/4，**约为 ScreenAgent 人工语料（0.60）的 4 倍** |

**M3 按原计划实现 `LocalVLMGrounding`，不降级为「出坐标 + 复核纠偏」形态。**

完整报告见 [`../m2-mode-b-feasibility.md`](../m2-mode-b-feasibility.md)。

> 报告里记了一处统计口径的坑：第一版把模型输出 `{"done": true}` 的 6 次
> 算成「字段缺失」，得出 85.7% 的假数字——那 6 次是模型判断子任务已完成、
> 压根没选动作，**正确行为被算成了缺陷**。分母改为「确实选了需要指向
> 某元素的动作」之后才是 100%。

  顺带一提，① 的处理中发现 ScreenAgent 的 `PlanAction.element` 字段就是
  标注者手写的自然语言元素描述（train 884 条 + test 284 条 = **1,168 条**），
  形如 "the address bar"、"Locate line 2 in the Python script as indicated by
  the error message"。**这是现成的模式 B `target_description` 参考语料**，
  ④ 可以拿它当基准来判断规划模型输出的描述是否「具体到能定位」，
  而不是只凭主观判断。
