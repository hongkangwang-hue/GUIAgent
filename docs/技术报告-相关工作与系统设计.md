# 2 相关工作

## 2.1 两条技术路线：端到端原生 vs 模块化流水线

GUI 智能体的目标是让模型「看懂屏幕、操作电脑」。围绕这一目标，
现有工作分化为两条差别明显的路线。

**端到端原生路线**把感知、规划、定位、动作生成压进单个模型。
UI-TARS[1] 是这条路线的代表：它用大规模 GUI 轨迹数据训练一个原生
Agent 模型，输入截图、直接输出动作，中间不设显式模块边界。
CogAgent[2] 更早地展示了同类思路——用高分辨率视觉编码器专门处理
GUI 截图，让单一模型同时承担理解与定位。这条路线的优势是端到端优化、
没有模块间的信息损失；代价是训练成本极高，且模型内部不可分解，
出错时难以定位是「没看见」「看见了但判断错」还是「判断对了但点偏了」。

**模块化流水线路线**把上述能力拆成独立模块。ScreenAgent[3] 是典型：
它把一次交互显式划分为规划（Planning）、执行（Acting）、
反思（Reflecting）三个阶段，每阶段单独调用视觉语言模型，
阶段之间用结构化文本传递。Claude Computer Use 等商业方案在接口层面
也呈现类似结构——模型输出结构化的工具调用，由外部执行器落到真实键鼠。
这条路线的优势是每一步都可观测、可替换、可单独评测；代价是模块边界处
需要人为设计协议，且误差会跨模块累积。

**本项目采用模块化流水线**，理由有三：其一，八周周期与消费级硬件下
训练原生模型不现实；其二，本项目的核心研究问题——「通用大模型的语义
规划能力与专用小模型的像素定位能力能否分工」——本身要求两种能力可分离
地测量，端到端模型无法提供这种可分解性；其三，模块化结构使得每一步的
截图、思考、坐标、耗时、成本都能落盘，这是后续全部实验分析的数据基础。

## 2.2 GUI Grounding：从坐标回归到原生输出

「给定一句自然语言描述，在截图上指出对应元素的位置」——这一子问题被
称为 GUI grounding，是模块化路线的核心瓶颈。

SeeClick[4] 明确提出把 grounding 作为独立能力来训练与评测，
并发布了 **ScreenSpot** 基准。此后 OS-ATLAS[5] 通过大规模跨平台
GUI 数据训练基础动作模型，进一步把 grounding 精度推高，并发布了修正
标注错误的 ScreenSpot-v2。

与此同时，通用视觉语言模型开始内置定位能力。Qwen2.5-VL[6] 支持直接
输出边界框或点坐标，无需额外的 grounding 模块。这带来一个现实问题：
**在什么情况下值得单独部署一个 grounding 模型？**

这正是本项目要回答的问题，也是双模式架构的由来（见 §3.2）：

- **模式 A**：规划模型直接输出像素坐标（利用其原生 grounding）
- **模式 B**：规划模型只输出元素的自然语言描述，由本地微调的小模型负责定位

两种模式共用同一套 Agent Loop、同一批任务、同一个执行环境，
差异仅在「谁产出坐标」这一步，因而可以做受控对比。

> **一个必须警惕的坐标系陷阱。** 本项目在 M1 阶段实测发现：
> `qwen3-vl-8b-instruct` 输出的坐标是**按轴归一化到 [0, 1000) 的**，
> 与送入图像的实际尺寸无关。实验方法是给模型同一张截图但声明不同的
> 高度：声明 768 时得到的 y 为 968 / 968 / 970 / 963，声明 640 时为
> 973 / 967 / 967 / 970——**y 值不随声明尺寸变化**。
>
> 若把模型输出当作图像像素坐标直接使用，在 1024×768 的输入上会得到
> 「坐标越界」的假象，而在 1000×1000 附近的输入上则会得到看似正常
> 但系统性偏移的结果。**后者更危险，因为它不报错。**
> 本项目因此在数据结构上把「图像尺寸」与「模型作答坐标系」分成两个
> 独立字段（见 §3.3.2）。

## 2.3 界面感知：结构化通道与视觉通道

获取屏幕上有哪些元素，有两类互补手段。

**结构化通道**直接读取操作系统的可访问性接口。Windows 平台上是
UI Automation（UIA），它以树状结构暴露每个控件的名称、类型、
边界矩形。优势是坐标精确、语义明确、不受渲染样式影响；
局限是只对遵循可访问性规范的应用有效——自绘控件、Canvas 内容、
浏览器渲染的网页 DOM 往往读不到。

**视觉通道**用 OCR 与图像处理从像素中恢复元素。优势是不依赖应用配合，
任何能显示出来的东西原则上都能识别；局限是只能获得文字外接框
（不是可点击区域），且对图标、无文字控件无能为力。

多数工作只用其中一类：端到端路线依赖纯视觉，而部分自动化框架
（如 RPA 工具）依赖纯结构化。**本项目同时使用两条通道并做融合去重**，
这一选择在 M1 的实测中得到了支持，但结论方向与预期相反：

| 实测项 | 结果 |
|---|---|
| 双通道融合后召回率（点击点判据） | **100%**（5 张截图 / 50 个任务相关元素） |
| 命中来源分项 | **UIA 72% / OCR 28%** |

原本预期「无文字的图标按钮 OCR 必然漏检，会拉低召回」，
实测画图（Paint）工具栏的铅笔、橡皮擦、取色器等纯图标控件
**全部命中**——现代 XAML 应用的控件 `Name` 属性完整，UIA 能读到
语义名称。结论因此反转为：

> 图标类控件不是感知盲区，因为 UIA 覆盖了它们。
> 反过来说，**在不具备 UIA 的平台上降级为 OCR 单通道时，
> 这批无文字元素才会真正丢失**——双通道不是冗余，是覆盖互补。

## 2.4 评测基准与其局限

现有基准可分为两类。

**离线定位基准**给定截图与指令，评判模型输出的坐标是否落在目标元素内。
ScreenSpot[4] 与 ScreenSpot-v2[5] 属于此类，优点是完全可复现、
成本低、可精确归因到 grounding 能力。

**在线交互基准**在真实或仿真环境中执行完整任务，以任务完成度评分。
WebArena[7] 构建了可自托管的真实网站环境并提供程序化的功能正确性判定；
Mind2Web[8] 面向真实网页的通用智能体；OSWorld[9] 把范围扩展到真实
操作系统上的开放式任务。这类基准更接近实际能力，但环境搭建成本高、
运行慢、结果受环境状态漂移影响。

**本项目对基准的使用有三点需要事先声明。**

**其一，ScreenSpot 与 ScreenSpot-v2 高度重叠，不可当作两个独立评测集。**
本项目实测：v1 的 610 张截图中有 **586 张（96.1%）**也出现在 v2 中；
839 对同图同指令的标注，bbox IoU 中位数 1.000、均值 0.993。
在两者上分别评测后取平均，等于把同一批题算了两遍。

**其二，WebArena 与 Mind2Web 是网页数据，与本项目的桌面目标不对齐**，
因此只做抽样查看与方法论借鉴，不做深度处理。
其中 WebArena 的「程序化功能正确性判定」思路被本项目直接采用
（见 §3.5.3）。

**其三，自建任务集与公开基准不可直接比较。** 本项目的任务成功率
（M2 起产出）只能与自身的消融组对比；引用 UI-TARS 等的公开分数时，
仅作技术水平参照，不做同表并列。

## 2.5 参数高效微调

在消费级硬件上适配大模型，LoRA[10] 与其量化版本 QLoRA[11] 是标准做法：
冻结主干权重，只训练低秩旁路矩阵，显存与存储开销降低一到两个数量级。
本项目的 grounding 模型微调采用这一方案（M3 阶段执行）。

> **一个与部署方式相关的约束值得记录。** LoRA 产出的是 adapter 权重，
> 而公共 API 平台不接受用户上传自定义权重。这意味着**微调本身就强制了
> 本地部署**——这不是技术选型偏好，而是路线的必然结果。
> 它也构成了本项目「模式 B 必须本地化」这一设计的现实基础。

## 2.6 本项目的定位

综合上述，本项目在已有工作中的位置可概括为：

| 维度 | 已有工作 | 本项目 |
|---|---|---|
| 架构 | 端到端原生 / 模块化，二者独立发展 | 模块化，且**把 grounding 做成可切换的两种模式** |
| Grounding | 要么依赖通用模型原生能力，要么单独训练 | **同一任务集上受控对比二者**，含成本与延迟维度 |
| 感知 | 多为单通道 | UIA + OCR 双通道融合，**并实测两者的分工比例** |
| 模型 | 常含闭源商业模型 | **全部为开放权重模型**，grounding 层完全本地化 |
| 可复现性 | 部分工作环境难以重建 | 隔离虚拟机 + 快照 + 全轨迹落盘 |

需要诚实说明的是：本项目的规模远小于上述任一工作，
不追求刷新任何基准分数。其价值在于**在受控条件下把一个具体问题
测清楚**——通用大模型的原生 grounding 与本地专用小模型，
在真实桌面任务上各自的能力边界与成本结构。

# 3 系统设计

## 3.1 总体架构

系统分三层，层与层之间只通过明确定义的数据结构通信。

```
                   用户指令
                      │
      ┌───────────────▼───────────────┐
      │  编排层  agent/                │
      │  Planner 拆解 → 上下文窗口管理  │
      └───────────────┬───────────────┘
                      │  单个原子子任务
      ┌───────────────▼───────────────┐
      │  核心循环  core/loop.py        │
      │  截图→问模型→定位→执行→回传截图 │
      └───┬───────────┬───────────┬───┘
          │           │           │
   ┌──────▼─────┐ ┌───▼────┐ ┌────▼──────┐
   │ LLMBackend │ │Grounding│ │ 感知与控制 │
   │   llm/     │ │Backend  │ │perception/│
   │            │ │grounding│ │ control/  │
   └────────────┘ └─────────┘ └───────────┘
```

**分层的判据是「变化的理由是否相同」。** 换一个规划模型不应触碰坐标
换算；换一种定位方式不应触碰动作执行；改变上下文策略不应触碰任何
下层。这一约束在 M2 的验收标准中被显式检查（「新增一个模型后端或
grounding 实现不需要改动 Agent 层与 Loop 层」）。

## 3.2 双模式 grounding 架构（核心设计）

系统的核心设计是把「决定做什么」与「决定在哪里做」拆成两个可独立
替换的后端。

```python
class LLMBackend(ABC):      # 什么动作
    def complete(...) -> RawResponse: ...

class GroundingBackend(ABC):  # 在哪里
    def locate(screenshot, target_description) -> GroundingResult: ...
```

| | 模式 A | 模式 B |
|---|---|---|
| 规划模型输出 | `{action, x, y}` | `{action, target_description}` |
| 坐标来源 | 规划模型的原生 grounding | 本地微调的 3B 模型 |
| `GroundingBackend` 实现 | `NativeGrounding`（透传并校验） | `LocalVLMGrounding`（M3 实现） |
| 单步模型调用 | 1 次 | 2 次 |
| 截图出本机 | 是 | 规划层是，定位层否 |

**切换发生在单步内部**——在「拿到动作意图」与「执行动作」之间，
而不是工具层面的切换。这是本项目不使用 LangChain `AgentExecutor`
的直接原因之一（见 §3.5.1）。

### 3.2.1 为什么 `NativeGrounding` 不是空实现

模式 A 下规划模型已经给出了坐标，看似 grounding 层无事可做。
但本项目仍让它承担一项职责：**校验坐标是否落在声明的坐标系内**，
并在越界时给出结构化的拒绝理由（`missing_coordinates` /
`non_integer_coordinates` / `out_of_space`）。

这一设计源于一个真实缺陷。早期实现中，循环用「坐标字段是否缺失」
判断是否需要 grounding，于是当模型给出 `x=5000` 这类**越界但存在**
的坐标时，`needs_grounding` 为假，越界坐标被直接送去执行，
最终被安全白名单拦下并报成 `action_failed`——**根因（模型输出不合规）
就此丢失**，而那正是 grounding 层存在的意义。修正后的判据改为
「grounding 是否跑过并产出了可用的点」。

## 3.3 感知层设计

### 3.3.1 双通道融合与调度

`ElementDetector` 同时运行 UIA 与 OCR，按 IoU 去重后输出统一的
`UIElement` 列表，每个元素标注来源通道。

**调度方式的选择在真机上被推翻过一次，值得记录。**
初始设计把 OCR 放进工作线程、UIA 留在调用线程并行执行，依据是
「OCR 是慢的那个（几百毫秒），UIA 很快」，同时 UIA 留在原线程
可以绕开 COM 线程套间（apartment）的问题。

这一前提在实际部署环境中不成立。隔离客机无 GPU，CPU 推理的
PaddleOCR 单张耗时 **11.5 秒**，占满 4 个 vCPU，UIA 的跨进程 COM
调用因此被饿死。同一个设置页面的实测：

| 调度方式 | UIA 耗时 | UIA 抓到 | 是否截断 | 分项结论 |
|---|---:|---:|---|---|
| 并行（初始设计） | 8133 ms | 61 个 | 时间截断 | uia 37.5% / ocr 62.5% |
| **串行（UIA 先跑完）** | **228 ms** | **98 个** | 无 | **uia 72% / ocr 28%** |

并行节省的是 `min(uia, ocr) ≈ 228ms`，代价却是 UIA 遍历不完整——
而**分项结论因此完全反转**。若未发现此问题，报告会得出「OCR 是主力
通道」的错误结论。

最终方案是按用途分别配置：**离线图集采集用串行**（完整性优先），
**Agent 循环用并行**（延迟优先，且不做分项统计）。

### 3.3.2 统一坐标系统

**真实屏幕坐标与模型坐标之间的转换只允许经过 `CoordinateScaler`。**
任何模块自行换算都会在某个 DPI 缩放或某台显示器上错位，
且这类缺陷表现为「点偏了一点点」，极难定位。

设计要点有三。

**其一，坐标系按名字注册，而非硬编码单一目标。** 模式 B 下送规划
模型与送 grounding 模型的截图分辨率不同，加上模型的归一化坐标系，
三者必须同时存在且互不干扰。

**其二，「图像尺寸」与「模型作答坐标系」是两个独立字段。**
这是 §2.2 中那个陷阱的直接对策：

```python
image_size: tuple[int, int] = (1024, 768)        # 实际送出去的图多大
coordinate_space: tuple[int, int] = (1000, 1000)  # 模型在哪个坐标系作答
```

**其三，往返误差有可计算的上界，而非写死的常数。**
一个模型像素覆盖 `1/sx` 个真实像素，四舍五入最多丢掉其中一半，
因此上界是 `0.5/sx`。验收标准中的「往返误差不超过 2px」对照该方法的
返回值检查，换分辨率时不会悄悄失效。

**实测结果**（客机 1920×1080，坐标系 1024×768，往返上界 0.94px）：

| DPI 缩放 | 12 个目标点的最大偏差 |
|---|---|
| 100% | **0.0 px** |
| 125% | **0.0 px** |
| 150% | **0.0 px** |

### 3.3.3 DPI 感知必须在任何截图之前声明

未声明 DPI 感知时，Windows 会对进程返回逻辑像素：在 150% 缩放的
2560×1600 屏幕上，`GetSystemMetrics` 返回 1707×1067，而截图拿到的
是 2560×1600。二者不一致会让每一次点击都按比例偏移。

本项目在 `ScreenCapturer` 实例化时即调用
`SetProcessDpiAwarenessContext(-4)`（per-monitor V2）。
此外，读取当前缩放必须用 `GetDpiForMonitor` 而非 `GetDpiForSystem`
——后者是会话级值，用户改了缩放但未注销时它仍返回旧值。

> 这一条同样是踩坑得来的：M1 早期的验证脚本在启用 DPI 感知之前就
> 读取并记录了 DPI，导致一台 150% 的机器被记成 100%。若未发现，
> 三档 DPI 的验收记录将全部作废。

## 3.4 控制层与安全设计

### 3.4.1 动作空间

每个动作是一个带 JSON Schema 的结构化对象，Schema 直接复用为模型的
工具定义，不做二次映射。覆盖点击（左/右/双击）、移动、拖拽、
滚动、文本输入、按键组合、等待。

**中文输入不能用 `pyautogui.write()`。** 它只发送 ASCII 键码，
中文会**静默失败**——不报错、也不输入。本项目改走
`pyperclip` 写剪贴板 + `Ctrl+V`，并且**必须读回验证**：
`verify_control.py` 在写入后用 UIA 读取控件值比对，
仅凭动作返回成功不能作为通过依据。

### 3.4.2 三道刹车

| 机制 | 触发方式 | 实测 |
|---|---|---|
| 安全白名单 | 高危文本/命令模式匹配 | 拦下 `shutdown /s /t 0` |
| PyAutoGUI FAILSAFE | 鼠标移至屏幕角落 | `FAILSAFE=True, PAUSE=0.0s` |
| 全局热键急停 | `Ctrl+Alt+Q`（pynput） | **客机 271 ms**，宿主机 247 ms |

第三道是**在 Agent 正控制鼠标时**测的——验证脚本一边持续移动鼠标
一边等待热键，因为「空闲时能中断」不构成有效验证。

> 建客机前曾预判 `Ctrl+Alt` 是 VMware 释放输入焦点的默认前缀键、
> 热键可能到不了客机。**实测被推翻**：热键正常送达，延迟 271ms。
> 记录此事是因为它一度被写进操作文档并指导过验证流程。

### 3.4.3 两道刹车的设计冲突

坐标链验证需要测试屏幕四角，而屏幕四角正是 FAILSAFE 的触发点——
验收标准 3（三档 DPI 点击正确）与标准 7（FAILSAFE 有效）在此直接冲突。

解法是**把「验证坐标换算」与「验证鼠标真能移到那里」分开**：
角点用纯数学校验换算正确性，真正移动鼠标的目标点内缩一格。
两条验收要求因此都能满足，且各自测的仍是原本要测的东西。

## 3.5 Agent Loop 与轨迹

### 3.5.1 为什么不用 LangChain 的 Agent 抽象

框架选用 LangChain，但**只用其成熟且真正省事的部分**：
`ChatPromptTemplate`（提示词模板与 few-shot 组织，YAML 外置）、
`PydanticOutputParser`（结构化输出）、`ChatOpenAI` + 自定义
`base_url`（多模态消息构造）。

**Agent Loop 自己写**，约 150 行。三条理由：

1. **交互形态不匹配。** `AgentExecutor` 的循环是「文本进 → 工具调用
   → 文本结果回传」；GUI Agent 每轮的反馈是**图像**而非文本。
2. **轨迹日志需要循环内部的完全控制。** 单步记录的字段来自四个不同
   位置——模型响应、grounding 结果、执行结果、后置截图，
   回调接口够不到这些中间态。而轨迹是后续全部分析的唯一数据源。
3. **模式 A/B 的切换发生在单步内部**，不是工具层面的切换。

多模态消息走 OpenAI 兼容接口而非各家社区封装，理由是截图传递是主链路、
每步都要走，而社区封装对图像内容块的支持成熟度不一，不能赌。

### 3.5.2 停止条件

循环有八种结束原因，分开记录而非合并为「失败」：
`done` / `max_iterations` / `cost_limit` / `grounding_failed` /
`action_failed` / `emergency_stopped` / `backend_error` /
`parse_error` / `resolution_changed`。

开源规划模型在多步任务上会犯两类要命的错——原地打转与越走越偏，
因此步数上限与单任务成本熔断是必需的。**成本上限在单价未知时不熔断**，
而不是拿一个恒为 0 的成本去比上限：后者等于悄悄关掉了保护。

其中 `resolution_changed` 是为虚拟机环境专设的：每步截图后比对
截图尺寸与坐标系建立时的区域，不符即终止。虚拟机上分辨率可能被
「自动适应窗口」悄悄改掉，而这类错配不会崩溃，只会让每次点击
系统性偏移，看起来像「模型定位不准」。

### 3.5.3 轨迹落盘

每步记录：前后截图、模型思考、动作意图、**模型坐标与真实坐标两套**、
执行状态、四段延迟拆分（API / grounding / 执行 / 截图）、token、
成本、错误类型。轨迹级别还记录**运行环境**（分辨率、DPI、截图引擎）。

最后一项是为「M5 的报告要引用 M2 的成本与成功率作参照」这一需求
服务的：两次评测跨越三周半、中间会恢复无数次快照，
「两次跑在同一环境」若只靠人记得核对，那是个**假设**；
记进每条轨迹，它才是**可查证的事实**。

**成功判定必须程序化**——进程检查、窗口标题检查、文件内容检查，
不用人工目测。这一思路直接来自 WebArena[7] 的功能正确性评测方法。
模型自报 `done` 只表示循环正常收尾，不等于任务真的完成，
两者在数据结构上是分开的字段。

## 3.6 执行环境：隔离与可复现

### 3.6.1 Agent 运行在客机内，而非宿主机控制虚拟机

初始设计为「宿主机截取虚拟机画面、向虚拟机发送键鼠事件」。
该方案有三个致命问题，已修正为 Agent 整体运行在客机内：

| 问题 | 宿主机侧执行 | 客机内执行 |
|---|---|---|
| 「宿主机不受控制」的隔离要求 | 违反——被控制的正是宿主机的鼠标，移出虚拟机窗口即点到真实桌面 | 物理隔离 |
| UIA 识别通道 | 无法穿透虚拟机边界，宿主机只看得到一个不透明窗口 | 正常 |
| 程序化成功判定 | 宿主机查不到客机内的进程与文件 | 直接可用 |

微调后的本地 grounding 模型仍部署在宿主机或租用 GPU 上，
客机经 HTTP 调用其 OpenAI 兼容端点。权重在本地硬件上运行，
仍属本地部署，只是换了传输方式。

### 3.6.2 快照与结果盘分离

评测环境必须可重置：M2 要求每个任务运行 5 次，
若第三次的客机状态已与第一次不同，成功率不可比。
方案是从固定快照恢复。

**但恢复快照会连同实验结果一起回滚。** 轨迹日志是后续全部分析的
唯一数据源，丢一次等于白跑一轮。因此实验结果写入一块
**独立持久磁盘**（不参与快照回滚），与被回滚的系统盘分离：

```
restore eval-baseline → 运行 → 结果写 R: → restore → 下一次
```

相应地，快照必须在客机**关机状态**下拍摄：带内存状态的快照会恢复
「当时内存里以为的磁盘状态」，与不回滚的独立磁盘不一致，
可能导致文件系统损坏。

### 3.6.3 隔离边界的诚实表述

**虚拟机解决执行隔离，不解决数据隐私。** 规划层走云端 API，
意味着客机截图会离开本机。因此还需关闭虚拟机的共享剪贴板、
共享文件夹、拖放与 USB 自动连接——否则宿主机的剪贴板内容会进入
客机，随截图上传。网络使用 NAT 而非桥接，客机无需成为局域网中的
独立设备。

> **本项目实际部署中的一处偏差需如实记录：** 客机使用了开发者本人的
> Windows 账号（含 OneDrive 同步）。因此技术报告中**不得声称**
> 「评测环境不含个人数据」。准确表述为：评测在隔离虚拟机内进行，
> 客机使用开发者本人账号；规划层调用云端 API，客机截图会传输至模型
> 服务方；未对客机内的个人数据做剥离。

## 3.7 数据处理设计

三个公开数据集统一到同一 schema：
`sample_id / screenshot_path / resolution / instruction / action_type /
bbox / point / platform / app`，坐标一律存**绝对像素**并强制记录
分辨率。

清洗规则逐条计数（越界 / 面积过小 / 退化框 / 落点越界 / 无文本无类型），
**剔除量本身是格式解析的校验信号**——若把归一化 bbox 当绝对像素解析，
越界计数会瞬间飙到接近全量，这比「清洗后剩 3 条」更容易看出问题在哪。

数据划分**按会话而非按样本切分**：同一张截图会被同一会话内的多条标注
引用，按样本随机切会让验证分数虚高且看不出来。划分写入固定文件并记录
随机种子与内容指纹，载入时重算比对，文件被改动即拒绝载入。

> **一个必须写入报告的负面发现。** ScreenAgent 的 train 划分共 2000 个
> 有效标注步，展开为 3073 个动作，其中**仅 716 个携带坐标**
> （其余为规划、子任务评估、键盘动作）。按会话切分后训练集 569 条，
> 与原定的 3000–4000 条相差约 5 倍。
>
> 更关键的是**指令质量**：这 716 个点击能配上的只有整体任务目标
> （形如「在网上查冯诺依曼的资料」），且 716 条中仅 **169 条不重复**。
> 数据集中确有 1168 条标注者手写的元素描述（`PlanAction.element`），
> 但实测确认它们与鼠标动作**从不出现在同一步**、描述的是**另一张截图**，
> 且中英混杂（73% 中文）无语言变体，因此无法用作 grounding 指令。
>
> 该结论直接决定 M3 的微调方案，已归档于 `docs/m3-prereq/`。

## 3.8 评测方法：为什么不用 IoU 作主判据

传统检测任务以 IoU ≥ 0.5 判命中。**本项目的主判据是「检测框的中心点
是否落在真值框内」**，理由是：对 GUI Agent 而言框重合多少不重要，
**点下去能不能点中才重要**。OCR 把按钮上的文字框成一个小框，
与按钮真值框的 IoU 可能只有 0.2，但中心点稳稳落在按钮里；
反过来一个横跨两个按钮的大框可能 IoU 达标，中心点却落在缝隙上。

标注过程中意外获得了该判断的直接实证。计算器一图最初只框住数字字形，
改为框住整个按钮后重新评测：

| 真值框画法 | 点击点判据 | IoU 判据 |
|---|---:|---:|
| 只框数字字形 | 100% | **10%** |
| 框整个按钮 | 100% | **100%** |

**检测结果一个字节未变，IoU 从 10% 变为 100%，仅因人画框的松紧不同**；
点击点判据两次均为 100%。这比引用文献更能说明问题。
