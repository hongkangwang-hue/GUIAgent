# 隔离虚拟机客机搭建说明

> 面向 M1 验收标准 3、5、6，以及 M2 之后所有真实执行。
> 配套：`docs/开发环境配置文档.md` 第 4 节（虚拟机规格）。

---

## 0. 先说清楚 Agent 跑在哪

**Agent 整体运行在客机内**——感知、规划调用、坐标换算、键鼠执行全在客机。
宿主机只负责：开发代码、跑本地 grounding 模型（M3）、看结果。

这与 M0 最初写的「宿主机截 VM 的屏、往 VM 发键鼠事件」不同，**已在 M0 与
M1 文档中修正**，理由：

| 问题 | 宿主机侧执行 | 客机内执行 |
|---|---|---|
| M0 全局约束 1「宿主机不受控制」 | ❌ 违反——宿主机的鼠标就是被控制的那只，移出 VM 窗口就点到真实桌面 | ✅ 物理隔离 |
| UIA 识别通道 | ❌ 无法穿透 VM 边界，宿主机只看得到一个不透明窗口 | ✅ 正常 |
| M2 任务 8 的程序化成功判定 | ❌ 宿主机查不到客机内的进程与文件 | ✅ 直接可用 |
| M1 验收标准 3 的三档 DPI | 要改宿主机缩放 | 客机内改，不动宿主机 |

官方大纲对执行位置无要求（唯一相关的是合规说明第 5 条「所有操作均在本地
计算机上进行」，客机运行同样满足）。

**M3 的本地模型依然跑在宿主机 / 服务器**，客机经 HTTP 调用其 OpenAI 兼容
端点。权重在本地硬件上跑，这仍是大纲要求的「本地部署」，只是换了传输
方式——而且我们的后端本来就是通用兼容层，加一条 provider 记录即可。

```

Disk C            100 GB  动态分配
Disk R            20 GB   Independent-Persistent / Writethrough（结果盘，不参与快照回滚）
Resolution        1920×1080  主实验基线（W7 分辨率消融时按计划改，见下）
DPI               M1: 100% / 125% / 150% 三档轮测
                  M2-M5: 固定 100%
Network           NAT
3D acceleration   初始关闭，M1 验证后锁定
Firmware          UEFI
TPM               2.0 (vTPM)
Secure Boot       On

Account           agent（本地测试账号，非微软账号）

Shared Folder     Off
Shared Clipboard  Off      ← 这条漏了整个隔离就白做

```

**M2-M5 为什么固定 100%**：1920×1080 下 100% 是 Windows 的默认值，
可用面积最大，元素尺寸也最接近 ScreenSpot 桌面语料。选哪一档其实不关键，
**关键是选定之后 M2 到 M5 全程不变**——M5 的分辨率消融变的是分辨率，不是 DPI。

`Disk R` 在 M1 阶段还用不上，可以等 M2 开始前再挂，但**必须在跑第一轮
5×5 评测之前挂好**，否则第一轮数据必丢（见 §3.1）。

### 每一轮评测的固定流程

```
restore eval-baseline
        ↓
确认 1920×1080  ← 代码已强制：AgentLoop 每步比对截图尺寸与坐标系区域，
        ↓            不符即终止并记 resolution_changed
确认 DPI 档位   ← 代码已记录：每条轨迹的 meta.environment 里存有
        ↓            分辨率 / DPI / 截图引擎，事后可查
启动 Agent
        ↓
执行任务
        ↓
trajectory / screenshot / cost / result → R:（不回滚）
        ↓
终止 Agent
        ↓
restore eval-baseline
        ↓
下一次 repetition
```

前两步不能只靠人记得核对，所以都落成了代码：尺寸不符**当场终止**，
环境信息**每条轨迹都记**。「M2 和 M5 跑在同一环境」因此是可查证的事实，
而不是一句假设——这正是 M5 能引用 M2 数据作参照的前提。

## 1. 客机规格

按 `docs/开发环境配置文档.md` 第 4 节，你的机器是 32GB：

| 项 | 配置 | 说明 |
|---|---|---|
| 虚拟化软件 | **VMware Workstation Pro** | 已对个人使用免费，不必再找 Player。VirtualBox 也能用，但本项目要反复「恢复快照 → 跑评测 → 再恢复」，Pro 的快照管理更顺手 |
| 客机系统 | Windows 11 | **中文版**——本项目测的是中文界面 |
| **内存** | **12GB** | 总内存的 1/3～2/5。给多了宿主机换页，截图延迟飙升 |
| CPU | 4 核 | 留一半给宿主机 |
| **磁盘** | **100GB 动态分配** | **微软对 Windows 11 的最低存储要求就是 64GB**，之前写的 60GB 本身就不合规。再加上系统更新、Python、浏览器、测试软件、日志截图与**快照增量**，100GB 才有余量。动态分配意味着只按实际写入增长，不会一上来吃掉 100GB |
| 固件 | **UEFI** | Windows 11 的硬性要求 |
| TPM | **vTPM 2.0** | 同上。VMware 新版建 Windows 11 虚拟机时一般会自动配好，但**需要给虚拟机加密**才能挂 vTPM，会让你设一个密码 |
| Secure Boot | **开启** | 同上 |
| **分辨率** | **固定 1920×1080** | 坐标系统依赖它。见下 |
| 3D 加速 | **先关闭作为基线** | 见下 |
| GPU 直通 | 不需要 | |

### 宿主机隔离：VMware Tools 装，但要关掉这四项

VMware Tools 必须装（显示驱动、分辨率控制靠它）。**装完立刻关掉：**

| 关掉什么 | 为什么 |
|---|---|
| **共享剪贴板** | **这条最要命。** 你在宿主机 Ctrl+C 复制的任何东西都会出现在客机剪贴板里。而客机的截图是要上传到云端 API 的——**整个数据边界就在这里破掉了** |
| 共享文件夹 | 客机能直接读写宿主机目录，隔离形同虚设 |
| 拖放 | 同上，只是走另一条通道 |
| USB 自动连接 | 插 U 盘时不该自动挂给客机 |

**网络用 NAT，不要 Bridged。** Agent 只需要「客机 → 互联网 → 百炼 API」这一条
路径。Bridged 会让客机变成你局域网里一台独立设备，能访问家里 / 学校网内的其他机器
——这是白送出去的攻击面，本项目一点也用不上。

隔离结构应该长这样：

```
宿主 Windows
├── 你的真实文件 / 浏览器 / 账号
└── VMware
     └── Windows 11 Agent 客机
          ├── 本地测试账号（非微软账号）
          ├── 预置测试文件
          ├── Python + Agent
          └── NAT → 百炼 API

     ✗ 共享文件夹   ✗ 共享剪贴板
     ✗ 拖放         ✗ 真实账号
```

### 分辨率为什么要固定并记录

`CoordinateScaler` 按截图区域建立映射。客机分辨率一变，之前所有轨迹里的
真实坐标就对不上了，M3/M4/M5 的对比分析会失去可比性。

**主实验期间不要改客机分辨率。** 记进验收材料。

但**不是整个项目永远不改**——我之前那句话说过头了。大纲 W7 明确要求
「分析系统在**不同应用、不同分辨率**下的表现差异」，所以正确的设计是
分成两层：

| | 分辨率 | 用途 |
|---|---|---|
| **主实验基线** | **1920×1080，100% 缩放** | M1–M5 的**全部主结果**都基于它 |
| **分辨率鲁棒性实验** | 1366×768 / 1600×900 / 1920×1080 | 只在 M5（第 7 周）做一次，作为独立的消融 |

M5 里已经排好了这组消融（三档 × 4 个任务 × 2 次，约 24 次执行），
所以这不是新增工作，是把「什么时候允许改」写清楚。

**两件事必须守住：**

1. **消融数据不得与主实验数据混在一起统计。** 主 benchmark 是
   1920×1080 的 60 次；分辨率消融是另一张表。合并平均等于把
   「系统有多强」和「系统有多稳」搅成一个数。
2. **每次改完分辨率必须重启 Agent 进程。** `CoordinateScaler` 是在进程
   启动时按当前屏幕建立映射的，不重启就会拿旧映射去点新分辨率——而
   `AgentLoop` 的尺寸闸门会当场拦下并记 `resolution_changed`，
   不至于出错数据，但那一轮就白跑了。

> 顺带说明一件已经做对的事：**`CoordinateScaler` 里没有任何硬编码分辨率**。
> 三个构造点分别是 `CoordinateScaler(probe.region)`（实际截一张图取尺寸）、
> `CoordinateScaler(capturer.monitor_region(1))`（实际显示器）、
> `CoordinateScaler(region)`。代码里出现的 1920 / 2560 全在文档字符串里，
> 是实测记录不是算法假设。所以换分辨率**不需要改任何代码**，
> 每次启动自动按当前屏幕重建映射。
>
> 分辨率是**实验配置**，不是算法假设——这条要一直守住。

**必须关掉 VMware 的「自动调整客机分辨率」。** 否则你拖一下 VMware 窗口边框，
客机就可能从 1920×1080 悄悄变成 1760×990，**没有任何提示**。

光靠「记得别改」不可靠，所以代码里也加了闸门：`AgentLoop` 每一步截完图都会
比对截图尺寸与 `CoordinateScaler` 建立映射时的区域，不一致就**立刻终止本轮**
并记 `resolution_changed`。这类错配不会崩，只会让每次点击都系统性偏移，
看起来像「模型定位不准」——M1 已经吃过一次同形态的亏，查了三组实验才定位到。

**DPI 缩放和分辨率是两回事**：分辨率固定 1920×1080 不动；显示**缩放**要在
M1 验收标准 3 里测 100% / 125% / 150% 三档，之后 M2–M5 固定用其中一档。

### 数据边界（M0 全局约束 1 的另一半）

虚拟机解决执行隔离，**不解决数据隐私**——规划层走云端 API，客机内的截图
会被上传出去。所以客机按「可公开的测试环境」建：

- ✅ 只装测试软件、只用为本项目新建的测试账号、只放预置测试文件
- ❌ 不登录任何真实个人账号，不放真实聊天记录、邮件、通讯录、支付信息

## 2. 客机内装什么

**OCR 必须在拍 `eval-baseline` 快照之前装好。**

这一条原先写反了（写的是「不需要装 paddleocr」）。M1 验收标准 4 要的是
「**双通道融合后**的召回率，**按来源分项统计**」——UIA 一条通道、OCR 一条
通道，缺一条既谈不上融合也谈不上分项，`capture_gallery.py` 也跑不了。

而且时机很关键：**快照拍完再装，每次恢复快照都会把它抹掉**，M2–M5 每轮
评测都要重装一次。代价只是快照大几个 GB，100GB 的盘装得下。

`bootstrap_guest.py` 默认已包含 OCR，不用你操心。torch / langchain 仍然
不装——M1 全程没有大模型参与；想让快照一次到位可以加 `--with-llm`。

先装 Python 3.10（勾选 "Add Python to PATH"），然后**跑一条命令就行**：

```powershell
git clone <你的仓库地址>
cd GUIAgent
python scripts/bootstrap_guest.py
```

它会装依赖、`pip freeze` 冻结版本、跑自检，并把客机的**截图引擎、分辨率、
DPI、截图延迟**写成 `docs/m1-guest-environment.md`——这份就是 M1 验收要的
环境材料，不用你手工记。

下面是它实际执行的内容，出问题时可以手工逐条来：

```powershell
# 客机内
git clone <你的仓库地址>
cd GUIAgent

python -m pip install --upgrade pip
pip install numpy pillow opencv-python mss pyautogui pynput pyperclip uiautomation dxcam
pip install pytest rich typer pyyaml
```

这份清单和 CI 里装的一致（`.github/workflows/ci.yml`），是跑 `verify_control.py`
的最小集合。约 200MB，几分钟装完。

**装完立刻冻结版本：**

```powershell
pip freeze > requirements-vm.lock.txt
```

之后 M2–M5 **不要 `pip install --upgrade`**。`pyautogui`、`mss`、`dxcam`、
`uiautomation` 里任何一个换版本都可能改变延迟或行为——对普通开发这无所谓，
对我们**软件版本本身就是实验变量**，中途变了等于换了实验条件。宿主机已经有
`requirements.lock.txt`，客机的依赖集不同，需要单独一份。

> **dxcam 在虚拟机里可能不可用**（DXGI 桌面复制依赖显卡驱动）。没关系，
> `ScreenCapturer` 会自动降级到 mss。脚本开头会打印实际用的引擎，记下来
> ——虚拟机内的截图延迟会明显高于宿主机的 dxcam，这个差异要进验收材料。

### 3D 加速：关闭是**基线**，不是定律

之前这份文档写的是「3D 加速必须关闭」，措辞过头了。它的出处是配置文档里
一张常见坑速查表的条目（「虚拟机内截图全黑 ← 客机启用硬件加速渲染」），
**是别人踩过的坑，不是我们的实测结论**。

正确做法是：**先关闭 3D 作为稳定性基线**，然后跑一次 `env_check.py` 与
`verify_control.py`，把这几项记下来：

- 实际启用的截图引擎（dxcam 还是 mss）
- 截图是否正常（有没有全黑）
- 平均延迟与 p95 延迟

如果关着 3D 一切正常，就**永久关闭并锁定**，不必再折腾。只有在 dxcam 明显
异常、且你确实需要它的速度时，才值得再做一次开启 3D 的对照。

**无论最后选哪个配置，M1 → M5 全程不再变化。**

### 装几个测试用软件

M1 验收标准 5 的中文输入检查需要一个文本框，M2 的 5 个基础任务也要有东西
可操作：

- 记事本（系统自带）
- 一个浏览器（Edge 自带即可）
- 文件资源管理器（系统自带）

够了。不要装办公套件之类的大件，快照会变大。

## 3. 存快照 —— 这一步不能省，而且要存两个

M2–M5 每轮评测都从快照恢复。理由：Agent 会真的操作客机——建文件、改设置、
开关程序。跑到第三轮时客机状态早已和第一轮不同，**成功率就不可比了**，
而 M2 要求每任务跑 5 次、M5 要求 20 任务 × 3 次。

**存两级，不要只存一个：**

| 快照 | 何时存 | 内容 |
|---|---|---|
| `clean-os` | 装完系统就存 | Windows 11 + 本地账号 + VMware Tools + 固定显示设置 + 系统更新完成 |
| `eval-baseline` | 装完 Python / 依赖 / 浏览器 / 测试数据，且确认全部正常之后 | 在 `clean-os` 基础上加完整实验环境 |

**日常评测恢复的是 `eval-baseline`。** 留着 `clean-os` 是为了万一 Python 环境
或依赖搞坏了，还有一个更早的干净点可退，不用从头装系统。

**存快照前先把客机正常关机，不要存带内存状态的快照。**

原因和 §3.1 的结果盘直接相关：独立磁盘（Independent-Persistent）**不参与
回滚**，而带内存状态的快照会把「当时内存里以为的磁盘状态」一起恢复。
两者对不上时，客机可能看到一个和内存记录不一致的 `R:` 盘——轻则文件句柄
失效，重则文件系统损坏。

所以流程是：**客机关机 → 拍快照**。恢复后开机，比恢复内存状态慢十几秒，
但换来的是不会踩这个坑。

VMware：客机关机 → 虚拟机 → 快照 → 拍摄快照（**不要勾选内存状态**）
VirtualBox：客机关机 → 机器 → 生成备份

---

## 3.1 结果盘 —— 恢复快照会把你的实验数据一起删掉

**这是最容易踩、代价最大的一个坑。**

恢复快照会把整块虚拟硬盘回滚。也就是说：

```
恢复 eval-baseline → 跑第 1 次 → 轨迹 / 截图 / 成本数据写进 C:
  → 恢复 eval-baseline 准备跑第 2 次
  → 第 1 次的数据全没了
```

而轨迹日志是 M3、M4、M5 **全部分析的唯一数据源**，M0 全局约束 5 写着
「禁止为了看结果重跑任务」。丢一次等于白跑一轮。

**解法：把「环境状态」和「评测结果」分到两块盘。**

给客机再挂一块虚拟硬盘（20GB 够用），设为**不参与快照回滚**：

- VMware：该磁盘设为 **Independent - Persistent**（独立-持久）
- VirtualBox：该磁盘设为 **Writethrough**（直写）

挂载为 `R:`，然后让轨迹落盘指向它：

```powershell
python -m cli run "打开记事本" --execute --root R:\evaluation_results
```

`TrajectoryWriter` 的 `root` 本来就是可配的，不用改代码。

于是流程变成：

```
恢复 eval-baseline → 跑第 1 次 → 结果写 R:（不回滚）
恢复 eval-baseline → 跑第 2 次 → 结果写 R:
...
```

这才是一套能重复跑的评测基础设施。

> **R: 盘要当成只追加的。** 它不参与回滚，也就意味着一旦被写坏就退不回去。
> 只往里写轨迹与截图，别在上面放任何需要回滚的东西。

> **M1 现在还用不上 R: 盘**（没有正式评测），可以等 M2 开始前再挂。
> 但**必须在跑第一轮 5×5 评测之前挂好**，否则第一轮数据必丢。

## 4. 跑 M1 验收

进客机，打开一个记事本（中文输入检查要用），然后：

### 4.1 三档 DPI（验收标准 3）

客机内改：设置 → 系统 → 显示 → 缩放。每档跑一次：

```powershell
python scripts\verify_control.py --only coord --note "客机 100% DPI"
# 改成 125%
python scripts\verify_control.py --only coord --note "客机 125% DPI"
# 改成 150%
python scripts\verify_control.py --only coord --note "客机 150% DPI"
```

**跑之前看脚本第一行**，确认它检测到的缩放和你设的一致。不一致脚本会直接
拒绝写报告并告诉你原因——这是有意的，档位标错的记录比没有记录更糟。

改完缩放要**重开 PowerShell 窗口**（Python 进程启动时才读 DPI）。

跑的时候**手离开鼠标**，否则会触发干扰重试。

### 4.2 完整验证（验收标准 5、6）

```powershell
python scripts\verify_control.py --note "客机 完整验证"
```

六组检查一次跑完：坐标链、点击落点（UIA 反查）、各动作冒烟、安全拦截、
中文输入、急停热键。**会真的点击和打字**——这正是要在客机里做的原因。

急停那一步会提示你按 `Ctrl+Alt+Q`，鼠标届时会持续移动，这是故意的
（验收标准 7 要求「Agent 正控制鼠标时仍能中断」）。

#### ⚠ 急停必须在客机内重测，而且热键本身可能根本不可用

宿主机测出的 **247ms 不能当作 VM 里的结果**。进了虚拟机，链路多了两段：

```
你的键盘 → VMware 输入捕获 → 客机 Windows → pynput → Agent 停止
```

**但比延迟更要紧的是：这个组合键可能压根到不了客机。**
`Ctrl+Alt` 是 VMware **释放输入焦点**的默认前缀键。如果 VMware 把
`Ctrl+Alt+Q` 截走了，你按下去的效果是「鼠标键盘交还给宿主机」，
而客机里的 Agent **仍在继续跑**——急停等于没有。

所以客机建好后必须按顺序确认这三件事，**不能只看延迟数字**：

1. **热键到不到得了客机。** 客机里跑
   `python scripts/verify_control.py --only stop`，按 `Ctrl+Alt+Q`，
   看脚本有没有反应。没反应就是被 VMware 截走了。
2. **被截走了就换一个。** 改用不带 `Ctrl+Alt` 前缀的组合，
   比如 `Ctrl+Shift+F12`。改完要同步改代码里的默认值与所有文档。
3. **确认能用之后再测延迟**，把客机的实测值记进
   `docs/m1-control-verification.md`，与宿主机的 247ms **并列呈现**，
   注明各自的测量环境。

宿主机的 247ms 保留为开发阶段记录，**M1 验收标准 7 以客机实测值为准**。

FAILSAFE（鼠标甩到屏幕角落）不受此影响——它由客机内的 pyautogui 自己
判定光标位置，不经过宿主机的按键处理。但也要在客机里实测一次。

结果全部追加进 `docs/m1-control-verification.md`。

## 5. 之后：让 Agent 在客机里跑起来

M1 验收过了之后，客机里再补装模型调用的依赖：

```powershell
pip install langchain langchain-openai
```

把宿主机的 `.env` 内容复制进客机的 `.env`（**手动复制，别放进 git**），
然后：

```powershell
python -m cli run "打开记事本"            # 先演练
python -m cli run "打开记事本" --execute  # 确认无误后实机执行
```

`--execute` 会二次确认并提示急停热键。**此时鼠标会被程序接管**，但一切
都发生在客机内，宿主机不受影响。
