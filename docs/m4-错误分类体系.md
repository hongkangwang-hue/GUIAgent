# 错误分类体系（基于实测频次重建）

> M4 交付物第 1 条 / 大纲 W6 任务 1。
> **频次全部来自实测**，不是设想出来的分类。
> 数据源：`docs/m3-trajectories-20260827/`（25 轮 / 185 步）
> 与 `docs/m2-runs/20260827-163522-all-exec-offline-lora-fixed-2.json`。
> 模型：Qwen2.5-VL-3B + adapter `20260827-174327`，客机 1920×1080。

---

## 0. 一句话结论

**失败不是多种原因各占一些，是一种原因占了绝大多数。**

```
94.4% 的子任务在执行 0~1 个动作之后就宣布完成
```

按频次排序，A 类一项就吃掉了绝大部分失败。**优化投入应该压倒性地
向 A 类倾斜**，其余三类目前不值得单独做恢复策略。

## 2. A 类：假 `done`（早停）

### 2.1 定义

模型输出 `{"done": true}` 结束子任务，但程序化判据（进程 / 窗口标题 /
文件内容）显示目标未达成。

### 2.2 典型案例：`close_app` 五轮完全一致

```
step1  {"action":"left_click","x":508,"y":67,"thinking":"点击计算器右上角的关闭按钮"}
       execution_status = ok            ← 点击确实执行了
step2  {"done":true,"thinking":"已经成功关闭了计算器"}
       execution_status = no_action
判定   ✗ 进程 'CalculatorApp.exe' 应已退出；找到 1 个
```

五轮的步数、耗时、坐标、输出全部相同——**这是确定性的失败模式，不是波动**。

### 2.3 病因：模型的完成判据是「我发出了动作」，不是「屏幕变了」

`model_thinking` 的句式直接暴露了这一点（146 条非空、去重 59 条）：

```
5×  因为发送按钮已经被点击，所以任务完成
5×  因为已经输入了文件路径，所以任务完成
5×  因为记事本已经在浏览器中打开了，所以已经完成了任务
4×  因为地址栏已经被点击，所以任务完成
```

**「因为我点了 X，所以任务完成」——句式本身就是以动作代替结果。**

更深一层的成因见 `docs/m3-微调效果对比分析报告.md` §11.7.5：
`done` 是动作集中**唯一不需要参数**的动作（训练集里占 41.6%、答案仅
14 个字符，其余动作 34~55 字符），对交叉熵来说是一条又便宜又常中的路。

> **训练数据无法纠正这一点。** ScreenAgent 的标注是「这一步该做什么」，
> **不含「上一步做成了没有」**。模型没有可学的信号去区分「点了」和「点中了」。
> 因此 A 类必须在**系统层**解决，不能指望换数据或加训练轮次。

### 2.4 检测手段

| 级联层 | 手段 | 成本 | 能挡住的部分 |
|---|---|---|---|
| 1 | 上一步动作后的 OpenCV 帧差 | 毫秒级、免费 | 「点了没中就报完成」——对应 78 次「动作 ok 后立刻 done」 |
| 2 | 程序化判据（进程/标题/文件/UIA 控件） | 毫秒级、免费 | 有明确判据的子任务 |
| 3 | 语义判定（本地 3B 复用常驻权重） | 一次本地推理 | 前两级冲突或都判不了时 |

**级联 1 应该能吃掉大部分**：A 类的主峰是「1 个动作后报 done」（81.1%），
而那个动作若真的命中，屏幕通常会变。

### 2.5 恢复策略

```
① 否决 done，不结束子任务
② 把「上一步没有产生预期变化」写进下一轮的子任务描述
③ 连续 N 次被否决则终止子任务并记为失败，避免死循环
```

**②是关键。** `core/retry.py` 的模块文档已经记录过：单纯把 `left_click`
升级成 `double_click` 改不了模型下一步的判断——**探针实测坐标重复率
75.3%**。要让模型换目标，必须把失败信息回传给它。

### 2.6 现状：完全没有对策

`core/loop.py` 第 332~336 行：

```python
# --- 3. 模型自报完成 ---
if intent.done:
    record.execution_status = "no_action"
    return self._commit(record), (STOP_DONE, ...)
```

**模型说 done，循环立刻返回，一次校验都不做。**
第 7.5 步的屏幕变化检测只在动作执行之后才跑，`done` 走不到那里。

这与 M2 定下的「程序化成功判定，绝不采信模型自报」是**同一条原则**，
只是当时只用在了**轮次级**的验收上，没有用在**子任务级**的推进上。

## 3. B 类：点击落空

### 3.1 定义

动作执行成功（`execution_status = ok`），但没有命中目标，屏幕无变化
或变化与预期无关。

### 3.2 已从 A 类中分离（2026-08-27 追加）

`--reflector` 会自动启用帧差，`record.meta["change"]` 因此有了数据。
Reflector 轮（`lora-reflector`，25 轮 / 220 步）实测：

```
动作执行后屏幕变了   49 次
动作执行后屏幕没变   30 次      ← B 类，占 38.0%
```

**38% 的动作 `execution_status = ok` 但屏幕没有任何变化。**
它们全部执行成功，只是没有命中目标。

`close_app` 是典型：点击 `ok`，但计算器进程仍在。

### 3.3 已有对策

`core/retry.py` 的 `RetryPolicy`：同位置点击无变化 → 升级为双击，
并通过 `hint()` 把「上一次点了没反应」回传给模型。

**默认关闭**，M2/M3 的实测都是关着跑的——打开会改变行为，
不能和历史数据混在一起比。

## 4. C 类：输出解析失败

```
实测 1/185 = 0.5%（parse_error）
```

微调前这是主要问题（离线格式合规率 24.0%），
微调后离线合规率 100.0%、端到端 0.5%。

**已基本消除，不需要专门的恢复策略。** 现有的重试机制足够。

## 5. D 类：坐标塌陷

```
客机 1920×1080  预测 x 中位 508，54.9% 落在 [480,540]，不重复坐标仅 45.1%
离线 1024×768   预测 x 中位 425，19.2% 落在 [480,540]，不重复坐标 82.2%
```

模型坐标空间 0~1000 映射到 1920 宽时 x 乘 1.92，**508 → 真实 x≈975，
正好是屏幕水平中线**。

**只在客机上发生，训练同尺寸图上正常。** 疑似宽高比造成
（训练 4:3，客机 16:9），详见 §11.7.7。

**这不是恢复策略能解决的类别**——它是预处理问题。验证方法是
把验证集 letterbox 成 16:9 后重跑离线评测。

## 6. 优先级结论

```
A 类   94.4%    → Reflector 级联 1+2，本阶段主要工作
B 类   含于 A   → 先打开帧差把它分离出来，再谈
C 类    0.5%    → 不做
D 类   离线可测 → 一次 letterbox 实验即可定性，与恢复策略无关
```

**不为 C、D 类写恢复策略。** 分类体系的作用是把投入放对地方，
把四类都做一遍恢复策略是把 0.5% 和 94.4% 当成同等重要。

## 7. Reflector 实测（2026-08-27）

单变量对照：唯一差别是 `--reflector`，模板同为 `executor_v0`，
`escalate_on_no_change` 两轮都是 `False`（存档字段可核）。

### 7.1 成功率：必须用同快照的那一列

**先说一个被纠正过的数字。** 初次对比拿的是不同快照的两轮，
得出「12% → 40%，3.3 倍」。补跑同快照对照后，正确的值是 **2 倍**。

| 档 | 客机快照 | Reflector | 成功 |
|---|---|---|---:|
| 无 Reflector（旧） | `eval-baseline 2` + 手工装依赖 | 否 | 3/25 = 12% |
| **无 Reflector（对照）** | `eval-baseline-llm` | 否 | **5/25 = 20%** |
| **有 Reflector** | `eval-baseline-llm` | 是 | **10/25 = 40%** |

```
换快照的贡献      12% → 20%    +8 个百分点
Reflector 的贡献  20% → 40%    +20 个百分点（2 倍）
```

> **但「Reflector 的贡献」不等于「Reflector 纠了错」。**
> 实测纠错率为 0%（§7.4），增益疑似来自额外耗时（§7.5）。
> **判决性实验做完之前，这 20 个百分点只能记作「打开开关后的差值」，
> 不能记作「错误恢复带来的提升」。**

**那 8 个百分点全部来自换快照，与 Reflector 无关。**
若不补这一轮，报告里会写下一个虚高 65% 的结论。

#### 分任务归因（同快照）

| 任务 | 无 Reflector | 有 Reflector | 差值 |
|---|---:|---:|---:|
| `open_browser` | 5/5 | 5/5 | **0** |
| `search_content` | 0/5 | 0/5 | 0 |
| `open_file` | 0/5 | 0/5 | 0 |
| `send_message` | 0/5 | **3/5** | **+3** |
| `close_app` | 0/5 | **2/5** | **+2** |
| 合计 | 5/25 | 10/25 | +5 |

**Reflector 的全部贡献是 `send_message` +3 与 `close_app` +2。**
`open_browser` 两轮都是 5/5——它从 3/5 涨到 5/5 完全来自换快照。

#### 两个交叉验证

```
close_app 平均步数    旧快照无Reflector 2.0
                     同快照无Reflector 2.0     ← 完全一致，环境可比
                     同快照有Reflector 2.8

零动作报完成          无Reflector 7/92 (8%)
                     有Reflector 7/84 (8%)     ← 一模一样
```

第二条正好验证了 §2.5 的**设计选择①**：刻意不否决「0 动作就 done」，
所以这个数应当不变——**实测确实没变**，设计意图与行为对上了。

其余佐证指标（同快照）：

```
模型自报完成            25/25  →  22/25
自报完成但判定未通过     20     →  12          少 40%
```

### 7.2 级联触发率（M4 要求记录的关键指标）

```
Reflector 判定 138 次 / 220 步

accept     74   53.6%
reject     57   41.3%
unknown     7    5.1%
```

**级联 1 单独出了 94.9% 的结论。** 里程碑设计的假设
「绝大多数步骤应在前两级出结论」成立——**且级联 1 一级就够，
级联 2/3 暂时用不上**（例外见 §8.4）。

### 7.3 撤回：Reflector 的纠错能力实测为零

> **本节的初稿是错的，2026-08-28 撤回。** 保留错误内容与成因，
> 因为它示范了一个很容易犯的统计错误。

#### 初稿写了什么

初稿称「否决之后模型改做了什么：`left_click` 7 次 / `type` 8 次，
坐标与上一次相同 0 次」，据此宣布
「告诉模型『动作没生效』和告诉它『再试一次』，效果完全不同」。

#### 为什么是错的

统计脚本有 bug：它维护一个 `pending_reject` 标志，
**只在遇到非 `done` 输出时才计数**——于是跳过了否决之后所有重复的 `done`，
把很多步之后（甚至下一个子任务里）的动作算成了「对否决的反应」。

正确的统计是「否决的**下一步**是什么」：

```
57 次否决之后，模型下一步：
  done（原样再报一次）    54 次   94.7%
  解析失败                 3 次    5.3%
  换了动作                 0 次    0.0%
```

**模型收到反馈之后，94.7% 的情况是把 `done` 原样再说一遍。**

反馈确实送达了——220 步中有 57 步带 `meta["hint"]`，与否决次数完全一致，
文本也正确：

```
上一步动作执行后屏幕没有发生变化，说明它很可能没有命中目标。
子任务尚未完成，请换一个位置或换一种方式再试，不要报告完成。
```

**是模型收到之后不为所动。** §2.5 引用 `retry.py` 的
「坐标重复率 75.3%」所作的预判**方向是对的**，初稿不该撤回它。

### 7.4 标准 5：错误自动恢复率 = 0.0%

M4 验收标准 5 要求「可恢复错误中被成功恢复的比例，按错误类型分项」。

**必须把两种 `accept` 分开**，否则会得出一个虚高 90 个百分点的数字：

| `accept` 的两种来源 | 判据 | 含义 |
|---|---|---|
| `accept_real` | 上一步动作后屏幕变了 | **真恢复** |
| `accept_cap` | 连续否决到上限（`max_rejects=2`）强制接受 | **安全阀触发，未恢复** |

138 次判定拆开：

```
accept 真·屏幕变了    47   34.1%
accept 到上限兜底     27   19.6%
reject 否决           57   41.3%
unknown 判不了         7    5.1%
```

被否决过的 30 个子任务：

```
真恢复（改了动作且屏幕变了）    0    0.0%
到上限强制接受（未恢复）       27   90.0%
仍在否决中就结束               3   10.0%
```

> **真实恢复率 = 0/30 = 0.0%。**
> 初稿把「到上限强制接受」也算成恢复，得出 90.0% —— 虚高 90 个百分点。
> 这与 §7.3 的统计错误是同一天、同一批数据上犯的两个独立错误。

### 7.5 那 20% → 40% 到底来自哪：计时假象的嫌疑

既然纠错率为零，成功率翻倍就必须另有解释。

**真动作数一个都没增加：**

| 任务 | 无 Reflector<br>真动作 / `done` 重复 | 有 Reflector<br>真动作 / `done` 重复 | 成功 |
|---|---|---|---|
| `close_app` | 5 / 5 | 5 / 9 | 0→2 |
| `open_browser` | 15 / 15 | 15 / 15 | 5→5 |
| `open_file` | 25 / 30 | 25 / 50 | 0→0 |
| `search_content` | 23 / 25 | 21 / 23 | 0→0 |
| `send_message` | 17 / 17 | **13** / 41 | 0→3 |

**`send_message` 真动作从 17 降到 13，成功率却从 0/5 涨到 3/5。**
多出来的 43 步全部是重复的 `done`（`execution_status = no_action`）。

而重复一次 `done` 要花一次模型调用 + 一次截图：

```
close_app      18.3s → 26.1s    +7.8s     0/5 → 2/5
send_message   49.8s → 64.9s   +15.1s     0/5 → 3/5
open_file      81.1s → 101.8s  +20.7s     0/5 → 0/5
```

**两个改善的任务恰好是多花了时间的任务**，而程序化判定在循环结束之后才跑。

本项目已记录过计时敏感的直接证据
（`docs/m3-微调效果对比分析报告.md` §7.5 第 2 条）：

> C 组有 1 轮无效（关闭应用第 1 次，起点未建立），
> 原因是 reset 里 `taskkill` 之后只等 3 秒，而 UWP 计算器冷启动更久。

**`close_app` 正是那个已知会受异步时序影响的任务。**

> **嫌疑而非定论。** `open_file` 也多花了 20.7 秒却没有改善，
> 说明时间不是充分条件。

#### 判决性实验

**不加 Reflector，只加等量延时**（判定前额外等待 8~15 秒）：

```
成功率同样涨到 40%   → Reflector 目前的收益是计时假象，纠错能力为零
成功率仍在 20%       → 时间不足以解释，Reflector 有别的作用机制
```

**在这个实验做完之前，§7.1 的「2 倍」不能写成「Reflector 能纠错」**，
只能写成「打开 Reflector 后成功率从 20% 升到 40%，机制待定」。

### 7.6 `open_file` 是最有价值的负例：级联 2 的存在理由

```
任务              accept  reject  unknown   成功
open_browser        15       0       0      5/5    从没被否决，本来就做对了
send_message        13      26       2      3/5    否决最多，救回 3 个
open_file           25      20       5      0/5    否决 20 次仍然全败
search_content      16       7       0      0/5
close_app            5       4       0      2/5
```

`open_file` 被否决 20 次、模型确实一直在改动作，但仍然 0/5。判定信息：

```
✗ 进程 'notepad.exe' 应在运行；未找到
当前窗口：记事本 - 搜索 - 个人 - Microsoft Edge
```

**模型在 Edge 里搜索「记事本」这三个字，而不是打开记事本程序。**

这是**任务理解错误**，不是执行未生效——帧差每次都显示「变了」，
级联 1 判定 `accept`，但方向从一开始就错了。

> **这正是级联 2（程序化判据）该管的。** 检查「`notepad.exe` 进程是否存在」
> 比看屏幕变没变有力得多。
>
> **级联 1 管「动作有没有生效」，级联 2 管「方向对不对」**
> ——这个分工现在有数据支撑，不再是设计时的猜想。

### 7.7 三条必须标注的限制

1. ~~**快照不同。**~~ **已解决。** 补跑了同快照对照
   （`lora-noreflector-same-snapshot`，`eval-baseline-llm`），
   把环境差异从 Reflector 的效果里剥了出来：8pp 归快照，20pp 归 Reflector。
   `scripts/run_basic_tasks.py` 新增 `--guest-snapshot`，
   漏传会打警告——**本项目已因未记快照名两次拿到无法验证的对比数据。**
2. **n=25，各跑一次。** 20% → 40% 幅度很大，但没有重复实验。
3. **`open_browser` 的快照敏感性未解释。** 同一模型、同一提示词，
   仅换快照就从 3/5 变成 5/5。原因未查（可能是 Edge 首次启动状态、
   任务栏图标位置或系统更新差异）。**这说明客机环境对成功率的影响
