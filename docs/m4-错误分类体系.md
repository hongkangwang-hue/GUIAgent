# 错误分类体系（基于实测频次重建）

> M4 交付物第 1 条 / 大纲 W6 任务 1。
> **频次全部来自实测**，不是设想出来的分类。
> 数据源：`docs/m3-trajectories-20260827/`（25 轮 / 185 步）
> 与 `docs/m2-runs/20260827-163522-all-exec-offline-lora-fixed-2.json`。
> 模型：Qwen2.5-VL-3B + adapter `20260827-174327`，客机 1920×1080。

---

## 0. 一句话结论

**失败不是多种原因各占一些，是一种原因占了绝大多数。**

```
94.4% 的子任务在执行 0~1 个动作之后就宣布完成
```

按频次排序，A 类一项就吃掉了绝大部分失败。**优化投入应该压倒性地
向 A 类倾斜**，其余三类目前不值得单独做恢复策略。

---

## 2. A 类：假 `done`（早停）

### 2.1 定义

模型输出 `{"done": true}` 结束子任务，但程序化判据（进程 / 窗口标题 /
文件内容）显示目标未达成。

### 2.2 典型案例：`close_app` 五轮完全一致

```
step1  {"action":"left_click","x":508,"y":67,"thinking":"点击计算器右上角的关闭按钮"}
       execution_status = ok            ← 点击确实执行了
step2  {"done":true,"thinking":"已经成功关闭了计算器"}
       execution_status = no_action
判定   ✗ 进程 'CalculatorApp.exe' 应已退出；找到 1 个
```

五轮的步数、耗时、坐标、输出全部相同——**这是确定性的失败模式，不是波动**。

### 2.3 病因：模型的完成判据是「我发出了动作」，不是「屏幕变了」

`model_thinking` 的句式直接暴露了这一点（146 条非空、去重 59 条）：

```
5×  因为发送按钮已经被点击，所以任务完成
5×  因为已经输入了文件路径，所以任务完成
5×  因为记事本已经在浏览器中打开了，所以已经完成了任务
4×  因为地址栏已经被点击，所以任务完成
```

**「因为我点了 X，所以任务完成」——句式本身就是以动作代替结果。**

更深一层的成因见 `docs/m3-微调效果对比分析报告.md` §11.7.5：
`done` 是动作集中**唯一不需要参数**的动作（训练集里占 41.6%、答案仅
14 个字符，其余动作 34~55 字符），对交叉熵来说是一条又便宜又常中的路。

> **训练数据无法纠正这一点。** ScreenAgent 的标注是「这一步该做什么」，
> **不含「上一步做成了没有」**。模型没有可学的信号去区分「点了」和「点中了」。
> 因此 A 类必须在**系统层**解决，不能指望换数据或加训练轮次。

### 2.4 检测手段

| 级联层 | 手段 | 成本 | 能挡住的部分 |
|---|---|---|---|
| 1 | 上一步动作后的 OpenCV 帧差 | 毫秒级、免费 | 「点了没中就报完成」——对应 78 次「动作 ok 后立刻 done」 |
| 2 | 程序化判据（进程/标题/文件/UIA 控件） | 毫秒级、免费 | 有明确判据的子任务 |
| 3 | 语义判定（本地 3B 复用常驻权重） | 一次本地推理 | 前两级冲突或都判不了时 |

**级联 1 应该能吃掉大部分**：A 类的主峰是「1 个动作后报 done」（81.1%），
而那个动作若真的命中，屏幕通常会变。

### 2.5 恢复策略

```
① 否决 done，不结束子任务
② 把「上一步没有产生预期变化」写进下一轮的子任务描述
③ 连续 N 次被否决则终止子任务并记为失败，避免死循环
```

**②是关键。** `core/retry.py` 的模块文档已经记录过：单纯把 `left_click`
升级成 `double_click` 改不了模型下一步的判断——**探针实测坐标重复率
75.3%**。要让模型换目标，必须把失败信息回传给它。

### 2.6 现状：完全没有对策

`core/loop.py` 第 332~336 行：

```python
# --- 3. 模型自报完成 ---
if intent.done:
    record.execution_status = "no_action"
    return self._commit(record), (STOP_DONE, ...)
```

**模型说 done，循环立刻返回，一次校验都不做。**
第 7.5 步的屏幕变化检测只在动作执行之后才跑，`done` 走不到那里。

这与 M2 定下的「程序化成功判定，绝不采信模型自报」是**同一条原则**，
只是当时只用在了**轮次级**的验收上，没有用在**子任务级**的推进上。

## 3. B 类：点击落空

### 3.1 定义

动作执行成功（`execution_status = ok`），但没有命中目标，屏幕无变化
或变化与预期无关。

### 3.2 与 A 类的关系

**B 类目前无法从 A 类中分离**——本次导出未包含 `frames/`（安全考量，
见 `docs/m3-trajectories-20260827/README.md`），没有帧差数据。

`close_app` 是可以确认的一例：点击 `execution_status = ok`，
但计算器进程仍在，说明点偏了。

> **要把 B 从 A 里分出来，必须打开 `--escalate-on-no-change`
> 让帧差数据进 `record.meta["change"]`。** 这是下一轮跑数据时要加的。

### 3.3 已有对策

`core/retry.py` 的 `RetryPolicy`：同位置点击无变化 → 升级为双击，
并通过 `hint()` 把「上一次点了没反应」回传给模型。

**默认关闭**，M2/M3 的实测都是关着跑的——打开会改变行为，
不能和历史数据混在一起比。

## 4. C 类：输出解析失败

```
实测 1/185 = 0.5%（parse_error）
```

微调前这是主要问题（离线格式合规率 24.0%），
微调后离线合规率 100.0%、端到端 0.5%。

**已基本消除，不需要专门的恢复策略。** 现有的重试机制足够。

## 5. D 类：坐标塌陷

```
客机 1920×1080  预测 x 中位 508，54.9% 落在 [480,540]，不重复坐标仅 45.1%
离线 1024×768   预测 x 中位 425，19.2% 落在 [480,540]，不重复坐标 82.2%
```

模型坐标空间 0~1000 映射到 1920 宽时 x 乘 1.92，**508 → 真实 x≈975，
正好是屏幕水平中线**。

**只在客机上发生，训练同尺寸图上正常。** 疑似宽高比造成
（训练 4:3，客机 16:9），详见 §11.7.7。

**这不是恢复策略能解决的类别**——它是预处理问题。验证方法是
把验证集 letterbox 成 16:9 后重跑离线评测。

## 6. 优先级结论

```
A 类   94.4%    → Reflector 级联 1+2，本阶段主要工作
B 类   含于 A   → 先打开帧差把它分离出来，再谈
C 类    0.5%    → 不做
D 类   离线可测 → 一次 letterbox 实验即可定性，与恢复策略无关
```

**不为 C、D 类写恢复策略。** 分类体系的作用是把投入放对地方，
把四类都做一遍恢复策略是把 0.5% 和 94.4% 当成同等重要。

---

## 7. 本文档不声称的事

- **不声称这四类穷尽了所有错误。** 它们是 25 轮 185 步里观察到的，
  更长的任务（M4 交付物 4 要求 8 步以上）可能暴露新类别。
- **不声称 A 类频次可外推。** 25 轮、5 个任务、单一模型。
- **不声称 B 类真的独立存在。** 目前它只是 A 类里一个尚未分离的子集，
  分离需要帧差数据。
- **不声称级联 1 能挡住多少。** 「应该能吃掉大部分」是推断，
  触发率是 M4 要实测记录的指标，不是现在能给的数。
