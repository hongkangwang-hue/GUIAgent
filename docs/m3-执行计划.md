## 0. 先纠正一处

M2 实测暴露了三个失败模式（零动作报完成、连续重复动作、拆解粒度与应用行为
错配），很容易顺手把它们排进 M3。**不行。** `milestone-3` 的「明确不做」第 9 条：

> 不做鲁棒性与错误恢复相关工作，留到 M4。

M3 是**微调与横评**，M4 才是鲁棒性。M2 的失败数据在 M3 里只有一个合法用途：
**当提示词消融的对照基线**（任务 3）。真正的修复归 M4。

### 依赖关系

    0 ✅ → 1 → 2 → 5 → 6
              ↘ 3
           4 ──────↗（4 用 base 模型，5 之前跑完）
    7、8 与上面互不依赖，可并行挂机

**第 1 步是全局卡点。** 它量出的 `max_pixels` 决定第 2、3、4、5、6 步
能不能在 6.75GB 里跑起来。**先做它，别跳过。**

### 每一步的产出与命令

**第 1 步 —— 峰值显存实测**

    python -m finetune.train_lora --smoke --max-steps 1

先用 1 步探路，看加载 + 一次前向反向占多少。爆显存就调小
`--max-pixels`（默认 896×896）。**报告里一律用实测值，不写「约 3GB」。**

**第 2 步 —— smoke test**

    python -m finetune.train_lora --smoke

100 步、不保存权重。只回答「这条链路在这台机器上跑不跑得起来」——
数据加载 → 前向 → 反向 → 优化器更新，全走一遍。
**这一步过了，第 5 步的挂机训练才不会空跑一夜。**

**第 3 步 —— 本地部署**

实现 `llm/qwen_vl_local.py`，让它能通过 M2 的 `LLMBackend` 接口被调用。
验收的重点不是「能加载模型」，而是**加了本地后端之后 Agent 层一行都不用改**
（M3 验收标准 12）。产出：显存峰值、单次推理延迟、冷加载耗时。

**第 4 步 —— 微调前基线**

    python -m eval.action --local Qwen/Qwen2.5-VL-3B-Instruct --tag before

**基线必须自己跑。** 拿官方模型卡数字当基线、自测数字当结果，是无效对比。

**第 5 步 —— 正式训练**

    python -m finetune.train_lora

2 epoch、543 条、batch 1 + 梯度累积 8。每 200 步存 checkpoint。
挂机，产出 adapter（约 30-60MB）+ loss 曲线。

**第 6 步 —— 微调后对比**

    python -m eval.action --local Qwen/Qwen2.5-VL-3B-Instruct         --adapter finetune/outputs/<run>/adapter --tag after
    python -m eval.action --report

**同一套提示词、同一个坐标空间、同一个验证集**，只换 adapter。

**第 7 步 —— 提示词消融**（客机，唯一需要客机的一步）

3 个版本 × 5 个基础任务 × 3 次 = 45 次执行。**必须在同一套 reset 下跑，
并沿用 `precondition`**——M2 实测显示只改环境就能让成功率从 44% 变 75%，
环境波动远大于提示词版本之间的预期差异。

**第 8 步 —— 三个点名模型的零样本定位**

    python -m eval.grounding --provider dashscope --platform desktop
    python -m eval.grounding --provider zhipu --model glm-4.6v --platform desktop
    python -m eval.grounding --provider nvidia --platform desktop

Llama 那一档的**预期结论是「不可用」**（未经坐标输出训练），
验证到能得出这个结论即收工。这是合法且有价值的横评发现。

需要 NVIDIA NIM 的 key（免费额度够）：https://build.nvidia.com/

## 3. M2 实测给 M3 的四条约束

这四条都是这周实测出来的，不是推测。

### ① 消融实验的环境必须先清干净，否则结论是噪声

M2 的对照数据：**同一份代码、同一个模型、只改环境**——

| | 脏环境 | 清场后 |
|---|---|---|
| 成功率 | 44% | **75%** |
| 零动作报完成 | 49% | **0%** |

**环境差异带来的波动（31 个百分点）远大于三个提示词版本之间的预期差异。**
消融跑 45 次执行，中间只要混进一次记事本会话恢复或一个卡住的模态框，
P1/P2/P3 的排序就没有意义。

**所以 M3 任务 3 开跑前，必须确认 `tasks/reset_desktop.py` 在客机上生效**，
并在消融报告里记录每一版跑的是同一套 reset。

### ② 消融的样本量 n=15/版本 撑不起强结论

同一个任务（`发送消息`）在四次测量里给出 **0/5、1/5、5/5、0/5**。
在这种方差下，n=15 分不出 P2 比 P1 好还是运气好。

验收标准 9 已经要求「说明 n=15/版本 的样本量对结论强度的限制」——**照做，
并且分任务报**，不要只给一个总成功率。分任务能看出「P2 只在多步任务上有用」
这类有信息量的模式，总成功率会把它抹平。

### ③ 模式 B 在这 5 个任务上大概率不提升成功率

M2 全部 170 步的实测：`grounding_ms` 合计 **0.2ms**，来源全是 `native`，
**没有一次失败是定位造成的**。失败全在规划层（提前报完成、重复动作、
拆解错配）和环境层。

模式 B 换的是坐标的**来源**，换不掉规划层的毛病。所以：

- **预期收益在 token 成本，不在成功率**（送 API 的截图可降分辨率）
- 降级路径 4 已经写明「模式 B 成功率低于模式 A 不视为失败」——这条会用上
- 报告里要**主动**给出这个预期与实测的对照，而不是等数据难看再解释

`LocalVLMGrounding` 仍是 P0，因为大纲 W5 要求微调成果在系统里承重。
**做，但对它的期望要摆正。**

### ④ 智谱免费档跑不了批量评测，横评档 5 要换付费模型

08-24 实测：`glm-4.6v-flash` 单次调用正常（7.3s / 1305 tokens，坐标在
范围内），但**连续 3 次必撞 429**，重试退避到 30s 仍然失败：

    限流，5s 后重试… / 15s 后重试… / 30s 后重试…
    Error code: 429 - code 1305「该模型当前访问量过大」

免费 flash 档是共享配额。M3 横评档 5（GLM-4V-9B）要在 ScreenSpot 上跑
几百个样本，按这个表现根本跑不完。三条路：

| | 做法 | 代价 |
|---|---|---|
| A | 每次调用间隔拉到 60s+ | 几百样本要十几小时，且仍可能失败 |
| **B** | **换智谱付费视觉模型** | 首选。账户余额够跑一批小样本 |
| C | 走降级路径 5，引用公开分数并标注非实测 | 里程碑允许，但少一组自测数据 |

**选 B，已确认可用：`glm-4.6v`**（去掉 `-flash` 后缀即付费档）。
08-24 实测 3/3 全通，代码一行没改，只改了 `.env` 的 `ZHIPU_MODEL`——
这本身也是对 `LLMBackend` 抽象的一次小验证。

坐标一致性很好，三次分别是 (456,310) / (455,309) / (456,307)，波动 < 3px。

**但延迟在连发时逐次上升，要算进排期：**

| 第几次 | 延迟 | tokens |
|---|---|---|
| 1 | 11.5s | 1458 |
| 2 | 17.5s | 1421 |
| 3 | **44.3s** | 1445 |

token 数几乎不变而延迟涨了近 4 倍，不像随机波动，像连发时的限速梯度。
按平均 25s/次估，ScreenSpot-Desktop 子集（约 330 样本）要跑 2-3 小时；
若延迟稳定在 44s 则接近 4 小时。**排进挂机线，留足夜间时间，不要放在
人力线的白天。**

顺带一条通用教训：**免费档能不能跑通单次调用，和能不能跑批量评测，
是两个问题。** M1 D1 只验了前者，所以这个坑到 M3 前夕才浮出来。
M3 接任何新平台时，第一件事应该是**连发 10 次**而不是单发 1 次。

### ⑤ 端到端对比要沿用 M2 的 `precondition` 机制

M2 加的起点检查（reset 之后、Agent 之前验一次环境）在实战里拦下了 5 轮
无效数据——消息程序没开时，那 5 轮本会被记成 0/5 失败，把总成功率从
75% 拉到 60%，而且从数字上完全看不出来。

M3 任务 9 的 30 轮对比、任务 3 的 45 次消融，**都要带这个机制**。
