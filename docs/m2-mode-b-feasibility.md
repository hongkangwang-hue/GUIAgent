# 模式 B 可行性验证报告 —— M2 交付物 12 / 验收标准 9

> 同时是 M3 前置件④（`target_description` 结构化输出验证）。
> 原始数据：`docs/m2-mode-b-raw.json`。复现方式见文末。

## 结论：模式 B 可行，不需降级

规划模型能**稳定**产出足够具体的元素描述。**M3 按原计划实现
`LocalVLMGrounding`，无需降级为「模型出坐标 + 本地模型复核纠偏」形态。**

| 指标 | 结果 |
|---|---|
| JSON 可解析率 | **35/35（100%）** |
| `target_description` 字段完备率 | **29/29（100%）** |
| 明显含糊、无法定位的描述 | **0/29** |
| 同一指令重复 5 次的输出 | **完全一致**（1 种） |
| 单次调用延迟 | p50 **993 ms**，p95 1297 ms |

---

## 要验证什么

模式 B 让规划模型只输出「点什么元素」的自然语言描述，坐标交给本地
grounding 模型。这套设计成立的**前提**是：规划模型能稳定产出
**足够具体、能唯一定位**的描述。

它若做不到——经常漏字段，或输出「那个按钮」这种谁也定位不了的话——
**模式 B 从设计上就不成立**，M3 的实现方案必须改。这就是本实验被固定在
M2 而非 M3 的原因：越早知道越好。

## 实验设置

| 项 | 值 |
|---|---|
| 模型 | `qwen3-vl-8b-instruct`（阿里云百炼） |
| 提示词 | `prompts/executor_modeb_v1.yaml` |
| 素材 | ScreenSpot-v2 桌面子集，30 条指令覆盖 **8 张不同界面** |
| 稳定性组 | 1 条指令 × 5 次重复 |
| 随机种子 | `20260823` |

### 提示词与模式 A 的唯一差别

`executor_modeb_v1` 由 `executor_v1` 改造而来，**只动两处**，
其余（角色设定、动作清单、完成判定、原则）逐字保持一致，
以便对照实验中「输出形态」是唯一变量：

1. 「坐标系」一节 → 换成「怎么描述元素」（给出四级线索优先级与反例）
2. few-shot 的输出 → 用 `target_description` 取代 `x` / `y`

### 素材选择的一处修正

原计划按 M2 任务 5 的字面要求「3 个界面场景各测 10 次」取样。
**数据不支持**：ScreenSpot-v2 桌面子集共 231 张图 / 334 条指令，
其中 156 张只有 1 条指令，最多的一张也只有 5 条——**没有任何一张能
单独供出 10 条**。

因此按任务的**意图**执行：保证覆盖足够多的不同界面（实得 8 张），
总量凑到 30 条（同时满足 M3 前置件④的「20-30 次」）。
**不假装满足了「每场景 10 条」。**

## 1 结构化输出：字段完备率 100%

35 次调用全部返回可解析的 JSON。按模型的选择分类：

| 模型选择 | 次数 | 是否该有 `target_description` |
|---|---:|---|
| 选了需指向元素的动作 | **29** | 是 |
| 判定子任务已完成（`done`） | 6 | 否 |
| 选了无需目标的动作（`type`/`key`/`wait`） | 0 | 否 |

**在需要目标的 29 次里，29 次都给出了 `target_description`——缺失率 0%。**

### 分母的口径必须说清

本实验第一版把「没有 `target_description`」一律算作字段缺失，
得出 85.7% 的完备率。**那个数字是错的**：其中 6 次是模型输出
`{"done": true}`——它判断子任务已经达成，压根没选动作，
自然不需要目标字段。**那是正确行为被算成了缺陷。**

修正后分母只取「模型确实选了一个需要指向某元素的动作」的那些。

> 这与 OCR 实验里「中英混排准确率」那个假指标是同一类问题：
> **口径不明确时，数字会指向错误的方向，而且不会报错。**
> 报告任何比率时都必须写明分母是什么。

### 那 6 次 `done` 暴露了素材的一处不匹配

它们不是模型的错，是**我用 ScreenSpot 指令当子任务目标造成的**。
ScreenSpot 的指令语义是「指出执行 X 的那个元素」（定位任务），
而模式 B 的提示词把它当作「达成 X 状态」（执行任务）。

例如指令 `check bluetooth` 配一张显示蓝牙已开启的截图，
模型回答：

> `{"done": true, "thinking": "截图显示蓝牙状态为 'On'，表明蓝牙已开启..."}`

这个判断本身是**合理的**。在 M2 的真实任务里子任务目标由 Planner 产出，
语义明确为「要达成什么」，不会有这种歧义。

**这是本实验的一处已知局限，不是模型缺陷。**

## 2 描述质量：比人工语料更具体

用四类可定位线索做启发式打分（引号内的界面原文 / 控件类型词 /
方位词 / 颜色），与 ScreenAgent 数据集里 **1168 条标注者手写**的
元素描述对照：

| | 模型输出（n=29） | 人工语料（n=1168） |
|---|---:|---:|
| 平均线索数 | **2.31 / 4** | 0.60 / 4 |
| 平均长度 | 22.6 字 | 23.3 字 |
| 明显含糊 | **0** | — |

**长度相当，但线索密度接近人工的 4 倍。**

线索命中分布：控件类型词 25/29、方位词 22/29、引号内原文 20/29、
颜色 0/29。模型主要靠「**什么类型的控件 + 在哪个区域 + 上面写着什么**」
三者组合定位，与提示词里给出的优先级一致。

实际样例：

```
指令: switch to alerts mode
描述: 标签页栏中的「Focus」标签

指令: disable "allow notifications" setting
描述: 写着「Allow Notifications」的开关按钮，当前处于开启状态

指令: zoom out
描述: 地图界面右下角的减号按钮
```

### 这个判据的局限

启发式打分**抓得住「那个按钮」这种明显含糊的，抓不住「写着确定的按钮」
但屏幕上有三个「确定」这种情况**。它衡量的是描述的**信息密度**，
不是**定位正确性**。

**真正的可用性只有接上 grounding 模型跑一遍才知道**，那是 M3 的工作。
本报告的结论止于「描述的形态支撑得起模式 B」。

---

## 3 稳定性：5 次重复输出完全一致

同一张截图、同一条指令（`zoom out`）连问 5 次：

```
×5  地图界面右下角的减号按钮
```

**5 次输出逐字相同。** M2 任务 5 的原话是「测试它能否**稳定**给出足够
具体的描述」，单次成功回答不了这个问题，因此单设这一组。

样本量小（1 条指令 × 5 次），只能说明该模型在此温度设置下输出确定性高，
不能外推到全部指令。

---

## 4 延迟：模式 B 的成本结构

| | 值 |
|---|---|
| 单次规划调用 p50 | **993 ms** |
| p95 | 1297 ms |

**模式 B 的单步需要两次模型调用**（规划一次 + 本地 grounding 一次），
而模式 A 只需一次。这 993ms 是其中的规划部分；grounding 部分的延迟
要等 M3 本地部署后实测。

模式 B 的收益是**高分辨率截图不出本机**（只有规划层上传，且可降分辨率），
代价是多一次调用。**这个权衡的完整数据在 M5 的模式 A/B 消融中给出。**

## 5 对 M3 的结论

| 问题 | 结论 |
|---|---|
| 模式 B 是否成立 | **成立**，按原计划实现 `LocalVLMGrounding` |
| 是否需降级为「出坐标 + 复核纠偏」 | **不需要** |
| 提示词是否需要重新设计 | 不需要，`executor_modeb_v1` 可直接用 |
| 需要注意什么 | 子任务目标的语义必须是「要达成什么」，不能是定位式描述（见 §1） |

### 尚未回答的问题

- 描述的**定位正确性**——需接上 grounding 模型（M3）
- 本地 3B 模型能否理解这种密度的描述（M3）
- 端到端成功率与模式 A 的对比（M5）
- 其他两个规划模型（GLM-4V / Llama 3.2 Vision）是否有同样的稳定性

```bash
python scripts/verify_mode_b.py --total 30 --repeats 5
```

需要 `.env` 中配置 `DASHSCOPE_API_KEY`，以及已下载的 ScreenSpot-v2：

```bash
python scripts/prepare_datasets.py --download --extract
```

成本：35 次调用。本次运行未配置单价环境变量，因此成本核算显示为
不可信（`priced=False`）——**这是有意的设计**：拿一个恒为 0 的成本去比
上限，等于悄悄关掉了成本熔断，不如老实承认这一路没有成本保护。
