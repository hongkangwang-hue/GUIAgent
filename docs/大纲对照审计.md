## 1. 与大纲**直接冲突**的（必须改）

### 1.1 合规：客机内有个人数据

**大纲原文**（合规与落地说明第 5 条）：

> 项目中涉及的所有操作均在本地计算机上进行，**不包含任何个人数据或敏感信息**。

**现状**：客机登录了开发者本人的微软账号，OneDrive 正在同步个人文件。
M2 实测期间 Agent 曾对着该账号的登录框连按 12 次回车，并修改保存了含
API key 的 `.env`。

**这是与大纲原文的直接冲突**，不是我们自加标准的问题。两条路：

- **清理客机**：改本地账户 → 改显示名 → 卸载 OneDrive → 删除已同步文件
  → 重拍快照。代价：M2 的实测数据环境变了，严格说不可比（但 M2 已验收，
  M3 起用新环境即可）。
- **不清理**：则技术报告与 M5 必须如实写明，且**不能引用大纲第 5 条**
  声称合规。

> 已在 `docs/执行计划.md` 记录为「用户已决定不清理」。但当时的依据是
> 我们自己的 M0 约束，**没有意识到大纲原文也这么写**。这一条需要重新决定。

### 1.2 M3 微调目标偏离

**大纲 W5 任务 3**：

> 对比微调前后模型在 **GUI 任务理解与动作生成** 上的效果

**我们的 `milestone-3`**：把目标窄化为 **grounding（指令 → 坐标定位）**，
指标定为 **ScreenSpot 命中率**。

后果：**训练数据与指标不匹配**。ScreenAgent 提供的是
「截图 + 任务目标 → 动作坐标」（正是大纲要的动作生成），
而 ScreenSpot 要的是「截图 + 元素描述 → 坐标」。569 条样本只有 135 个
不重复描述，「Insert a circle」出现 17 次对应 17 个不同坐标——
**对 grounding 是矛盾监督，对动作生成是正常的多步轨迹。**

**按大纲口径，应当把微调目标改回「动作生成」**，数据立刻匹配，
且不需要补任何数据。

### 1.3 M5 验收标准 9 的表述

`milestone-5` 写着「不含真实个人账号与个人数据」，与 1.1 的现状冲突。
随 1.1 的决定一并修改。

### 2.1 模式 B 要不要砍 —— 单独说

**模式 B 是全项目最大的一块「超出大纲」内容**：M2 的可行性验证、
M3 的 `LocalVLMGrounding`（P0、两个完整白天）、M5 的 A/B 消融，
全都建立在它上面。大纲从头到尾没有这个概念。

但它同时是**唯一让微调成果在系统里承重的机制**。大纲 W5 要求
「微调后的模型权重 + 微调效果对比分析报告」——**没要求把微调模型接进系统**。
按大纲，训练完跑个对比、写个报告就够了。

三种处理：

| | 做法 | 后果 |
|---|---|---|
| **A** | **全砍**，M3 只做「微调 + 前后对比报告」 | 完全贴合大纲，M3 工作量减半；微调成果不进系统 |
| **B** | 保留为**可选加分项**，P0 降为 P2，跑不通就不提 | 折中；仍占 M3 的日程 |
| C | 维持现状 | 大幅超出大纲 |

**按「一切以大纲为主」的原则，应选 A。**

## 4. 技术栈替换需要论证的三处

大纲点名了具体工具，我们换了别的。**每一处都要在报告里给出理由**，
否则算偏离：

| 大纲 | 我们用的 | 理由 | 记在哪 |

单请求推理，vLLM 的批处理与 PagedAttention 收益为零。**这个理由成立，
但要写下来**，不能只在 `milestone-3` 的「明确不做」里列一行。
