## 3. ⚠ 曾出现 Code 43，已修复 —— 原因是快速启动，不是驱动

环境搭建当天独显处于故障状态，`nvidia-smi` 报 "insufficient permissions"。**该报错具有误导性，真实原因不是权限：**

```
Get-PnpDevice -Class Display

Problem : CM_PROB_FAILED_POST_START     ← Code 43 的底层含义
Status  : Error
Service : nvlddmkm  →  State: Stopped
```

`CM_PROB_FAILED_POST_START` 的准确含义是**驱动已加载、设备已启动，但启动后设备报告失败**，与"设备认不出来"是两回事。

### 定性依据（排除硬件故障）

| 证据 | 说明 |
|---|---|
| PCI 枚举完整 | `VEN_10DE&DEV_2D59&SUBSYS_39F81043&REV_A1` 全部可读，`Present: True`。硬件故障通常报 Code 10/12 或读不全 |
| 30 天内零 `nvlddmkm` 事件 | 无 TDR、无崩溃重启。显存/核心物理问题一般会堆一片 Event 4101。它是**一次都没成功启动**，不是跑着挂了 |
| 驱动签名完整 | `IsSigned: True`，文件未损坏 |

### 修复方式 —— 关掉快速启动 + **重启**（不是关机再开机）

管理员 PowerShell（只关快速启动，保留休眠）：

```powershell
Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Power" -Name HiberbootEnabled -Value 0
```

然后**点「重启」**。修复后 `Get-PnpDevice -Class Display` 两块显卡均为 `CM_PROB_NONE`。

**为什么"关机再开机"没用**：本机原先 `HiberbootEnabled = 1`。快速启动是混合关机，会把内核会话连同设备错误状态一起休眠，下次开机原样恢复——所以必须走完整的重启路径才能重新初始化设备。这是 NVIDIA 笔记本 Code 43 最常见的放大器。

> 驱动本身**没有更换**，仍是 572.90。当时怀疑的"驱动过旧"不是本次故障的原因，但它确实引出了第 4 节的另一个问题。

## 4. ⚠ PyTorch 的 cu 版本有两个独立的陷阱

### 陷阱一：索引路径已变，文档里的 cu128 在选择器上找不到了

pytorch.org 版本选择器（Windows + pip + 稳定版）现在的 CUDA 档位是 **cu126 / cu130 / cu132**，**cu128 已从选择器移除**。但 `download.pytorch.org/whl/cu128` 索引仍然存活，最新为 torch 2.11.0+cu128：

```powershell
pip index versions torch --index-url https://download.pytorch.org/whl/cu128
# torch (2.11.0+cu128)
```

### 陷阱二：CUDA runtime 不能高于驱动支持的上限（新增，文档原先未覆盖）

**第一次按选择器装了 cu130，结果 CUDA 不可用**——但失败原因与文档第 3 节描述的那种不同：

```
驱动 572.90  →  nvidia-smi 头部 CUDA Version: 12.8   ← 驱动支持的上限
torch cu130  →  torch.version.cuda = 13.0            ← 需要的 runtime
                13.0 > 12.8  →  cudaErrorNotSupported
```

```
UserWarning: cudaGetDeviceCount() returned cudaErrorNotSupported,
likely using older driver or on CPU machine
```

**这是两个必须分开判断的失败模式**，都表现为"能 import 但用不了"：

| 失败模式 | 症状 | 判据 | 修法 |
|---|---|---|---|
| 构建不含本卡算力 | `is_available()` 可能为 True，**一运算就崩** `no kernel image is available` | `sm_XXX in torch.cuda.get_arch_list()` | 换含该算力的 cu 版本 |
| **runtime 高于驱动上限** | `is_available()` 直接 **False**，报 `cudaErrorNotSupported` | 比对 `torch.version.cuda` 与 `nvidia-smi` 头部的 `CUDA Version` | **降 torch 的 cu 版本**，或升驱动 |

注意后者的 `get_arch_list()` **仍然含 sm_120**——光看 arch_list 会误判为"装对了"。选版本时必须**两头都核**：既要 cu 版本含本卡算力，又要其 CUDA runtime ≤ 驱动支持上限。

### 本机的正确装法

```powershell
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu128
```

满足文档「sm_120 → cu128 或更高」，且 12.8 正好等于驱动 572.90 的上限。若日后把驱动升到 580+，可改用 cu130/cu132；驱动不升就不要用。

### 三重判据实测结果

| 项 | 实测值 |
|---|---|
| torch | **2.11.0+cu128** |
| torchvision | 0.26.0+cu128 |
| `torch.version.cuda` | 12.8 |
| `torch.cuda.is_available()` | **True** ✅ |
| `torch.cuda.get_arch_list()` | `['sm_75', 'sm_80', 'sm_86', 'sm_90', 'sm_100', 'sm_120']` ✅ 含 sm_120 |
| `torch.cuda.get_device_capability(0)` | `(12, 0)` → `sm_120` |
| GPU 矩阵乘实测 | ✅ 跑完，`(x @ x).sum()` = -1277.005859375 |
| bitsandbytes | 0.50.1，4-bit 加载 Qwen2.5-0.5B-Instruct 成功，占用 **0.45 GB** |

## 7. ⚠ PaddlePaddle 3.3.1 需要关闭 oneDNN

paddlepaddle 3.3.1 的新执行器（PIR）在 oneDNN 路径上有 bug，OCR 推理直接崩：

```
NotImplementedError: (Unimplemented) ConvertPirAttribute2RuntimeAttribute
not support [pir::ArrayAttribute<pir::DoubleAttribute>]
(at ..\paddle\fluid\framework\new_executor\instruction\onednn\onednn_instruction.cc:118)
```

**绕过方式**——设环境变量后 OCR 正常：

```powershell
$env:PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT = "False"
```

注意 `FLAGS_use_mkldnn=0` 和 `FLAGS_enable_pir_api=0` **都不管用**，PaddleX 用自己的开关。建议写进 `.env` 或运行脚本，否则每次新开终端都要重设。

## 9. 本次为适配新版本所做的代码改动

`perception/ocr_engine.py` 的 `_parse` 只认 paddleocr 2.x 的 list 输出，而本机装的
**paddleocr 3.7.0 改为按图返回映射**（`rec_texts` / `rec_polys` / `rec_scores` 三个
等长列表），导致 `KeyError: 0`。已新增 `_parse_v3` 分支处理该格式，2.x 路径保持不变。

这正是该函数原注释预判的情况——「OCR 库的输出格式在版本间变过好几次，写死一种解析必然踩雷」。

`perception/` 与 `control/` 的其余代码未改动。

  `--force-reinstall` 会把 fsspec 升到 2026.7.0 与 datasets 冲突，需回退：
  `pip install "fsspec[http]==2026.6.0"`，之后 `pip check` 干净。
- **PaddlePaddle 装的是 CPU 版**（`paddlepaddle==3.3.1`），符合文档要求。它对 Blackwell 的支持进度独立于 PyTorch。
- `requirements.lock.txt` 已按本机重新生成（**机器相关，不要套用到另一台**）。
- Git Bash 终端跑 env_check 会因 GBK 编码在 rich 表格处抛 `UnicodeEncodeError`，
  用 PowerShell 或设 `PYTHONIOENCODING=utf-8`。
